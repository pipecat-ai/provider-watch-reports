# Provider watch — 2026-10-28

- Two shipped defaults retire within three weeks. `google/tts`'s `gemini-3.1-flash-tts-preview` shuts down on the Gemini API on 2026-11-17 and the replacement Google names, `gemini-3.8-flash-lite-tts`, is not served by Cloud TTS at all — so the shared default probably has to become backend-dependent, and that is a call nobody has made (`reports/google/tts/2026-10-28.md`). `sarvam/tts` still defaults to `bulbul:v3`, which Sarvam retires on Voice Agents on 2026-11-10. Behind them sits the gpt-4.1 cluster: the same default shuts down 2027-01-14 across `openai/llm`, `openai/responses-llm` and `openrouter/llm`, OpenAI's named successor `gpt-6-luna` regresses on aiewf-eval (91.8% against 95.9%) and probes slower everywhere, and the five `examples/flows/yaml` bots pin gpt-4.1 explicitly and retire with it. `openai/tts` is the same shape one step further on — every `/v1/audio/speech` model is now deprecated with a 2027-01-06 shutdown and the named replacement is a Realtime model the speech endpoint refuses to serve.
- The `google/vertex-llm` default bump that landed last week looks like a regression. Commit 714573d00 (2026-10-20) moved the default to `gemini-3.8-flash`; re-measured this run it is roughly twice as slow as `gemini-3.6-flash` on a trivial prompt (TTFAT 1210 ms against 685 ms, medians of 5) and one run in five produced no chunk at all and tripped the service's 20 s `stream_idle_timeout_secs`, the same tail the 2026-10-12 sweep saw. The quality case holds up on aiewf-eval, but the stated reason does not: no Google page announces a Vertex retirement of `gemini-3.6-flash`, and `google/llm` still defaults to it, so the two units now disagree (`reports/google/vertex-llm/2026-10-28.md`).
- `openai/stt` got worse since the last run and is the most user-visible breakage of the date: appending audio before `session.update` lands no longer just logs an error, it truncates the transcript. An ad-hoc client reproduces it deterministically on both realtime models — a clip reading "The quick brown fox jumps over the lazy dog. Pipecat makes voice agents easy to build." comes back as "It's easy to build." — and through the service 4 of 5 probe runs truncated where the same probe was 6/6 clean on 2026-10-12. The service connects in `setup()` and appends from the first `InputAudioRawFrame`, so any user who speaks in the opening moments loses the start of the utterance. Four more services are broken on a configuration their own docs hand you, none of them new: `openai/realtime` still hangs on any session carrying an MCP tool: #6329 fixed the event half, but `ConversationItem.type` has no `mcp_list_tools`, and a modeled event that fails validation raises out of `_receive_task_handler`, so the session goes quiet with no ErrorFrame. `speechmatics/stt` has two routes to a permanently dead session at 4 weeks open — `punctuation_overrides` is rejected as a `protocol_error`, and `Settings(turn_detection_mode="vad")` raises `AttributeError` at StartFrame, the form Speechmatics' own Pipecat page passes. `aws/stt` logs "Converting from 24000 Hz to 16000 Hz" and declares 16000 in the presigned URL while forwarding the bytes untouched, though the clamp is not even needed. And `google/vertex-realtime`'s `pipecat init` snippet is still, 8 weeks on, the only one of 104 entries in `SERVICE_CONFIGS` that fails `compile()`.

Eight were raised this run and are mostly one-field pass-throughs; the two worth a look beyond that are #6400 (Simli Trinity-2 framing, OpenAI Live audio and the simli-ai 2.1 bump, several changes at once) and #6434, which picks the lowest reasoning effort for `gpt-6.1-terra` — a model with no aiewf-eval row yet.
