## Changes to consider

**High**

- [asyncai/tts](https://github.com/pipecat-ai/provider-watch-reports/blob/main/reports/asyncai/tts/2026-09-01.md) — Server error frames are dropped by the websocket receive loop — Async's error frame is `{error_code, message, request_id, extra}` with no `context_id` (reproduced with a bogus voice id: two `error_code: BAD_REQUEST` frames). `_receive_messages` handles only `final` and `audio`, so the frame falls through the context check, is logged as `Ignoring message from unavailable context: None` and nothing is pushed upstream: the turn yields no audio and the app sees no error. The message the loop drops right after init is `{event: init_ack, request_id, context_id, context_restored}`, carrying a server-assigned context id — harmless, but it logs the same unavailable-context line on every connect. — *needs a call: whether an `error_code` frame should push an ErrorFrame and close the context, or only be logged*
- [aws/other](https://github.com/pipecat-ai/provider-watch-reports/blob/main/reports/aws/other/2026-09-01.md) — `invoke_agent_runtime` is called without `runtimeSessionId`, so turns are not pinned to one AgentCore session — AWS: "By providing the same session identifier across multiple requests, you can maintain conversation context, allowing the agent to reference previous interactions", and without a consistent ID each request may be routed to a new microVM with cold-start latency. The default payload transformer sends only the latest user message, so with no session ID the agent has neither Pipecat-side history nor AgentCore-side continuity. AWS recommends a UUID; botocore's SessionType is min 33 / max 256 characters. — *needs a call: Where the ID comes from — a constructor argument, or one generated per conversation — and whether teardown should call StopRuntimeSession.*
