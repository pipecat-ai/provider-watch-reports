# Async TTS — 2026-09-01

No change at Async in the last day — same three models, same request schema, no announcements since 2026-06-02 — and both classes synthesize; the open item is still the websocket receive loop discarding error frames.

## What's new for Pipecat

### PRs
- https://github.com/pipecat-ai/pipecat/pull/5464 — Apply model, voice and language changes by opening a new session (still open; runtime `Settings` updates are otherwise stored and warned about, not applied)

### To consider
- **Server error frames are dropped** (high, since 2026-08-31) — reproduced again: a websocket init with an invalid voice id gets two `{"error_code": "BAD_REQUEST", "message": "Invalid initialization data format: ...", "request_id": "..."}` frames, neither with a `context_id`. `_receive_messages` understands only `final` and `audio`, so the frame takes the "unavailable context" branch, logs `Ignoring message from unavailable context: None` and continues — no `ErrorFrame`, no audio, silent failure. The message the loop drops immediately after init is now identified: `{"event": "init_ack", "request_id": ..., "context_id": <server uuid>, "context_restored": false}`. It is undocumented and benign, but its server-assigned context id never matches ours, so every connect logs an unavailable-context line. — *Needs a call: whether an `error_code` frame should push an ErrorFrame and close the context, or only be logged.*
- **`speed_control` and `stability` not exposed** (low, since 2026-08-31) — both are documented HTTP request fields and `AsyncAITTSSettings` adds no fields over `TTSSettings`. Async's model page still restricts them to `async_flash_v1.0`, so on the default they are accepted and ignored. — *Needs a call: a stance on exposing settings that the default model accepts but does not honor.*
- **Language map is wider than the default model** (low, since 2026-08-31) — `language_to_async_language` maps 16 `Language` values; the model page gives `async_flash_v1.5` six (en, es, fr, de, it, pt) and the other nine to `async_flash_v1.0` only, and `nl` appears in neither the model page nor the HTTP reference's list of language codes. — *Needs a call: whether to warn per model, document the split, or leave the map model-agnostic.*

`async_flash_v1.5` is still Async's recommendation for voice agents, so the default stands. `async_pro_v1.0` remains English-only and quality-tier, not a real-time default candidate, and `Settings.model` is a free-form string with no allowlist, so all three are already selectable.

The previous report's note about `probe.py` stalling on the websocket class still applies and is unchanged: `TTSService._maybe_pause_frame_processing` holds frame processing until a `BotStoppedSpeakingFrame` the bare probe pipeline never emits. It is a harness limitation shared by every websocket TTS service with `pause_frame_processing=True`, not an Async defect.

## Verification

| model            | class / path                 | ok | latency                     | note |
| ---------------- | ---------------------------- | -- | --------------------------- | ---- |
| async_flash_v1.5 | AsyncAIHttpTTSService        | ✅ | 2.55 s wall for the turn    | real class via `run_test`; 126,720 bytes in one `TTSAudioRawFrame`. `probe.py` cannot build it (`aiohttp_session` is a required constructor arg) |
| async_flash_v1.5 | AsyncAITTSService (probe.py) | ⚠️ | —                           | timed out at 90 s with no output flushed; the `pause_frame_processing` stall described above |
| async_flash_v1.5 | raw websocket, valid voice   | ✅ | first audio 274 / 275 / 267 ms | the class's exact init + `force` message, with `language` null, omitted and `"en"`; all three synthesize |
| async_flash_v1.5 | raw websocket, bad voice id  | ✅ | —                           | two `error_code: BAD_REQUEST` frames, neither carrying a `context_id`; `init_ack` observed on every successful connect |

The websocket `context_id` must be a UUID — the server rejects a free-form one with `BAD_REQUEST` — which the service satisfies, but an ad-hoc probe must too. `probe.py` does not read `ASYNCAI_VOICE_ID` (`voice` is a settings param, not an `include_params` entry), so a websocket probe needs `--setting voice=…`. Ad-hoc scripts are in `.pw-scratch/asyncai_*.py`.
