# Async TTS — 2026-08-31

`async_flash_v1.5` remains Async's recommended model and both classes synthesize correctly; the item to act on is the websocket receive loop silently discarding Async's error frames.

## What's new for Pipecat

### PRs
- https://github.com/pipecat-ai/pipecat/pull/5464 — Apply model, voice and language changes by opening a new session (open since 2026-08-27; runtime `Settings` updates are otherwise stored and warned about, not applied)

### To consider
- **Server error frames are dropped** (high, since 2026-08-31) — probing a websocket connection with an invalid voice id, Async replies `{"error_code": "BAD_REQUEST", "message": "Invalid initialization data format: ...", "request_id": "...", "extra": null}`. The frame carries no `context_id`, so `_receive_messages` — which understands only `final` and `audio` — takes the "unavailable context" branch, logs `Ignoring message from unavailable context: None` and continues. No `ErrorFrame` is pushed and the turn produces no audio, so a bad voice or model id fails silently. The same loop also drops the message the server sends immediately after the init message. — *Needs a call: whether an `error_code` frame should push an ErrorFrame and close the context, or only be logged.*
- **`speed_control` and `stability` not exposed** (low, since 2026-08-31) — both are documented request fields and `AsyncAITTSSettings` adds no fields over `TTSSettings`. Async's model page states only `async_flash_v1.0` supports them, so on the default they are accepted and ignored. — *Needs a call: a stance on exposing settings that the default model accepts but does not honor.*
- **Language map is wider than the default model** (low, since 2026-08-31) — `language_to_async_language` maps 16 `Language` values; Async's model page gives `async_flash_v1.5` six languages (en, es, fr, de, it, pt), the other nine to `async_flash_v1.0` only, and lists `nl` for neither. An HTTP call with `language=ja` on the default model returns 200 with audio, so nothing tells the user the code did not apply. — *Needs a call: whether to warn per model, document the split, or leave the map model-agnostic.*

Dropped from the previous report: "a websocket TTS turn synthesizes but the pipeline never finishes". It reproduces, but it is `probe.py`'s harness, not this service. `TTSService._maybe_pause_frame_processing` pauses frame processing while an audio context is open and only resumes on `BotStoppedSpeakingFrame`, which the harness — a bare `[Source, service, Sink]` pipeline with no output transport — never emits, so the `EndFrame` stays queued. `ElevenLabsTTSService`, which also sets `pause_frame_processing=True`, stalls identically; the earlier control, `CartesiaTTSService`, does not only because it sets `pause_frame_processing=False`. Every websocket TTS unit with the pause enabled will report this until the harness sends the frame.

Also for the record: `async_pro_v1.0` is not a default candidate (English-only, and Async reserves the real-time recommendation for Flash v1.5), and `Settings.model` is a free-form string with no allowlist, so users can already select any of the three.

`probe.py` does not read `ASYNCAI_VOICE_ID` (`voice` is a settings param, not an `include_params` entry), so the websocket probe needs `--setting voice=…`. Ad-hoc scripts are in `.pw-scratch/asyncai_*.py`.
