# Async TTS — 2026-08-31

`async_flash_v1.5` is still Async's recommended model for voice agents, so the default stands; the finding to act on is that a websocket turn leaves the pipeline unable to shut down.

## What's new for Pipecat

### PRs
- https://github.com/pipecat-ai/pipecat/pull/5464 — Apply model, voice and language changes by opening a new session (open since 2026-08-27; runtime `Settings` updates are otherwise stored and warned about, not applied)

### To consider
- **Pipeline never finishes after a websocket turn** (high, since 2026-08-31) — `AsyncAITTSService` synthesizes correctly (TTFB 241 ms, TTFA 441 ms, audio frames pushed and the context closed with `close_context`), but `EndFrame` never reaches the end of the pipeline: the probe harness waits ~79 s, cancels, and the process still does not exit. The keepalive task goes on sending `{"transcript": " "}` the whole time. The identical harness completes normally for `CartesiaTTSService`, so this is specific to this service. — *Needs a call: whether the stall is in this service's context-close / keepalive teardown or in the shared websocket TTS base.*
- **Server errors are silently dropped** (medium, since 2026-08-31) — Async's websocket sends error frames carrying `error_code`, `message` and `extra`; `_receive_messages` handles only `final` and `audio`, so an error is logged as "Ignoring message from unavailable context" and the turn hangs with nothing pushed upstream. Observed by probing with the voice unset. — *Needs a call: whether an `error_code` frame should push an ErrorFrame and close the context, or only be logged.*
- **`speed_control` and `stability` not exposed** (low, since 2026-08-31) — both are documented request fields (`speed_control` 0.7-2.0, `stability` 0-100) and `AsyncAITTSSettings` adds no fields over `TTSSettings`. A raw request with both set returns 200 on all three models, but Async's model page states only `async_flash_v1.0` supports them, so on the default they are accepted and ignored. — *Needs a call: a stance on exposing settings that the default model accepts but does not honor.*

Not a gap, for the record: `async_pro_v1.0` (English-only, highest quality) is new to the catalogue relative to what the service documents, but `Settings.model` is a free-form string with no allowlist, so users can already select it; at 1397 ms TTFB against 257 ms for `async_flash_v1.5` it is not a candidate for the streaming default, which Async's own model page reserves for Flash v1.5.
