# Async TTS — 2026-09-28

Nothing moved at Async — same three models, same request and websocket schemas, latest announcement still 2026-06-02 — and both classes synthesized end-to-end; the only change is that a rejected request now raises a generic error instead of nothing, which downgrades the open item rather than closing it.

## What's new for Pipecat

### PRs
Nothing.

### To consider
- **Server error frames are dropped** (medium, since 2026-08-31) — a raw tap on the socket shows a rejected init message drawing two frames keyed `error_code` / `message` / `extra` / `request_id` within 0.25 s, none carrying a `context_id`; `_receive_messages` therefore routes them to its "unavailable context" branch and discards them. Driving the real class the same way produced no audio and, roughly 3 s later at context completion, a single `ErrorFrame` reading `TTS context <id> completed with no audio`. That frame comes from `TTSService`, which has reported every zero-audio context since bf3c97882 (2026-08-25), not from Async's message — so the application learns that the turn failed but not that Async rejected it or why, and the failure surfaces a context-completion late rather than immediately. This is the change from the previous report, which found the path entirely silent. The same branch still swallows the undocumented connect ack (keys `event`, `context_restored`, `context_id`, `request_id`), logging `Ignoring message from unavailable context: <uuid>` on every healthy connect. — *Needs a call: whether an `error_code` frame should push an ErrorFrame carrying Async's message and close the context, or only be logged now that the base class reports the silence.*
- **`speed_control` and `stability` not exposed** (low, since 2026-08-31) — both are documented HTTP request fields and `AsyncAITTSSettings` still adds no fields over `TTSSettings`. Async's model page continues to restrict them to `async_flash_v1.0`, so on the default they are accepted and ignored, and the websocket init message has no slot for them. — *Needs a call: a stance on exposing settings that the default model accepts but does not honor, and that the websocket class cannot send.*
- **Language map is wider than the default model** (low, since 2026-08-31) — `language_to_async_language` maps 16 `Language` values; the model page gives `async_flash_v1.5` six (en, es, fr, de, it, pt) and the other nine to `async_flash_v1.0` only, and `nl` appears in neither the model page nor the HTTP reference's 15-code list. — *Needs a call: whether to warn per model, document the split, or leave the map model-agnostic.*

`async_flash_v1.5` is still Async's stated recommendation for voice agents, so the default stands. `async_pro_v1.0` remains English-only and quality-tier, not a real-time default candidate, and `Settings.model` is a free-form string with no allowlist, so all three are already selectable. No example or docstring pins a model string other than the default, and no service code changed since the last report.

`probe.py` still cannot drive either class. `AsyncAIHttpTTSService` needs an `aiohttp_session` constructor argument it has no way to supply. `AsyncAITTSService` stalls with a valid voice, because `TTSService._maybe_pause_frame_processing` holds frame processing until a `BotStoppedSpeakingFrame` the bare probe pipeline never emits — a harness limitation shared by every websocket TTS service with `pause_frame_processing=True`, not an Async defect. Run without `--setting voice=...` it instead fails fast on Async's rejection, because `build_kwargs` fills only `include_params` from the environment and the registry entry carries `voice` under `settings_params` with no `param_defaults`; that is a probe harness matter, not a gap in this unit. Both classes were probed instead through `run_test` (`.pw-scratch/asyncai_probe.py`), the websocket one sending the `BotStoppedSpeakingFrame` by hand, and the protocol was checked with a direct socket tap (`.pw-scratch/asyncai_socket_tap.py`).
