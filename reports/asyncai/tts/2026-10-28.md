# Async TTS — 2026-10-28

Nothing moved at Async this month — the same three models, the same HTTP and websocket schemas, and no announcement since 2026-06-02 — so the default stands and the three known items carry forward unchanged.

## What's new for Pipecat

### PRs
Nothing.

### To consider
- **Server error frames are dropped** (medium, since 2026-08-31) — a raw tap on the socket shows a rejected init message drawing two frames keyed `error_code` / `message` / `extra` / `request_id` within 31 ms, none carrying a `context_id`; `_receive_messages` keys entirely off `msg.get("context_id")`, so they land in the "unavailable context" branch and are discarded. Driving the real class the same way (an unknown `model_id` through `probe.py`) produced no audio and, ~3 s later at context completion, a single `ErrorFrame` reading `TTS context <id> completed with no audio` — that frame comes from `TTSService`, which reports every zero-audio context, not from Async's message, so the application learns the turn failed but not that Async rejected it or why, and learns it a context-completion late. The tap also pinned down the undocumented connect ack: `{"event": "init_ack", "request_id": ..., "context_id": <server-assigned uuid>, "context_restored": false}`. Because that `context_id` is the server's own and never one Pipecat created, the same branch swallows it and logs `Ignoring message from unavailable context: <uuid>` on every healthy connect. — *Needs a call: whether an `error_code` frame should push an ErrorFrame carrying Async's message and close the context, or only be logged now that the base class reports the silence.*
- **`speed_control` and `stability` not exposed** (low, since 2026-08-31) — both are documented HTTP request fields and `AsyncAITTSSettings` is still an empty subclass of `TTSSettings`, so the runtime surface is `model` / `voice` / `language` only, and neither class reads `Settings.extra` when building its request. Async's model page continues to restrict both to `async_flash_v1.0`, so on the default they are accepted and ignored, and the websocket init message has no slot for them. — *Needs a call: a stance on exposing settings that the default model accepts but does not honor, and that the websocket class cannot send.*
- **Language map is wider than the default model** (low, since 2026-08-31) — `language_to_async_language` maps 16 `Language` values; the model page gives `async_flash_v1.5` six (en, es, fr, de, it, pt) and the other nine to `async_flash_v1.0` only, and `nl` appears in neither the model page nor the HTTP reference's 15-code list. — *Needs a call: whether to warn per model, document the split, or leave the map model-agnostic.*

`async_flash_v1.5` is still Async's stated recommendation for voice agents, so the default stands; `async_pro_v1.0` remains English-only and quality-tier, and `Settings.model` has no allowlist, so all three are already selectable. The server's own rejection message enumerates exactly `async_flash_v1.0, async_flash_v1.5, async_pro_v1.0`, confirming the catalogue first-hand. No example or docstring pins a model string other than the default, and the voice UUID both examples hard-code (`e0f39dc4-…`) still synthesizes. No service code changed since the last report; `pyproject.toml` still has `asyncai = []`, so there is no SDK to pin.

One harness note, not a gap in this unit: `probe.py run` now drives `AsyncAITTSService` end-to-end, where the previous report found it stalling on `pause_frame_processing`. `AsyncAIHttpTTSService` still cannot be probed — it takes a required `aiohttp_session` constructor argument `probe.py` has no way to supply — so it was driven through `run_test` instead (`.pw-scratch/asyncai_http_probe.py`), and the protocol was checked with a direct socket tap (`.pw-scratch/asyncai_socket_tap.py`).
