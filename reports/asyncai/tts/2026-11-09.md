# Async TTS — 2026-11-09

Nothing moved at Async since the last run — three models, unchanged HTTP and websocket schemas, no announcement since 2026-06-02 — and `async_flash_v1.5` is also the fastest of the three through our class, so the default stands and the three known items carry forward.

## What's new for Pipecat

### PRs
Nothing.

### To consider
- **Server error frames are dropped** (medium, since 2026-08-31) — `_receive_messages` keys entirely off `msg.get("context_id")`, and Async's error frames (`error_code` / `message` / `extra` / `request_id`) carry none, so they land in the "unavailable context" branch and are discarded. This run reproduced it without contriving anything: build the service with no voice — which the Pipecat docs explicitly warn about, since `voice` has no default — and Async rejects the init with `Invalid initialization data format: ... voice.id  UUID input should be a string, bytes or UUID object [input_value=None]`, then rejects each subsequent `sendText` with `voice  Field required` because the session was never initialized. Three `BAD_REQUEST` frames inside ~160 ms, every one discarded; what the application sees is a single `ErrorFrame` reading `TTS context <id> completed with no audio`, emitted ~3 s later by `TTSService` for any zero-audio context, so it learns the turn failed but not that Async rejected it, why, or that the whole session is dead rather than just this turn. The same branch swallows the undocumented connect ack, `{"event": "init_ack", "request_id": ..., "context_id": <server-assigned uuid>, "context_restored": false}`; because that `context_id` is the server's own and never one Pipecat created, every healthy connect logs `Ignoring message from unavailable context: <uuid>`. — *Needs a call: whether an `error_code` frame should push an ErrorFrame carrying Async's message and close the context, or only be logged now that the base class reports the silence.*
- **`speed_control` and `stability` not exposed** (low, since 2026-08-31) — both are documented HTTP request fields and `AsyncAITTSSettings` is still an empty subclass of `TTSSettings`, so the runtime surface is `model` / `voice` / `language` only, and neither class reads `Settings.extra` when building its request. Async's model page continues to restrict both to `async_flash_v1.0`, so on the default they are accepted and ignored, and the websocket init message has no slot for them. — *Needs a call: a stance on exposing settings that the default model accepts but does not honor, and that the websocket class cannot send.*
- **Language map is wider than the default model** (low, since 2026-08-31) — `language_to_async_language` maps 16 `Language` values; the model page gives `async_flash_v1.5` six (en, es, fr, de, it, pt) and the other nine to `async_flash_v1.0` only, and `nl` appears in neither the model page nor the HTTP reference's 15-code list. — *Needs a call: whether to warn per model, document the split, or leave the map model-agnostic.*

`async_flash_v1.5` remains Async's stated recommendation for voice agents and is the fastest of the three through our class this run (TTFB 382 ms vs 402 ms for `async_flash_v1.0` and 1292 ms for `async_pro_v1.0`), so the default stands; `Settings.model` has no allowlist, so all three are already selectable, and all three synthesized. No example or docstring pins a model string other than the default, and the voice UUID both examples hard-code (`e0f39dc4-…`) still synthesizes. No service code changed since the last report, `tests/test_asyncai_tts.py` passes (6 tests), and `pyproject.toml` still has `asyncai = []`, so there is no SDK to pin.

Two harness notes, neither a gap in this unit. `probe.py run` never fills `voice` for this unit — `build_kwargs` resolves environment variables only for the registry entry's `include_params` (`api_key`), not its `settings_params` (`voice`) — so a bare `probe.py run --service AsyncAITTSService` sends `voice: {"mode": "id", "id": null}` and fails with zero audio; every probe below passes `--setting voice=…` explicitly. And `AsyncAIHttpTTSService` still cannot be probed at all, because it takes a required `aiohttp_session` constructor argument `probe.py` has no way to supply; it was exercised instead by replaying the exact payload `run_tts` builds against the live endpoint (`.pw-scratch/asyncai_tap.py`).
