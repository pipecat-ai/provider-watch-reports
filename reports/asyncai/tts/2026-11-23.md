# Async TTS — 2026-11-23

Async has not moved — three models, unchanged HTTP and websocket schemas, no announcement since 2026-06-02 — and `async_flash_v1.5` is still the fastest of the three through our class, so the default stands; the three known items carry forward and reading the streaming endpoint's reference for the first time surfaced a second silent-error path.

## What's new for Pipecat

### PRs
Nothing.

### To consider
- **Server error frames are dropped** (medium, since 2026-08-31) — `_receive_messages` keys entirely off `msg.get("context_id")`, and Async's error frames (`error_code` / `message` / `extra` / `request_id`) carry none, so they land in the "unavailable context" branch and are discarded; the same branch swallows the undocumented `init_ack`, whose server-assigned `context_id` is why every healthy connect logs `Ignoring message from unavailable context: <uuid>`. The 2026-11-09 run reproduced the failure mode without contriving anything (service built with no voice: three `BAD_REQUEST` frames in ~160 ms, all discarded, application told only `TTS context <id> completed with no audio` ~3 s later). The receive loop is byte-for-byte unchanged since then. — *Needs a call: whether an `error_code` frame should push an ErrorFrame carrying Async's message and close the context, or only be logged now that the base class reports the silence.*
- **Quota-exhaustion marker played as audio** (medium, since 2026-11-23) — Async's reference for `POST /text_to_speech/streaming`, the endpoint `AsyncAIHttpTTSService.run_tts` posts to, documents that a mid-stream quota exhaustion does not change the status: the 200 `application/octet-stream` body simply receives the literal bytes `--ERROR:QUOTA_EXCEEDED--`. `run_tts` checks only `response.status != 200` and then accumulates every chunk into one buffer that it yields as a `TTSAudioRawFrame`, so the sentinel is handed to the output transport as PCM and the turn looks successful. The websocket class is not affected (errors arrive as JSON frames there — the item above). Unprobed by design: provoking it means burning the account's quota. — *Needs a call: whether to scan streamed chunks for the sentinel, including the case where it straddles a chunk boundary, or to treat in-band errors as the caller's problem.*
- **`speed_control` and `stability` not exposed** (low, since 2026-08-31) — both appear on the streaming, non-streaming and with-timestamps request bodies, and `AsyncAITTSSettings` is still an empty subclass of `TTSSettings`, so the runtime surface is `model` / `voice` / `language` only and neither class reads `Settings.extra`. Async's model page continues to restrict both to `async_flash_v1.0`, so on the default they are accepted and ignored, and the websocket init message has no slot for them. — *Needs a call: a stance on exposing settings that the default model accepts but does not honor, and that the websocket class cannot send.*
- **Language map is wider than the default model** (low, since 2026-08-31) — `language_to_async_language` maps 16 `Language` values; the model page gives `async_flash_v1.5` six (en, es, fr, de, it, pt) and the other nine to `async_flash_v1.0` only, and `nl` appears in neither the model page nor the HTTP reference's 15-code list. — *Needs a call: whether to warn per model, document the split, or leave the map model-agnostic.*
- **Word timestamps unused** (low, since 2026-11-23) — `POST /text_to_speech/with_timestamps` returns `alignment` arrays (`words`, `word_start_times_milliseconds`, `word_end_times_milliseconds`) for all three model ids, and neither class calls it, so Pipecat has no word timing for this provider. The websocket protocol has no timestamp message, and the endpoint returns one JSON blob rather than a stream, so using it in `AsyncAIHttpTTSService` would cost the chunked response it reads today. — *Needs a call: whether word timestamps justify a non-streaming HTTP path when the websocket class cannot have them either.*

`async_flash_v1.5` remains Async's stated recommendation for voice agents and was again the fastest of the three through our class (TTFB 607 ms vs 648 ms for `async_flash_v1.0` and 1463 ms for `async_pro_v1.0`), so the default stands; `Settings.model` has no allowlist, so all three are already selectable, and all three synthesized. No service code has changed since 2026-10-15 (`1d1fe9b39`, the shared TTS keepalive), which predates the last report, and `pyproject.toml` still has `asyncai = []`, so there is no SDK to pin. No example or docstring pins a model string other than the default; the voice UUID the four examples hard-code (`e0f39dc4-…`) is unchanged and the previous run confirmed it still resolves. One doc detail worth not re-deriving: the streaming endpoint accepts `pcm_mulaw` as well as `pcm_s16le` / `pcm_f32le`, and `AsyncAIHttpTTSService`'s `encoding` constructor argument already passes it through, so telephony encoding is reachable today.

The harness note from the last run still applies: `probe.py run` does not fill `voice` for this unit (`build_kwargs` resolves environment variables for the registry entry's `include_params` only, not its `settings_params`), so every probe below passes `--setting voice=…` explicitly; and `AsyncAIHttpTTSService` cannot be probed at all, because its required `aiohttp_session` constructor argument has no `probe.py` equivalent.
