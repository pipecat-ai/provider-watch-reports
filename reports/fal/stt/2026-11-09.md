# Fal STT — 2026-11-09

Nothing moved on fal's side; two of last run's items closed in main, and language auto-detect is the only remaining gap that costs a user a transcript.

## What's new for Pipecat

### PRs
Nothing.

### To consider
- **Language auto-detect errors out** (high, since 2026-09-01) — Wizper documents `language: null` as auto-detect and the request does succeed, but `Language(self._settings.language)` in `run_stt` raises `None is not a valid Language`; the handler turns the whole utterance into an ErrorFrame, so the user gets no transcript. Re-probed today, unchanged. — *Needs a call: what `TranscriptionFrame.language` should carry when fal auto-detects — the response returns a `languages` list rather than a single code.*
- **`task` is construction-only** (low, since 2026-10-12) — switching between transcription and translation means rebuilding the service: `task` lives in `self._task` from the constructor, not in `FalSTTSettings`, so no `STTUpdateSettingsFrame` can reach it. — *Needs a call: whether `task` becomes a Settings field; it would have to win over the constructor argument, so it is not a pure pass-through.*
- **Language map never applied** (low, since 2026-09-14) — `run_stt` puts `self._settings.language` into the payload directly, bypassing `language_to_service_language`, so the 96-entry `LANGUAGE_MAP` and `resolve_language`'s base-code fallback are unreachable from the request path. Settings deltas are converted on the way in (`Settings(language=Language.ES)` stores `es`), so the common path is fine and this stays latent — but a raw string fal does not recognise reaches the API instead of degrading to its base code. — *Needs a call: whether to route the payload through `language_to_service_language`, which changes the wire value for regional codes fal currently tolerates.*
- **Wizper-only endpoint** (low, since 2026-09-01) — `https://fal.run/fal-ai/wizper` is hard-coded and `Settings(model=...)` is accepted but ignored. fal's STT catalogue grew to twelve endpoints this cycle, adding `kotoba-technologies/kotoba-stt/v1/speech-to-text` (2026-10-09) and `kotoba-technologies/kotoba-streaming-stt/v1/realtime` (2026-10-14), neither reachable from Pipecat — nor are Canary, Scribe v2 or Cohere Transcribe. — *Needs a call: keep Fal support Wizper-only, as the registry label `Fal (Wizper)` implies, or add model routing / a streaming class; the endpoints have different request schemas.*
- **`max_segment_len` / `merge_chunks` unexposed** (low, since 2026-09-01) — the only two Wizper request fields the service never sends; both only shape chunking of long audio (`max_segment_len` is bounded 10–29 s), while `SegmentedSTTService` posts one utterance at a time and reads only `text`. — *Needs a call: whether they earn Settings fields given segmented input.*

Closed since the last run: the settings example is fixed and merged (pipecat-ai/pipecat#6134, now `language=Language.ES` in `examples/update-settings/stt/stt-fal.py`), and the leaked aiohttp session is fixed in main — commit `0469fe593` added a `cleanup()` that closes the session when `_owns_session`, and today's probes printed no `Unclosed client session`.

Checked and clear: the live Wizper schema is byte-identical to the last three runs — `version` still `const "3"`, `chunk_level` still `const "segment"`, `task` still the two-value enum, `max_segment_len` still 10–29, `audio_url` still the only required field. Wizper reports `deprecated: false` in fal's model index with no successor, and every other STT entry is non-deprecated too. The `fal` extra pulls no SDK (`fal = []` in `pyproject.toml`), so there is no pin to compare.
