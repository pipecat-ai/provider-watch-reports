### To consider
- **Language auto-detect errors out** (high, since 2026-09-01) — fal's Wizper page states that passing `None` makes it detect the language, and its example body sends `"language": null`. Pipecat can't ask for that: `run_stt` only adds the key when the setting is non-None, so a `Settings(language=None)` request reaches Wizper with no `language` at all and gets its `en` default — and then `Language(self._settings.language)` raises `None is not a valid Language`, so the handler yields an ErrorFrame and the utterance is lost. The code path is byte-identical to the one probed on 2026-11-09, where it failed; today's account lockout prevented a fresh probe. — *Needs a call: what `TranscriptionFrame.language` should carry when fal auto-detects — the response returns a `languages` list rather than a single code.*
- **`task` is construction-only** (low, since 2026-10-12) — switching between transcription and translation means rebuilding the service: `task` lives in `self._task` from the constructor, not in `FalSTTSettings`, so no `STTUpdateSettingsFrame` can reach it. — *Needs a call: whether `task` becomes a Settings field; it would have to win over the constructor argument, so it is not a pure pass-through.*
- **Language map never applied** (low, since 2026-09-14) — `run_stt` puts `self._settings.language` into the payload directly, bypassing `language_to_service_language`, so the 96-entry `LANGUAGE_MAP` and `resolve_language`'s base-code fallback are unreachable from the request path. Settings deltas are converted on the way in (`Settings(language=Language.ES)` stores `es`), so the common path is fine and this stays latent — but a raw string fal does not recognise reaches the API instead of degrading to its base code. — *Needs a call: whether to route the payload through `language_to_service_language`, which changes the wire value for regional codes fal currently tolerates.*
- **Wizper-only endpoint** (low, since 2026-09-01) — `https://fal.run/fal-ai/wizper` is hard-coded and `Settings(model=...)` is accepted but ignored. The catalogue holds eleven STT endpoints, none of the other ten reachable from Pipecat: Canary and its turbo/stream variants, ElevenLabs Scribe v2, Cohere Transcribe, ElevenLabs forced alignment and the two Kotoba Japanese models. — *Needs a call: keep Fal support Wizper-only, as the registry label `Fal (Wizper)` implies, or add model routing / a streaming class; the endpoints have different request schemas.*
- **`max_segment_len` / `merge_chunks` unexposed** (low, since 2026-09-01) — the only two Wizper request fields the service never sends; both only shape chunking of long audio (`max_segment_len` is bounded 10–29 s), while `SegmentedSTTService` posts one utterance at a time and reads only `text`. — *Needs a call: whether they earn Settings fields given segmented input.*

Checked and clear: the live Wizper schema is unchanged from the last four runs — `version` still `const "3"`, `chunk_level` still `const "segment"`, `task` still the two-value enum, `max_segment_len` still 10–29, `audio_url` still the only required field, `language` still the 97-value enum plus `null`. Wizper reports `deprecated: false` with no successor; its page calls it "[Experimental]", as it has all along. The `fal` extra pulls no SDK (`fal = []` in `pyproject.toml`), so there is no pin to compare, and no commit has touched `src/pipecat/services/fal/` since `0469fe593` (reported 2026-11-09).

One catalogue change, affecting nothing we ship: `nvidia/nemotron-asr-multilingual/asr`, listed last run, is gone from fal's model index (no longer under `speech-to-text`, `audio-to-text` or an `asr` keyword search), so the STT catalogue is eleven entries rather than twelve. Pipecat never reached it.
