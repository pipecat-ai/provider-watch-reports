# Deepgram Flux STT — 2026-10-12

Flux's one STT change this cycle is that `numerals` became a Configure field; the branch applies it over the live connection instead of reconnecting. `flux-general-en` stays the default.

## What's new for Pipecat

### PRs

- https://github.com/pipecat-ai/pipecat/pull/6124 — Toggle Deepgram Flux numerals over the live connection
- https://github.com/pipecat-ai/pipecat/pull/5584 — Add manual turn finalization to Deepgram Flux STT (open since 2026-09-01; adds a `turn_detection` mode and a public `force_end_turn()`, which is what the `ForceEndTurn` gap asks for)

### To consider

- **SageMaker SDK pin is behind** (medium, since 2026-10-12) — `pyproject.toml` pins `aws_sdk_sagemaker_runtime_http2>=0.6.0,<0.10` while PyPI is at 0.12.0 (2026-10-08), so an application already on 0.10+ cannot resolve `pipecat-ai[deepgram,sagemaker]`. AWS ships no release notes for the package; separately, `pipecat.services.aws.sagemaker.bidi_client` imports the deprecated `SageMakerRuntimeHTTP2Client` alias, which the SDK says to replace with `AsyncSageMakerRuntimeHTTP2Client`. — *Needs a call: the pin covers every SageMaker service, and with no changelog for a 0.x preview, widening it means running the AWS BiDi services against 0.12.0 first.*
- **`flux_encoding` overstates Flux's constraint** (low, since 2026-09-01) — both constructors document the encoding as "Must be `linear16`", while the `/v2/listen` reference accepts linear16, linear32, mulaw, alaw, opus and ogg-opus. The default is still the only workable value in Pipecat, since transports deliver linear16 PCM. — *Needs a call: whether Flux should accept the other encodings at all; if not, the wording should attribute the constraint to Pipecat rather than to Flux.*

PR 5739 (the `url` docstring) merged on 2026-09-14, closing that gap. Every `/v2/listen` query parameter is still reachable from `Settings` or the constructor, and the Configure reference's full field set — `thresholds`, `keyterms`, `language_hints`, `numerals` — is covered once the branch lands. Flux's reference omits `profanity_filter` from Configure, but the live endpoint accepts it and reports it back in `ConfigureSuccess`, so the behavior Pipecat shipped in PR 5523 still holds. Deepgram's other September/October entries are Nova-3 languages and models, Nova-3 mid-stream keyterms on `/v1/listen`, a GA India endpoint, Voice Agent changes, and a self-hosted release — none of them touch this unit; the India and self-hosted endpoints need no code change, since `DeepgramFluxSTTService` already takes an arbitrary `url`. `DeepgramFluxSageMakerSTTService` was not probed: it needs a deployed SageMaker endpoint. No decisions file exists for this unit, and the digest comments name no Deepgram item.

## Verification

| model           | class                  | ok | latency      | note                                                       |
| --------------- | ---------------------- | -- | ------------ | ---------------------------------------------------------- |
| flux-general-en | DeepgramFluxSTTService | ✅ | TTFB 5570 ms | default, unmodified code; transcript correct                |
| flux-general-en | DeepgramFluxSTTService | ✅ | TTFB 5572 ms | branch code; same transcript, so the Configure change is inert for a stream that never updates settings |

TTFB is dominated by the fixture's leading silence — Flux reports a turn only at `EndOfTurn` — so it is a liveness signal, not a latency measurement.

An ad-hoc WebSocket check (`.pw-scratch/adhoc/flux_configure_numerals.py`, one connection) sent `{"type": "Configure", "numerals": true}` to `/v2/listen?model=flux-general-en`: Flux answered `ConfigureSuccess` with `numerals: True` in the active configuration, confirming the branch's premise. `probe.py` cannot drive a mid-stream settings update, hence the script.
