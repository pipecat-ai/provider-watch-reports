# Deepgram Flux STT — 2026-11-23

Both PRs from previous runs merged, and with them Pipecat now exposes every parameter and client message the Flux reference documents; nothing new this cycle needs code.

## What's new for Pipecat

### PRs

Nothing.

### To consider

- **SageMaker SDK pin is behind** (medium, since 2026-10-12) — `pyproject.toml` still pins `aws_sdk_sagemaker_runtime_http2>=0.6.0,<0.10` while PyPI moved from 0.12.0 to 0.13.1 (2026-11-18), so an application already on 0.10+ cannot resolve `pipecat-ai[deepgram,sagemaker]`. AWS ships no release notes for the package; separately, `pipecat.services.aws.sagemaker.bidi_client` imports the deprecated `SageMakerRuntimeHTTP2Client` alias. — *Needs a call: the pin covers every SageMaker service, and with no changelog for a 0.x preview, widening it means running the AWS BiDi services against 0.13.1 first.*
- **`flux_encoding` overstates Flux's constraint** (low, since 2026-09-01) — `DeepgramFluxSTTService.__init__` and `DeepgramFluxSTTBase.__init__` document the encoding as "Must be `linear16`", while the `/v2/listen` reference accepts linear16, linear32, mulaw, alaw, opus and ogg-opus. The default is still the only workable value in Pipecat, since transports deliver linear16 PCM, and the SageMaker constructor already words it as a default. — *Needs a call: whether Flux should accept the other encodings at all; if not, the wording should attribute the constraint to Pipecat rather than to Flux.*
- **US residency endpoint is undocumented** (low, since 2026-11-23) — `api.us.deepgram.com` went GA for Flux STT on 2026-11-23, and after the end of January `api.deepgram.com` becomes a globally routed endpoint that makes no residency promise. `DeepgramFluxSTTService(url=...)` already reaches it, but the docstring names only the global default. — *Needs a call: the same wording applies to every Deepgram service, so where it belongs is a repo-wide question rather than a Flux one.*

PR 5584 merged on 2026-11-16 as "Add Pipecat turn detection to Deepgram Flux STT", closing the `ForceEndTurn` gap open since 2026-09-01: `DeepgramFluxSTTBase.force_end_turn()` sends the control message and `vad_force_turn_endpoint=True` calls it on every `VADUserStoppedSpeakingFrame`. PR 6668 merged on 2026-11-09, closing the `redact_usage` gap. With those in, every `/v2/listen` query parameter has a `Settings` field or a constructor argument, and all four client messages (Media, CloseStream, ForceEndTurn, Configure) are implemented.

Deepgram shipped no new Flux STT model and deprecated neither of the two; `flux-general-multi` still lists exactly the ten languages `language_to_deepgram_flux_language` maps, so the Nova-3 language expansions of 2026-10-23 and 2026-11-16 do not touch this unit. The 2026-11-10 self-hosted release makes Flux reject unsupported `language_hint` values at connect and on Configure; Pipecat already drops unmapped codes in `_prepare_language_hints` and skips hints entirely on `flux-general-en`, so stricter validation is safe. The 2026-11-08 and 2026-11-20 entries are Flux TTS and AWS Marketplace, not Flux STT.

One doc discrepancy resolved rather than filed: Deepgram's Configure reference does not list `profanity_filter` among the settable fields, but `_CONFIGURE_FIELDS` includes it. A single ad-hoc connection confirmed Flux accepts it, so the code is right and the reference is incomplete. `DeepgramFluxSageMakerSTTService` was not probed: it needs a deployed SageMaker endpoint. No decisions file exists for this unit, and the digest comments name no Deepgram item.

## Verification

| model              | class                  | ok | latency      | note                                      |
| ------------------ | ---------------------- | -- | ------------ | ----------------------------------------- |
| flux-general-en    | DeepgramFluxSTTService | ✅ | TTFB 5575 ms | default; transcript correct               |
| flux-general-multi | DeepgramFluxSTTService | ✅ | TTFB 7297 ms | transcript correct, language auto-detected |

TTFB is dominated by the fixture's leading silence — Flux reports a turn only at `EndOfTurn` — so it is a liveness signal, not a latency measurement.

An ad-hoc WebSocket check (`.pw-scratch/adhoc/flux_configure_profanity_filter.py`, one connection) sent `{"type": "Configure", "profanity_filter": true}` to `/v2/listen?model=flux-general-en`: Flux answered `ConfigureSuccess` with `profanity_filter: true` in the active configuration. `probe.py` cannot drive a settings update mid-stream, hence the script.
