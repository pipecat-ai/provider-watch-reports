# Deepgram STT — 2026-11-23

`nova-3-general` is still Deepgram's highest-performing general-purpose model; the one new request parameter since the last run, `redact_usage`, is on a branch, and the `diarize` deprecation that blocks `diarize_model` is unchanged — though the segmented class has since shown how to resolve it.

## What's new for Pipecat

### PRs

- https://github.com/pipecat-ai/pipecat/pull/6963 — Add a redact_usage Settings field to the Deepgram STT services

### To consider

- **`diarize` is deprecated and blocks `diarize_model`** (high, since 2026-08-25) — both `/v1/listen` references still mark `diarize` "Deprecated. Use `diarize_model` instead.", and setting both parameters in one request is rejected. `DeepgramSTTService` hardcodes `diarize=False` into its default settings, so `diarize=false` goes out on every connection: a user who reaches for the replacement through `extra={"diarize_model": "latest"}` gets a 400 at the handshake, which `_connection_handler` treats as permanent and retires the service (re-probed today). What is new is that `DeepgramSegmentedSTTService` fixed exactly this on 2026-11-13 (3545e4aea): `diarize` remains the switch, a `diarize_model` field (default `"latest"`) picks the model, and Deepgram's `diarize` is never sent. Mirroring that in the streaming class is a settings-to-request mapping change, not a pass-through, and it moves current `diarize=True` users off Deepgram's oldest diarizer. — *Needs a call: adopt the segmented class's mapping in `DeepgramSTTService`, accepting that `diarize=True` starts resolving to the `latest` diarizer.*
- **An undeclared `extra`/`addons` key retires the service** (high, since 2026-08-25) — `_build_connect_kwargs` spreads `extra` and `addons` into `client.listen.v1.connect(**kwargs)`, whose signature is exactly the AsyncAPI query-param list; an undeclared key raises TypeError, is retried three times and then retires the service. Probed both ways today with `redact_usage`: TypeError on the installed 7.17.0, clean connection on 7.19.0. On 7.19.0 the signature finally covers every parameter the streaming reference documents, so the hole is now a lag — each parameter Deepgram ships is unreachable, and fatal to reach for, until the SDK regenerates and the user upgrades, which our `>=6.1.1,<8` pin does not force. The SDK spreads `request_options["additional_query_parameters"]` into the WebSocket URL, so undeclared keys could be routed there; the segmented and SageMaker classes build their own query strings and have no such limit. — *Needs a call: forward undeclared keys to Deepgram unvalidated, or reject them at construction rather than failing mid-run.*
- **Keyterm updates still reconnect** (medium, since 2026-10-12) — `send_configure` has been on the Listen v1 socket client since deepgram-sdk 7.13.0, with typed replies since 7.14.0, and Deepgram serves mid-stream keyterm updates from every region. `_update_settings` still reconnects on any non-local settings change, so a keyterm swap costs a full WebSocket round trip and the audio buffered across it; `features` would also toggle `numerals` in place. — *Needs a call: route keyterm and numerals through `Configure` and reconnect only for the rest, and decide what a `ConfigureFailure` should do.*
- **Deepgram's endpointing and Configure events are dropped** (medium, since 2026-09-01) — `_on_message` handles only `ListenV1Results`, while the SDK exports `ListenV1UtteranceEnd`, `ListenV1SpeechStarted`, `ListenV1Metadata`, `ListenV1Error` and the two Configure replies, and since 7.18.0 hands anything unrecognized over as a raw dict. `utterance_end_ms` is a documented Settings field, so a user can set it, see it in the request, and get nothing back. — *Needs a call: whether Deepgram's own endpointing signals should feed turn-taking, or whether the setting should be documented as inert.*
- **`vad_events` undeclared in Settings** (low, since 2026-08-25) — accepted by `connect()` and reachable through `extra`, so this is discoverability only, and the `SpeechStarted` messages it produces are the ones the item above says are dropped. — *Needs a call: whether `vad_events` is worth a field before its event is handled.*
- **New Nova-3 languages missing from the `Language` enum** (low, since 2026-11-23) — Nova-3 added 36 monolingual languages on 2026-11-16 for batch and streaming; 12 of their codes (`ab`, `ady`, `ak`, `dv`, `mhr`, `kbd`, `kln`, `rw`, `kmr`, `dav`, `tn`, `ve`) have no enum member. The setting is typed `Language | str` and a bare code works — `language="tn"` transcribed fine today — so nothing is blocked, but `Language` is shared by every service. — *Needs a call: whether provider-watch should extend the shared enum for one provider's new languages.*

Last run's `language_hint` gap is closed: #6665 merged on 2026-11-09.

The STT catalogue is unchanged since 2026-10-12. Deepgram's US endpoint `api.us.deepgram.com` went GA on 2026-11-23 — workloads with a US residency requirement should move by 2027-01-31, after which the global endpoint may route outside the US — and both the streaming and segmented classes already take it through `base_url`, so there is nothing to change. Self-hosted release 261110 makes an unsupported Nova-3 multilingual language hint an error, which is what the `language_hint` docstring already says Deepgram does. The Nov 17 German and Hindi Nova-3 improvements and the Nov 20 AWS Marketplace x402 listing need nothing from Pipecat; the rest of the changelog is Flux or Voice Agent work belonging to other units.

The branch's field is unset by default, so the parameter is only sent when asked for. `DeepgramSTTService` needs deepgram-sdk 7.19.0 for it — the first release declaring `redact_usage` in `connect()` — which the docstring states rather than raising the `>=6.1.1,<8` pin, the same way `language_hint` documents 7.15.0. The segmented and SageMaker classes build their own query strings and need no particular SDK.
