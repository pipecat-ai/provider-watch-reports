# Deepgram STT — 2026-08-25

`nova-3-general` is still Deepgram's current general model and needs no change; the finding worth a maintainer's time is that the `extra`/`addons` passthrough cannot pass anything the SDK doesn't already declare.

## What's new for Pipecat

### PRs

Nothing.

### To consider

- **`extra`/`addons` passthrough is broken for undeclared params** (high, since 2026-08-25) — `_build_connect_kwargs` spreads `extra` and `addons` into `client.listen.v1.connect(**kwargs)`, whose signature is exactly the AsyncAPI query-param list. `Settings(extra={"filler_words": "true"})` raises `AsyncV1Client.connect() got an unexpected keyword argument 'filler_words'`, gets retried three times and then permanently retires the service (probed below). Deepgram documents `filler_words` and `measurements` for streaming Nova, so both are unreachable from this class; the SageMaker class, which builds its own query string, accepts them. The SDK spreads `request_options["additional_query_parameters"]` into the WebSocket URL (`deepgram/listen/v1/client.py`), so undeclared keys could be routed there. — *Needs a call: forward undeclared keys to Deepgram unvalidated, or reject them at construction rather than failing mid-run.*
- **`diarize_model`, `vad_events`, `version` undeclared in Settings** (low, since 2026-08-25) — all three are accepted by `connect()` and reach Deepgram through `extra` today, so this is discoverability only; `version` pins a model version against Deepgram's silent model refreshes, `diarize_model` picks the streaming diarizer. — *Needs a call: whether Settings should mirror every SDK query param, and how `diarize_model` should combine with the existing `diarize` field (setting it enables diarization on its own).*

Deepgram's Flux models are served by `DeepgramFluxSTTService` (a separate unit) and are deliberately absent from this class's catalogue view. `DeepgramSageMakerSTTService` was not probed: it needs a deployed SageMaker endpoint.
