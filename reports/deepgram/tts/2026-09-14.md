# Deepgram TTS — 2026-09-14

Current: `aura-2-helena-en` is served and recommended, Deepgram shipped nothing for Aura in this window, and last run's `speed` PR merged — no branch this time.

## What's new for Pipecat

### PRs

Nothing.

https://github.com/pipecat-ai/pipecat/pull/5552 (the `speed` setting) merged on 2026-09-02, so that gap is closed; the field is on `DeepgramTTSSettings` in main and probed working below. docs.pipecat.ai already documents it for both Aura classes.

### To consider

- **`tag` is Flux-only** (medium, since 2026-09-01) — the REST `/v1/speak` reference documents `tag` for labelling requests in usage reporting, and `DeepgramFluxTTSService` plus both Flux STT services already take `tag: list[str]` and append one `tag=` per value. Users who split Deepgram spend by workload can do it for Flux and for STT but not for Aura. — *Needs a call: it means a new constructor argument, and the Aura WebSocket reference does not list `tag`, so WebSocket support has to be confirmed first.*
- **`extra` is dropped** (medium, since 2026-09-01) — `DeepgramTTSSettings` inherits `extra`, but `_connect_websocket` and the HTTP `run_tts` assemble their query from named fields only. `Settings(extra={"tag": "prod"})` is accepted, stored, and never sent, so there is no escape hatch for a parameter Pipecat has no field for. The STT service has the mirror-image problem: it forwards `extra` into an SDK call that raises on undeclared keys. — *Needs a call: forward undeclared keys to the query string unvalidated, or reject them at construction rather than dropping them silently.*
- **Settings `model` does nothing** (low, since 2026-09-01) — Deepgram's request parameter is `model` but these classes read it from `voice`; `_update_settings` syncs `model` from `voice` and not the reverse. A user who sets `model` gets a reconnect and the old voice, with no warning. — *Needs a call: alias `model` to `voice` the way `voice_id` already is, reject it, or document it as derived.*
- **SageMaker class is behind** (low, since 2026-09-01) — the cloud classes now carry `speed` and `DeepgramSageMakerTTSSettings` is still `pass`; its `_update_settings` warns rather than reconnecting, so any setting would be construction-time only, and Deepgram's self-hosted notes require an April 2026 or later Aura-2 voice pack for `speed` (older packs return 400). — *Needs a call: a deployed endpoint to verify against, and whether the class should reconnect on settings changes first.*

The catalogue is byte-for-byte what it was on 2026-09-01 — 102 TTS entries, 90 Aura-2 and 12 Aura-1 — and none of it is gated by our classes, which pass the voice string through. The three September changelog entries are Nova-3 languages, agent `defer_until_eot`, and a React SDK release; nothing touches `/v1/speak`. Aura-2 remains the current generation with no Aura-1 deprecation notice, `speed` is still 0.7–1.5 on both transports for English and Spanish, and pause controls are still "coming soon". Flux TTS gained an `expressivity` control and a wider 0.5–1.5 speed range this window, but that is `/v2/speak` and belongs to the Flux classes, not these.

Method, for the next researcher: `probe.py run --service DeepgramTTSService` never returns on a *successful* WebSocket synthesis — with no output transport there is no `BotStoppedSpeakingFrame`, so the service's `pause_frame_processing=True` latches and the `EndFrame` never drains. Run it under a shell `timeout` **with `--verbose`** and read TTFB/TTFA from the service's own log lines; without `--verbose` the probe prints nothing at all before it is killed, since its only output is the final summary. Do not clean up with `pkill -f "probe.py run"` — the pattern matches the invoking shell. `DeepgramHttpTTSService` takes a required `aiohttp_session`, which `probe.py` cannot supply, so it needs an ad-hoc `run_test` script.
