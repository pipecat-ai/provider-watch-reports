# Deepgram Flux TTS — 2026-09-01

Flux TTS is current in Pipecat: every `/v2/speak` query parameter is exposed, the sample-rate, speed and expressivity ranges match the spec, and synthesis works with the shipped default. Nothing warrants a branch this run.

## What's new for Pipecat

### PRs

Nothing.

### To consider

- **`Interrupt` carries no `playback_offset`** (medium, since 2026-09-01) — Deepgram's barge-in pattern is: stop playback locally, then send `{"type": "Interrupt", "playback_offset": {"type": "time_ms", "value": <session ms played>}}`, and Flux answers with `text_spoken` / `text_remaining` so the LLM context matches what the user actually heard. `on_audio_context_interrupted` sends a bare `Interrupt`, so the server omits both fields and `audio_played_ms` degrades to its own generated-audio total. The offset is cumulative from the start of the *session* and each one must advance past the previous, or Flux rejects it with `INVALID_INTERRUPT_OFFSET`. — *Needs a call: whether Pipecat can give the service a session-cumulative played-ms counter, and whether Flux's `text_spoken` should override the assistant aggregator's own account of what was spoken.*
- **Ignored-`Interrupt` warning is noisy** (low, since 2026-09-01) — the quiet path in `_handle_message` is keyed on `NO_ACTIVE_SPEECH`, described in the code as "no active turn to interrupt". Flux uses that code for a `Flush` with no active turn; an `Interrupt` with nothing to interrupt — a barge-in in the first moments of a turn — is `NO_AUDIO_GENERATED` and falls through to `logger.warning`. Both codes were reproduced on one live connection. — *Needs a call: whether an ignored `Interrupt` should be quiet at all, since `INTERRUPT_IN_PROGRESS` is also an ignored barge-in and there a warning is arguably the right level.*
- **No batch REST path** (low, since 2026-09-01) — the same Flux voices are served by `POST /v2/speak` with mp3/opus/flac/aac output, for pre-rendering fixed audio. `DeepgramHttpTTSService` speaks `/v1/speak` only, which rejects `flux-*` model strings. — *Needs a call: whether a batch Flux path is wanted at all, given the streaming class already covers the live-agent case.*

Checked and clean: all seven `/v2/speak` query parameters (`model`, `encoding`, `sample_rate`, `speed`, `expressivity`, `mip_opt_out`, `tag`) are reachable; `SUPPORTED_SAMPLE_RATES` matches the spec exactly; `speed` 0.85–1.15 in 0.05 steps and `expressivity` −2…2 match, as does `_CONFIGURE_FIELDS = {"speed"}` (expressivity is fixed for the connection). `flux-cole-en` in `examples/voice/voice-deepgram-flux.py` is a GA voice. The 60-second inactivity timeout is covered by the `websockets` default ping interval. `DeepgramFluxSageMakerTTSService` was not probed — it needs a deployed SageMaker endpoint — but it shares `_build_query_string` and all message handling with the WebSocket class.

`probe.py run` produces the audio and the metrics but then hangs in teardown for this class: `TTSService(pause_frame_processing=True)` holds frame processing until a `BotStoppedSpeakingFrame`, which only an output transport emits, so the harness's `EndFrame` is never processed and `--json` never prints.
