# Deepgram Flux TTS — 2026-09-14

Flux's `speed` range is 0.5–1.5, not the 0.85–1.15 our docstring claims — a live probe accepted 0.6 at connect and 1.4 over `Configure`; branch ready. Everything else is unchanged from the last run.

## What's new for Pipecat

### PRs

- https://github.com/pipecat-ai/pipecat/pull/5740 — Document the full Flux TTS speed range

### To consider

- **`Interrupt` carries no `playback_offset`** (medium, since 2026-09-01) — Deepgram's barge-in pattern is: stop playback locally, then send `{"type": "Interrupt", "playback_offset": {"type": "time_ms", "value": <session ms played>}}`, and Flux answers with `text_spoken` / `text_remaining` so the LLM context matches what the user actually heard. `on_audio_context_interrupted` sends a bare `Interrupt`, so the server omits both fields and `audio_played_ms` degrades to its own generated-audio total. The offset is cumulative from the start of the *session* and each one must advance past the previous, or Flux rejects it with `INVALID_INTERRUPT_OFFSET`. — *Needs a call: whether Pipecat can give the service a session-cumulative played-ms counter, and whether Flux's `text_spoken` should override the assistant aggregator's own account of what was spoken.*
- **Ignored-`Interrupt` warning is noisy** (low, since 2026-09-01) — the quiet path in `_handle_message` is keyed on `NO_ACTIVE_SPEECH` alone; an `Interrupt` with nothing to interrupt — a barge-in in the first moments of a turn — is `NO_AUDIO_GENERATED` and reaches `logger.warning`. The spec's warning list has since grown `NO_SYNTHESIZABLE_TEXT`, `SYNTHESIS_RETRYING` and `INPUT_MARKUP_STRIPPED`, which take the same path, so a decision here should cover the code-by-code levels rather than one code. — *Needs a call: whether an ignored `Interrupt` should be quiet at all, since `INTERRUPT_IN_PROGRESS` is also an ignored barge-in and there a warning is arguably the right level.*
- **No batch REST path** (low, since 2026-09-01) — the same Flux voices are served by `POST /v2/speak` with mp3/opus/flac/aac output, for pre-rendering fixed audio. `DeepgramHttpTTSService` speaks `/v1/speak` only, which rejects `flux-*` model strings. — *Needs a call: whether a batch Flux path is wanted at all, given the streaming class already covers the live-agent case.*

Checked and clean: the `/v2/speak` query-parameter set is unchanged (`model`, `encoding`, `sample_rate`, `speed`, `expressivity`, `mip_opt_out`, `tag`), all seven reachable; `SUPPORTED_SAMPLE_RATES` still matches the `linear16` list; `expressivity` is still −2…2, still beta, and still fixed for the connection, matching `_CONFIGURE_FIELDS = {"speed"}`; the voice catalogue is the same 36 `flux-*-en` voices with no new languages; inline pause and pronunciation controls are still "coming soon" and still stripped before synthesis. No Flux TTS entry in Deepgram's September changelog. Neither TTS source file has changed since the previous report. `DeepgramFluxSageMakerTTSService` was not probed — it needs a deployed SageMaker endpoint — but it shares `_build_query_string` and all message handling with the WebSocket class, so the speed docstring fix covers it too.
