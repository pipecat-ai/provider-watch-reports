# Gladia STT — 2026-10-12

Current: Gladia's live API still accepts only `solaria-1`, our default, and shipped no live-API parameter changes since the last run. One branch fixes a translation-model docstring; the standing `language` and region/latency items are unchanged.

## What's new for Pipecat

### PRs
- https://github.com/pipecat-ai/pipecat/pull/6128 — Document Gladia's batch translation model

### To consider
- **`language` is silently dropped** (high, since 2026-09-01) — `_prepare_settings` builds the `/v2/live` body from `language_config` alone, so `GladiaSTTService.Settings(language=Language.FR)` has no effect; the base class converts it to `"fr"` and nothing reads it. Re-probed this run with `--setting language=fr` against the English clip: transcript unchanged. docs.pipecat.ai still lists `language` in the Settings table. — *Needs a call: whether `language` should populate `language_config.languages`, and what wins when both are set.*
- **Published TTFS assumes a nearby region** (medium, since 2026-09-14) — `region` is unset by default, so Gladia processes in eu-west. From the US runner the service's own TTFB metric (speech end → final transcript, i.e. TTFS) was 8653 ms against `GLADIA_TTFS_P99 = 1.49`; `region=us-west` gave 757 ms median of 3 (749–943 ms), matching last run's 820 ms. Turn stop strategies size their wait from that constant, so the far-region case cuts turns short, and nothing in the `region` or `ttfs_p99_latency` docstrings connects the two. — *Needs a call: whether to document the region/latency coupling (and the region the constant was measured in), or leave it to the stt-benchmark.*
- **`post_processing` not exposed** (low, since 2026-09-01) — `/v2/live` accepts `post_processing.summarization` with `summarization_config.type` (`general`, `bullet_points`, `concise`); a bare `summarization: true` init was accepted this run. `messages_config.receive_post_processing_events` is already a Settings field, but nothing can turn the processing on and `_receive_messages` drops those message types. — *Needs a call: whether end-of-session summaries belong in a real-time pipeline, and what frame would carry them.*
- **Oversized buffered resend** (low, since 2026-09-01) — after a reconnect `_send_buffered_audio` sends the entire buffer (20 MB by default) as one base64 `audio_chunk`; Gladia's websocket guidance is 20-50 ms chunks, and Gladia's own SDK 1.0.7 release notes say its reconnect now resends buffered audio in smaller chunks. — *Needs a call: confirm Gladia actually rejects or truncates such a frame before reworking the reconnect path.*
- **`words_accurate_timestamps` left Gladia's schema** (low, since 2026-10-12) — our `RealtimeProcessingConfig` exposes it, but it is absent from `api.gladia.io/openapi.json` and the live init reference. The endpoint still accepts it today (201), and `/v2/live` rejects unknown `realtime_processing` properties with a 400 at session init, so the day Gladia drops it a user who sets it cannot start a session. — *Needs a call: deprecate the field now, or wait until Gladia rejects it.*

Notes that are not gaps: `solaria-3` and `solaria-fusion` stay pre-recorded-only — `StreamingSupportedModels` is still `["solaria-1"]`, and the public `/v1/models` listing shows solaria-1 alone. Passing a plain dict to a pydantic-typed Settings field (e.g. `realtime_processing={...}`) raises `'dict' object has no attribute 'model_dump'` in `_prepare_settings`; the fields are typed as the config models, so this is caller error, not a provider gap. The `gladia` extra declares no SDK (`gladia = []`), so there is no pin to compare against Gladia's Python SDK 2.0.0.
