# Gladia STT — 2026-11-23

Nothing new from Gladia — solaria-1 is still the only live model and the changelog has not moved since 2026-09-14 — but the language map sends `mymr` for Burmese, which Gladia rejects; branch ready.

## What's new for Pipecat

### PRs

- https://github.com/pipecat-ai/pipecat/pull/6961 — Convert Burmese to Gladia's `my` language code

`language_to_gladia_language` mapped `Language.MY_MR` to `mymr`, a code Gladia's live API does not accept: an init POST with `language_config.languages: ["mymr"]` returns 400 while `["my"]` returns 201, and `my` is the code in both `TranscriptionLanguageCodeEnum` and the live init reference. Both `Language.MY` and `Language.MY_MR` now resolve to `my`. (`jv`, the other value in our map missing from the published enum, is accepted by the endpoint — 201 — so it is left alone.) Nothing reaches Gladia through this path today, because `Settings.language` is dropped (second item below); the fix matters for callers of `language_to_service_language` and for whatever resolves that gap.

### To consider
- **Regional language codes break session init** (high, since 2026-11-09) — `_prepare_settings` dumps `language_config` straight into the init body, so `LanguageConfig(languages=[Language.EN_US])` is sent as `en-US`. An ad-hoc init POST with `["en-US"]` came back 400 again this run, `["en"]` 201; `_setup_gladia` raises on a non-ok response, so the service never starts. `language_to_gladia_language` already maps `EN_US` → `en`, but nothing calls it for this path. Gladia publishes the accepted set as `TranscriptionLanguageCodeEnum` (99 codes), so either conversion or validation has a canonical list to work from. Our two examples pass `Language.EN`, whose value is already `en`, so they hide the trap. — *Needs a call: convert `language_config.languages` like other language inputs (and widen its type to accept `Language`), or validate and fail with a clear message.*
- **`language` is silently dropped** (medium, since 2026-09-01) — `GladiaSTTService.Settings(language=Language.FR)` has no effect: the base class converts it to `"fr"` and `_prepare_settings` never reads it, with no warning. Re-probed this run with `--setting language=fr` against the English clip: transcript unchanged. docs.pipecat.ai documents the field as having no effect, so only the code question is left. — *Needs a call: whether `language` should populate `language_config.languages`, and what wins when both are set.*
- **`post_processing` not exposed** (low, since 2026-09-01) — `/v2/live` accepts `post_processing.summarization` with `summarization_config.type` (`general`, `bullet_points`, `concise`), 201 again this run. `messages_config.receive_post_processing_events` is already a Settings field, but nothing can turn the processing on and `_receive_messages` drops those message types. — *Needs a call: whether end-of-session summaries belong in a real-time pipeline, and what frame would carry them.*
- **Oversized buffered resend** (low, since 2026-09-01) — after a reconnect `_send_buffered_audio` sends the entire buffer (20 MB by default) as one base64 `audio_chunk`; Gladia's websocket guidance is 20-50 ms chunks, and its own SDK 2.0.0 resends buffered audio in smaller chunks. — *Needs a call: confirm Gladia actually rejects or truncates such a frame before reworking the reconnect path.*
- **`words_accurate_timestamps` left Gladia's schema** (low, since 2026-10-12) — our `RealtimeProcessingConfig` exposes it, but it is absent from `api.gladia.io/openapi.json` and the live init reference. The endpoint still accepts it today (201), and `/v2/live` rejects unknown `realtime_processing` properties at session init, so the day Gladia drops it a user who sets it cannot start a session. — *Needs a call: deprecate the field now, or wait until Gladia rejects it.*
- **Published TTFS assumes a nearby region** (low, since 2026-09-14, was medium) — eu-west measured 1014 ms median of 3 from the US runner against 919 ms for `region=us-west`, both comfortably inside `GLADIA_TTFS_P99 = 1.49`. The far-region penalty has shrunk on each of the last three runs (8653 → 1255 → 1014 ms), so what remains is that neither the `region` nor the `ttfs_p99_latency` docstring mentions the other. — *Needs a call: whether to document the region/latency coupling (and the region the constant was measured in), or leave it to the stt-benchmark.*

Notes that are not gaps: Gladia's changelog is unchanged since GladiaFlow 1.1.0 (2026-09-14). `StreamingSupportedModels` is still `["solaria-1"]` and `StreamingSupportedRegions` still `us-west | eu-west`, matching our `Literal`; `solaria-3` and `solaria-fusion` remain pre-recorded-only. The live init schema is byte-for-byte the same shape as last run, with `callback` / `callback_config` still the only other unexposed fields — they have no place in a streaming pipeline. The `gladia` extra declares no SDK (`gladia = []`), so `sdk-versions` has no pin to compare.
