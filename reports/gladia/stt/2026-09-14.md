# Gladia STT — 2026-09-14

Current: Gladia shipped nothing new since the last run, and its live API still accepts only `solaria-1`, our default. Two things want a maintainer: `language` is still silently ignored, and the default region makes the final transcript arrive ~4 s after speech end from a US client.

## What's new for Pipecat

### PRs
Nothing.

### To consider
- **`language` is silently dropped** (high, since 2026-09-01) — `_prepare_settings` builds the `/v2/live` body from `language_config` alone, so `GladiaSTTService.Settings(language=Language.FR)` has no effect; the base class converts it to `"fr"` and nothing reads it. Re-probed this run with `--setting language=fr` against the English clip: transcript unchanged. docs.pipecat.ai lists `language` as a supported way to set the transcription language. — *Needs a call: whether `language` should populate `language_config.languages`, and what wins when both are set.*
- **Published TTFS assumes a nearby region** (medium, since 2026-09-14) — `region` is unset by default, so Gladia processes in eu-west. From the US runner the service's own TTFB metric (speech end → final transcript, i.e. TTFS) was 4871 ms median of 5 against `GLADIA_TTFS_P99 = 1.49`; pinning `region=us-west` brought it to 820 ms median of 5 with a tenth of the spread. Turn stop strategies size their wait from that constant, so the far-region case cuts turns short. Nothing in the `region` or `ttfs_p99_latency` docstrings connects the two. — *Needs a call: whether to document the region/latency coupling (and the region the constant was measured in), or leave it to the stt-benchmark.*
- **`post_processing` not exposed** (low, since 2026-09-01) — `/v2/live` accepts `post_processing.summarization` and `messages_config.receive_post_processing_events` is already a Settings field, but nothing can turn the processing on and `_receive_messages` drops those message types. Gladia now documents `chapterization` as ignored, so summarization is the whole of it. — *Needs a call: whether end-of-session summaries belong in a real-time pipeline, and what frame would carry them.*
- **Oversized buffered resend** (low, since 2026-09-01) — after a reconnect `_send_buffered_audio` sends the entire buffer (20 MB by default) as one base64 `audio_chunk`; Gladia's websocket guidance is 20-50 ms chunks. — *Needs a call: confirm Gladia actually rejects or truncates such a frame before reworking the reconnect path.*

Notes that are not gaps: `solaria-3` and `solaria-fusion` remain pre-recorded-only — the live enum still rejects them (probe below). The `gladia` extra declares no SDK (`gladia = []` in `pyproject.toml`), so there is no pin to compare against Gladia's Python SDK 1.0.3. The rest of `StreamingRequest` is covered by our config models; only `post_processing`, `callback` and `callback_config` are unexposed, and the callback pair is a batch-webhook feature with no place in a pipeline.
