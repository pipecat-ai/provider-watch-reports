# Gladia STT — 2026-11-09

Current on models — Gladia's live API still accepts only `solaria-1` — but `language_config.languages` is passed through unconverted, so a regional `Language` value makes the session fail to start.

## What's new for Pipecat

### PRs

Nothing.

### To consider
- **Regional language codes break session init** (high, since 2026-11-09) — `_prepare_settings` dumps `language_config` straight into the init body, so `LanguageConfig(languages=[Language.EN_US])` is sent as `en-US`. An ad-hoc init POST with `["en-US"]` came back 400 ("language_config.languages must only contain the following values: af, am, ar, …"), while `["en"]` was 201; `_setup_gladia` raises on a non-ok response, so the service never starts. `language_to_gladia_language` already maps `EN_US` → `en`, but nothing calls it for this path — only for the `language` field, which is itself dropped (next item). Our two examples pass `Language.EN`, whose value is already `en`, so they hide the trap. — *Needs a call: convert `language_config.languages` like other language inputs (and widen its type to accept `Language`), or validate and fail with a clear message.*
- **`language` is silently dropped** (medium, since 2026-09-01) — `GladiaSTTService.Settings(language=Language.FR)` has no effect: the base class converts it to `"fr"` and `_prepare_settings` never reads it, with no warning. Re-probed this run with `--setting language=fr` against the English clip: transcript unchanged. docs.pipecat.ai has since been corrected to say the field is not sent, which takes the documentation half of this off the table. — *Needs a call: whether `language` should populate `language_config.languages`, and what wins when both are set.*
- **Published TTFS assumes a nearby region** (medium, since 2026-09-14) — with `region` unset Gladia processes in eu-west; from the US runner that measured 1255 ms median of 3 against 782 ms median of 3 for `region=us-west`, both well short of the 8653 ms the last run saw, so the penalty varies by route. `GLADIA_TTFS_P99 = 1.49` has now been exceeded by the eu-west median in two of the last three runs, and nothing in the `region` or `ttfs_p99_latency` docstrings connects the two. — *Needs a call: whether to document the region/latency coupling (and the region the constant was measured in), or leave it to the stt-benchmark.*
- **`post_processing` not exposed** (low, since 2026-09-01) — `/v2/live` accepts `post_processing.summarization` with `summarization_config.type` (`general`, `bullet_points`, `concise`), 201 again this run. `messages_config.receive_post_processing_events` is already a Settings field, but nothing can turn the processing on and `_receive_messages` drops those message types. — *Needs a call: whether end-of-session summaries belong in a real-time pipeline, and what frame would carry them.*
- **Oversized buffered resend** (low, since 2026-09-01) — after a reconnect `_send_buffered_audio` sends the entire buffer (20 MB by default) as one base64 `audio_chunk`; Gladia's websocket guidance is 20-50 ms chunks, and its own SDK 2.0.0 resends buffered audio in smaller chunks. — *Needs a call: confirm Gladia actually rejects or truncates such a frame before reworking the reconnect path.*
- **`words_accurate_timestamps` left Gladia's schema** (low, since 2026-10-12) — our `RealtimeProcessingConfig` exposes it, but it is absent from `api.gladia.io/openapi.json` and the live init reference. The endpoint still accepts it today (201), and `/v2/live` rejects unknown `realtime_processing` properties at session init, so the day Gladia drops it a user who sets it cannot start a session. — *Needs a call: deprecate the field now, or wait until Gladia rejects it.*

Closed since last run: pipecat-ai/pipecat#6128 (the `TranslationConfig.model` docstring) merged on 2026-10-12, so `base | batch | enhanced` is documented and that gap is gone.

Notes that are not gaps: Gladia shipped no changelog entry since 2026-09-14, and no live-API change since the SDK 2.0.0 release of 2026-09-09. `solaria-3` and `solaria-fusion` stay pre-recorded-only — `StreamingSupportedModels` is `["solaria-1"]` and the models doc says "Use Solaria-1 instead for live streaming". `StreamingSupportedRegions` is still `us-west | eu-west`, matching our `Literal`. `callback` / `callback_config` remain the only other live-init fields we don't expose; they have no place in a streaming pipeline. The `gladia` extra declares no SDK (`gladia = []`), so there is no pin to compare against Gladia's Python SDK.
