# Ollama LLM — 2026-09-14

No change since the last run: the `/v1` base URL and OpenAI-compat surface are still correct, and the same two items need a maintainer's call.

## What's new for Pipecat

### PRs
Nothing.

### To consider
- **`llama2` default** (medium, since 2026-09-01) — `OLLamaLLMService()` with no settings asks for a July-2023 model whose library page carries no `tools` tag, so function calling silently cannot work; Ollama's quickstart is `ollama run gemma4` and Pipecat's own eval judge defaults to `gemma4:12b`. No in-tree caller relies on the default, and aiewf-eval has no Ollama-served row to rank a candidate with. — *Needs a call: Ollama designates no successor and a local runtime only serves models the user pulled, so the choice is between an opinionated modern default and making `model` required.*
- **Ollama Cloud unreachable** (medium, since 2026-09-01) — `api_key` is hardcoded to `"ollama"`, so passing a real key raises `TypeError: got multiple values for keyword argument 'api_key'`; Ollama Cloud serves glm-5.3, kimi-k3, qwen3.5 and gpt-oss over the same `/v1` surface with `OLLAMA_API_KEY`. — *Needs a call: the fix adds a constructor parameter, which the automatic-PR rules exclude, so someone has to decide whether cloud is in scope for this class.*

Not gaps: v0.34.0's "OpenAI-compatible client tool search and response compaction" is server-side support for agent clients (ChatGPT Desktop), not a request parameter our chat-completions path sends. `reasoning_effort` and `reasoning` stay reachable through `Settings.extra`; `tool_choice`, `n`, `logprobs`, `logit_bias` and `user` remain unsupported by Ollama but Pipecat never sends them. The cloud retirement list (minimax-m2.5, kimi-k2.5) touches no string Pipecat hardcodes.
