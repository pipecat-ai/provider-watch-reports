# OpenAI Realtime — 2026-11-09

`gpt-realtime-2.1` stays the default — OpenAI has shipped no Realtime model or changelog entry since July. One real addition slipped in through the spec rather than the changelog: `audio.input.noise_reduction.strength`, which a branch now exposes. PR #5547 is still the other thing to action.

## What's new for Pipecat

### PRs
- https://github.com/pipecat-ai/pipecat/pull/6659 — Add noise-reduction strength to OpenAI Realtime's audio input

  `strength` appeared in the GA spec between `openai` 3.40.0 and 3.46.0 and is documented in the `session.update` reference as a number from 0 to 1, default 1 when noise reduction is first enabled, with omission preserving the current value. `InputAudioNoiseReduction` had only `type`, and since pydantic drops unknown keys a user passing `strength=` today loses it silently — confirmed live: `main`'s model serialized `{"type": "far_field"}` and the server echoed `strength: 1.0`. From the branch the same code sends `{"type": "far_field", "strength": 0.25}` and the server echoes it back. `model_dump(exclude_none=True)` keeps the field out of the payload when unset, so an existing session is unchanged.

- https://github.com/pipecat-ai/pipecat/pull/5547 — Expose OpenAI Realtime conversation truncation and input-transcription settings (open since 2026-09-01, unchanged)

  Still the fix for the `gpt-live-transcribe` / `gpt-transcribe` hang: the hand-written `InputAudioTranscription.__init__` has no `languages`, those models' `session.updated` carries it, `parse_server_event` re-raises and the receive task exits with no `ErrorFrame`. PR #6329's tolerance does not help — `session.updated` is a modeled type, so validation still runs. These are the models OpenAI names as replacements for `whisper-1` and the `gpt-4o-*transcribe*` family (shutdown 2027-02-26), so migrating users land on this. The PR also retargets the `InputAudioTranscription.model` docstring, which on `main` still names both retiring models, so no separate branch is needed for it.

### To consider
- **MCP tools still hang the session** (high, since 2026-09-01) — unchanged since last run. PR #6329 fixed the event half; the item half stands: the server's `conversation.item.added` carries an `mcp_list_tools` item and `ConversationItem.type` is still a three-value `Literal`, so validation fails, the exception leaves `_receive_task_handler` (no try/except), and the bot goes silent. GA's item union has nine members, including `mcp_call` and `mcp_approval_request`. — *Needs a call: model the MCP item types (and surface approval requests), or make the receive loop log and skip anything that fails validation, not just unmodeled types.*
- **Lawful GA payloads our models reject** (medium, since 2026-10-28) — re-checked against `openai` 3.46.0 and identical to 3.40.0: `conversation.item.input_audio_transcription.delta` requires `content_index` and `delta` where GA has both optional; that event's `failed` sibling uses our `RealtimeError`, which requires `type` and `message` where GA's per-event Error has every field optional (so a partial failure report kills the session it reports on); `ItemContent.type` is required but `response.content_part.*` marks `part.type` optional; `RealtimeConversation` requires `id` and `object` where `conversation.created` marks both optional. These models are shared with client events and the `error` event, which is why #6329 left them. — *Needs a call: split the shared models so the server side can be permissive, or stop the receive loop raising on validation failure at all — the latter subsumes the MCP item-type gap too.*
- **GPT-Live 1 is GA but out of reach** (medium, since 2026-09-14) — probed again and still `invalid_model` through our class: `gpt-live-1` is a different API on `v1/live/sessions`. The divergence widened this cycle — outbound SIP calling opened to all organizations on 2026-11-02, on top of October's Decisions delegation and prompt-to-voice voices, while Realtime got nothing at all. Realtime is not deprecated and its guide still uses `gpt-realtime-2.1`, so this remains an addition, not a migration. — *Needs a call: whether GPT-Live gets its own Pipecat service — new unit, new protocol, a delegation model — or waits; either way far too large for a provider-watch PR.*
- **server_vad idle timeout and response controls** (medium, since 2026-09-01) — GA's `ServerVad` has `idle_timeout_ms`, `create_response` and `interrupt_response`; our `TurnDetection` has none of them, though `SemanticTurnDetection` already carries the last two. Since #6329, `input_audio_buffer.timeout_triggered` is skipped rather than fatal, so `idle_timeout_ms` would no longer kill the session it is meant to rescue. — *Needs a call: under server VAD the service never sends `response.create` itself, so `create_response=false` leaves the bot permanently silent — does the pass-through ship with that documented, or with handling?*
- **`parallel_tool_calls`** (medium, since 2026-09-01) — one of GA's 14 session fields with no home in `SessionProperties`; `gpt-realtime-2.1` accepts it, `gpt-realtime-1.5` fails the session with `invalid_value`, the same reasoning-model-only hazard `_strip_unsupported_reasoning` absorbs for `reasoning`. — *Needs a call: whether that stripping generalizes to a second capability-gated field.*
- **`tool_choice` cannot name a tool** (low, since 2026-09-01) — ours is `Literal["auto", "none", "required"]` on both session and response properties; GA also accepts an object forcing one function or MCP tool. — *Needs a call: whether forcing a tool is meaningful on a service that drives its own responses.*
- **Custom voices** (low, since 2026-09-01) — `AudioOutput.voice` is `str | None`, covering all built-in voices but not GA's `{"id": "voice_1234"}` object. October's prompt-to-voice release does not change the shape of this: text-prompt voices are Live-only, and Realtime custom voices must come from audio samples. — *Needs a call: whether Pipecat exposes OpenAI custom voices at all; no other OpenAI service here does.*
- **Safety identifier has no setting** (low, since 2026-10-12) — `_auth_headers()` lets a subclass add `OpenAI-Safety-Identifier` without reimplementing `_connect`, but the hook is private and undocumented, so there is still no configured path to the header OpenAI's own WebSocket examples always send. — *Needs a call: whether the hook is answer enough, or the identifier deserves a named setting — a constructor argument is outside the automatic-PR rules, and a Settings field would be the first that configures the connection rather than the session.*
- **Out-of-band responses** (low, since 2026-11-09) — `send_client_event` is public, so a `ResponseCreateEvent` can be sent, but `ResponseProperties` models seven fields and not GA's `conversation` (`"none"` for a response that adds nothing to the conversation) or `input` (a fresh item list for that response alone). `openai` 3.41.0 widened `input` to accept `{"type": "item_reference", "id": ...}`, so a side-channel response can cite items already in the session rather than repeat them. — *Needs a call: whether out-of-band responses are a pattern Pipecat wants on a service that drives its own responses, and if so whether they belong on `ResponseProperties` or on a dedicated API.*
