# OpenAI Realtime — 2026-09-14

`gpt-realtime-2.1` stays the default — OpenAI's Realtime guide still shows it and nothing deprecates it. The finding that needs action is that PR #5547, open since the last run, turns out to fix a silent hang and not just add settings: on `main`, pointing input transcription at `gpt-live-transcribe` or `gpt-transcribe` — the models OpenAI names as the replacements for the retiring `whisper-1`/`gpt-4o-transcribe` family — kills the session with no audio and no error.

## What's new for Pipecat

### PRs
- https://github.com/pipecat-ai/pipecat/pull/5547 — Expose OpenAI Realtime conversation truncation and input-transcription settings (open since last run; now also the fix for the hang below)

  Setting `InputAudioTranscription(model="gpt-live-transcribe")` makes the server echo the session back with `audio.input.transcription.languages` populated. `InputAudioTranscription` defines a hand-written `__init__(model, language, prompt)`, which is what pydantic validates against, so the extra key is a `TypeError`; `parse_server_event` re-raises it, `_receive_task_handler` exits, and the bot goes silent — no `ErrorFrame`. Probed live on `gpt-realtime-2.1`: no audio in 25 s on `main` for both `gpt-live-transcribe` and `gpt-transcribe`, and the traced failure is `session.updated` carrying `{'model': 'gpt-live-transcribe', 'language': None, 'languages': None, 'prompt': None}`. The default `gpt-realtime-whisper` is unaffected because the server does not echo `languages` for it. Checked out PR #5547 and re-probed: `gpt-live-transcribe` reaches audio at TTFB 499 ms, because the PR's new `languages` field absorbs the echo. The PR also replaces the `gpt-4o-transcribe`/`whisper-1` docstring examples (both shut down 2027-02-26) with `gpt-transcribe`/`gpt-live-transcribe`, so the retired-string item is covered too.

### To consider
- **MCP tools hang the session** (high, since 2026-09-01) — unchanged in code. `SessionProperties.tools` accepts provider-native dicts, so OpenAI's `{"type": "mcp", ...}` config reaches the server; the server answers with a `conversation.item.added` carrying an `mcp_list_tools` item, `ConversationItem.type` is `Literal["message", "function_call", "function_call_output"]`, validation fails, and the receive task exits silently. The general form is that Pipecat validates server payloads strictly and dies on anything new: 26 server event types in OpenAI's current schema are missing from `_server_event_types`, including `input_audio_buffer.timeout_triggered`, `input_audio_buffer.dtmf_event_received`, `conversation.item.input_audio_transcription.segment`, and the `mcp_*`/`response.mcp_call*` families. The transcription hang above is that same path reached without MCP, on a supported model, so this is a demonstrated hazard. — *Needs a call: support MCP tools end to end (item types plus the `mcp_*` events), or make the receive loop log and skip unknown events instead of raising.*
- **GPT-Live 1 is GA but out of reach** (medium, since 2026-09-14) — OpenAI shipped `gpt-live-1` on 2026-09-10 ($0.05/min, full-duplex, reasoning delegated to a backend Responses model or to the client). It is not a Realtime model: it has its own endpoint (`v1/live/sessions`) and its own event protocol (`openai.types.live` in the SDK — connect, fork, commentary, delegation events), and probing it through `OpenAIRealtimeLLMService` fails with `invalid_model`, "not supported in realtime mode". OpenAI claims a 30-point Full Duplex Bench gain over `gpt-realtime-2.1`. The Realtime API is not deprecated and its guide still shows `gpt-realtime-2.1`, so this is an addition rather than a migration. — *Needs a call: whether GPT-Live gets its own Pipecat service — a new unit with a new protocol and a delegation model — or waits; either way it is far too large for a provider-watch PR.*
- **server_vad idle timeout and response controls** (medium, since 2026-09-01) — `TurnDetection` exposes only `threshold`, `prefix_padding_ms` and `silence_duration_ms`; the API also takes `idle_timeout_ms`, `create_response` and `interrupt_response`, the last two of which `SemanticTurnDetection` already has. — *Needs a call: neither half is a clean pass-through — `idle_timeout_ms` makes the server emit the unmapped `input_audio_buffer.timeout_triggered` (so the unknown-event decision has to land first), and under server VAD the service never sends `response.create` itself, so `create_response=false` would leave the bot permanently silent.*
- **`parallel_tool_calls`** (medium, since 2026-09-01) — a documented session field with no home in `SessionProperties`; `gpt-realtime-2.1` accepts it while `gpt-realtime-1.5` rejects it with `invalid_value` and the session dies, the same reasoning-model-only hazard `_strip_unsupported_reasoning` absorbs for `reasoning`. — *Needs a call: whether that stripping generalizes to a second capability-gated field.*
- **`tool_choice` cannot name a tool** (low, since 2026-09-01) — ours is `Literal["auto", "none", "required"]`; the API also accepts an object forcing one function or MCP tool. — *Needs a call: whether forcing a tool is meaningful on a service that drives its own responses.*
- **Custom voices** (low, since 2026-09-01) — `AudioOutput.voice` is `str | None`, which covers all built-in voices but not the API's `{"id": "voice_1234"}` custom-voice object. — *Needs a call: whether Pipecat exposes OpenAI custom voices at all; no other OpenAI service here does.*

Realtime probes are connect-only through `probe.py`, and `--setting` validates keys against the `Settings` dataclass, so nested `SessionProperties` fields cannot be reached from the CLI (`--setting session_properties={...}` fails in the constructor). The rows that set session fields come from `.pw-scratch/rt_probe.py` and `rt_probe2.py`, which build the service directly and reuse `probe.py`'s `_run_pipeline`, sending an `LLMContextFrame` and waiting for `TTSAudioRawFrame`; `rt_probe2.py` wraps `parse_server_event` to record which event fails. TTFB varies session to session; the numbers show acceptance, not a ranking.
