# OpenAI Realtime — 2026-10-28

`gpt-realtime-2.1` stays the default: OpenAI's changelog has had no Realtime entry since July, and GA's session schema in `openai` 3.40.0 has the same 14 fields it had last run. PR #5547 is still the only thing to action, and a live probe confirms the hang it fixes. The news is on our side: a community PR merged on 2026-10-23 closed half the silent-hang class — unmodeled server event *types* are now skipped — and left a precise list of what it did not fix, which is this run's new gap.

## What's new for Pipecat

### PRs
- https://github.com/pipecat-ai/pipecat/pull/5547 — Expose OpenAI Realtime conversation truncation and input-transcription settings (open since 2026-09-01, unchanged)

  Confirmed live this run: a session that selects `gpt-live-transcribe` gets a `session.updated` whose transcription block is `['language', 'languages', 'model', 'prompt']`, the hand-written `InputAudioTranscription.__init__` rejects `languages`, `parse_server_event` re-raises, and the receive task exits with no `ErrorFrame`. The merged tolerance PR does not help here — `session.updated` is a modeled type, so validation still runs and still raises. `gpt-live-transcribe` and `gpt-transcribe` are the models OpenAI names as replacements for `whisper-1` and the `gpt-4o-*transcribe*` family (shutdown 2027-02-26), so migrating users land on this. The PR also already retargets the `InputAudioTranscription.model` docstring, which still names the two retiring models on `main`; no separate branch is needed for it.

No branch left this run: nothing else met the automatic-PR bar — there is no successor model to bump to, no retired string the open PR does not already cover, and every remaining item needs a design call rather than a value change.

### To consider
- **MCP tools still hang the session** (high, since 2026-09-01) — half fixed. PR #6329 made `parse_server_event` return `None` for an event type with no model, so the eight `mcp_list_tools.*` / `response.mcp_call*` events no longer stop the loop. The item half stands: the server's `conversation.item.added` carries an `mcp_list_tools` item and `ConversationItem.type` is still a three-value `Literal`, so validation fails, the exception leaves `_receive_task_handler` (no try/except), and the bot goes silent. GA's item union has nine members, including `mcp_call` and `mcp_approval_request`. — *Needs a call: model the MCP item types (and surface approval requests), or make the receive loop log and skip anything that fails validation, not just unmodeled types.*
- **Lawful GA payloads our models reject** (medium, since 2026-10-28) — the list #6329 deferred, checked against `openai` 3.40.0: `conversation.item.input_audio_transcription.delta` requires `content_index` and `delta` where GA has both optional; that event's `failed` sibling uses our `RealtimeError`, which requires `type` and `message` where GA's per-event Error has every field optional (so a partial failure report kills the session it reports on); `ItemContent.type` is required but `response.content_part.*` marks `part.type` optional; `RealtimeConversation` requires `id` and `object` where `conversation.created` marks both optional. These models are shared with client events and the `error` event, which is why the merged PR left them. — *Needs a call: split the shared models so the server side can be permissive, or stop the receive loop raising on validation failure at all — the latter subsumes the MCP item-type gap too.*
- **GPT-Live 1 is GA but out of reach** (medium, since 2026-09-14) — `gpt-live-1` is not a Realtime model: `v1/live/sessions`, its own protocol, `invalid_model` when probed through our class. It is where OpenAI's audio work is going — this cycle it got native Decisions delegation (2026-10-15) and prompt-to-voice custom voices plus nine new voices (2026-10-16), while Realtime got nothing. Realtime is not deprecated and its guide still uses `gpt-realtime-2.1`, so this remains an addition, not a migration. — *Needs a call: whether GPT-Live gets its own Pipecat service — new unit, new protocol, a delegation model — or waits; either way far too large for a provider-watch PR.*
- **server_vad idle timeout and response controls** (medium, since 2026-09-01) — GA's `ServerVad` has `idle_timeout_ms`, `create_response` and `interrupt_response`; our `TurnDetection` has none of them, though `SemanticTurnDetection` already carries the last two. The blocker named last run is half gone: `input_audio_buffer.timeout_triggered` is now skipped rather than fatal, so `idle_timeout_ms` would no longer kill the session it is meant to rescue (it would simply do nothing visible to the pipeline). — *Needs a call: under server VAD the service never sends `response.create` itself, so `create_response=false` leaves the bot permanently silent — does the pass-through ship with that documented, or with handling?*
- **`parallel_tool_calls`** (medium, since 2026-09-01) — one of GA's 14 session fields with no home in `SessionProperties`; `gpt-realtime-2.1` accepts it, `gpt-realtime-1.5` fails the session with `invalid_value`, the same reasoning-model-only hazard `_strip_unsupported_reasoning` absorbs for `reasoning`. — *Needs a call: whether that stripping generalizes to a second capability-gated field.*
- **`tool_choice` cannot name a tool** (low, since 2026-09-01) — ours is `Literal["auto", "none", "required"]`; GA also accepts an object forcing one function or MCP tool. — *Needs a call: whether forcing a tool is meaningful on a service that drives its own responses.*
- **Custom voices** (low, since 2026-09-01) — `AudioOutput.voice` is `str | None`, covering all ten built-in voices but not GA's `{"id": "voice_1234"}` object. October's prompt-to-voice release does not change the shape of this: the spec states voices created from text prompts are Live-only, and Realtime custom voices must come from audio samples. — *Needs a call: whether Pipecat exposes OpenAI custom voices at all; no other OpenAI service here does.*
- **Safety identifier has no setting** (low, since 2026-10-12, was medium) — downgraded: PR #6329 moved the connection headers into an overridable `_auth_headers()` hook, so a subclass can add `OpenAI-Safety-Identifier` without reimplementing `_connect`. The hook is private and undocumented, so there is still no configured path to the header OpenAI's own WebSocket examples always send. — *Needs a call: whether the hook is answer enough, or the identifier deserves a named setting — a constructor argument is outside the automatic-PR rules, and a Settings field would be the first that configures the connection rather than the session.*
