# OpenAI Realtime — 2026-10-12

A quiet month: OpenAI shipped no Realtime model, no session field and no deprecation since the last run, so `gpt-realtime-2.1` stays the default. PR #5547 is still open and still the only thing to action — it is the fix for the silent hang on OpenAI's replacement transcription models. One new gap: the `OpenAI-Safety-Identifier` header OpenAI's own WebSocket examples now send cannot be set through the service.

## What's new for Pipecat

### PRs
- https://github.com/pipecat-ai/pipecat/pull/5547 — Expose OpenAI Realtime conversation truncation and input-transcription settings (open since 2026-09-01, unchanged)

  Still the fix for the hang the last run documented: on `main`, `InputAudioTranscription(model="gpt-live-transcribe"|"gpt-transcribe")` makes the server echo the session back with `audio.input.transcription.languages` populated, the hand-written `InputAudioTranscription.__init__` rejects the extra key, `parse_server_event` re-raises, the receive task exits, and the bot goes silent with no `ErrorFrame`. Those are the two models OpenAI names as the replacements for `whisper-1` and the `gpt-4o-*transcribe*` family (shutdown 2027-02-26), so users will hit it on migration. Verified unchanged on `main` this run by reading the code — `InputAudioTranscription` still has no `languages` field and `SessionProperties` still has no `truncation`.

### To consider
- **MCP tools hang the session** (high, since 2026-09-01) — unchanged in code. `SessionProperties.tools` accepts provider-native dicts, so OpenAI's `{"type": "mcp", ...}` config reaches the server; the server answers with a `conversation.item.added` carrying an `mcp_list_tools` item, `ConversationItem.type` is `Literal["message", "function_call", "function_call_output"]`, validation fails, and the receive task exits silently. The general form is that Pipecat validates server payloads strictly and dies on anything new: 15 of the 46 event types in the openai SDK's `RealtimeServerEvent` union are missing from `_server_event_types` — `conversation.item.created`, `conversation.item.input_audio_transcription.segment`, `input_audio_buffer.timeout_triggered`, `input_audio_buffer.dtmf_event_received`, the three `output_audio_buffer.*`, and the eight `mcp_list_tools.*` / `response.mcp_call*`. The transcription hang above is that same path reached without MCP, on a supported model. — *Needs a call: support MCP tools end to end (item types plus the `mcp_*` events), or make the receive loop log and skip unknown events instead of raising.*
- **GPT-Live 1 is GA but out of reach** (medium, since 2026-09-14) — `gpt-live-1` (GA 2026-09-10, $0.05/min, full-duplex, reasoning delegated to a backend Responses model or to the client) is not a Realtime model: its endpoint is `v1/live/sessions` and its protocol is `openai.types.live`, and probing it through `OpenAIRealtimeLLMService` fails with `invalid_model`. Nothing changed this month except that the `gpt-live-1-*` preview slugs dropped out of the catalogue. The Realtime API is not deprecated and its guide still builds sessions with `gpt-realtime-2.1`, so this is an addition rather than a migration. — *Needs a call: whether GPT-Live gets its own Pipecat service — a new unit with a new protocol and a delegation model — or waits; either way it is far too large for a provider-watch PR.*
- **server_vad idle timeout and response controls** (medium, since 2026-09-01) — `TurnDetection` exposes only `threshold`, `prefix_padding_ms` and `silence_duration_ms`; the API's `ServerVad` also takes `idle_timeout_ms`, `create_response` and `interrupt_response`, the last two of which `SemanticTurnDetection` already has. — *Needs a call: neither half is a clean pass-through — `idle_timeout_ms` makes the server emit the unmapped `input_audio_buffer.timeout_triggered` (so the unknown-event decision has to land first), and under server VAD the service never sends `response.create` itself, so `create_response=false` would leave the bot permanently silent.*
- **`parallel_tool_calls`** (medium, since 2026-09-01) — a documented session field with no home in `SessionProperties`; `gpt-realtime-2.1` accepts it while `gpt-realtime-1.5` rejects it with `invalid_value` and the session dies, the same reasoning-model-only hazard `_strip_unsupported_reasoning` absorbs for `reasoning`. — *Needs a call: whether that stripping generalizes to a second capability-gated field.*
- **Safety identifier cannot be sent** (medium, since 2026-10-12) — `_connect` passes `additional_headers={"Authorization": ...}` and nothing else, so no connection header is reachable. OpenAI's Realtime WebSocket guide sends `OpenAI-Safety-Identifier: hashed-user-id` next to `Authorization` in all of its examples, and the safety guide describes it as how a Realtime session is attributed to an end user for abuse monitoring (identifiers do not carry between sessions). Probed by injecting the header into that dict: the session opens and completes a turn at TTFB 477 ms, so the API-side work is nil. — *Needs a call: where the value belongs. A `safety_identifier` constructor argument is the obvious shape but the automatic-PR rules exclude new constructor parameters; the alternative is a Settings field, which would be the first setting that configures the connection rather than the session.*
- **`tool_choice` cannot name a tool** (low, since 2026-09-01) — ours is `Literal["auto", "none", "required"]`; the API also accepts an object forcing one function or MCP tool. — *Needs a call: whether forcing a tool is meaningful on a service that drives its own responses.*
- **Custom voices** (low, since 2026-09-01) — `AudioOutput.voice` is `str | None`, which covers all built-in voices but not the API's `{"id": "voice_1234"}` custom-voice object. — *Needs a call: whether Pipecat exposes OpenAI custom voices at all; no other OpenAI service here does.*
