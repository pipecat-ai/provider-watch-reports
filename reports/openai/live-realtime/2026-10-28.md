# OpenAI Live (realtime) — 2026-10-28

`gpt-live-1` is still the only live model and carries no deprecation, so nothing is urgent; October's two Live additions — prompt-to-voice custom voices and the Decisions integration — both land outside what the service's types and event set can express, and no item is mechanical enough to branch this run.

## What's new for Pipecat

### PRs

Nothing. The previous run's branch is merged (https://github.com/pipecat-ai/pipecat/pull/6135, `store` Setting), so that gap is closed.

### To consider

- **Custom voices are unreachable** (medium, since 2026-10-28) — the 2026-10-16 release lets any customer create a voice from a text description and use it in a Live session by setting `audio.output.voice` to `{"id": "voice_123"}`; `OpenAILiveLLMSettings.voice` and `events.AudioOutputConfig.voice` are both `str | None`, so only the built-in names fit. The object form is validated server-side today (a bogus id fails with "No voice found with id", a non-string id with `invalid_type` on `...voice.id`). — *Needs a call: whether `voice` widens to a typed reference or a plain dict, and whether the docs' advice to repeat the voice description in `instructions` should be reflected.*
- **Decisions transcript triggers** (medium, since 2026-10-28) — the 2026-10-15 release added `session.triggers`, which answers a bounded-choice question on every input or output transcript delta and returns `decision.event`; it is what drives an avatar's expression or gesture mid-conversation. The field is absent from `SessionConfig` and `decision.event` from events.py. A session started with triggers is accepted (the server echoes `triggers` in the session resource), so only Pipecat's side is missing. — *Needs a call: where trigger answers surface — a frame, an event handler, or the thinking channel — since sending the config without routing the results achieves nothing.*
- **Delegated backends skip the reasoning defaults** (medium, since 2026-10-28) — `_responses_delegation_config` sends `reasoning` only when the caller set it, while `OpenAIResponsesLLMService` sends the model's `_THINKING_DEFAULTS` entry when it is unset. The same `OpenAIResponsesLLMSettings(model="gpt-6-sol")` therefore reasons at the server default under delegation and at `effort: none` through the Responses service — in a voice session, the one place the table exists for. The server accepts `reasoning` on the delegated path and leaves it out when unset. — *Needs a call: whether the delegated path should adopt the table, which changes latency and cost for bots that never set reasoning.*
- **Mid-session developer and system messages go nowhere** (medium, since 2026-09-14) — `_handle_context` forwards nothing from a context after the first, because user and assistant messages there cannot be distinguished from the service's own transcript recordings. Developer and system messages can only come from the app, and `instructions` stays appendable for the life of a session; `events.SessionInstructionsAppendEvent` exists and the service never sends it, so an app injecting context mid-call is silently ignored. — *Needs a call: whether to diff each incoming context for new developer/system messages, and whether they belong in instructions or in the thinking channel.*
- **No native Decisions delegation** (low, since 2026-10-28) — `delegation` accepts a third mode, `{"type": "decisions", "decisions": {"model": ..., "questions": [...]}}` (it starts on this account; omitting `decisions` or its `model` is rejected by name). The service's union and constructor know only client and Responses delegation, and `decision.event` has no model. — *Needs a call: whether a bounded-choice backend is a mode Pipecat wants, given it costs a third delegation class plus result routing.*
- **Client delegation cannot delay the acknowledgement** (low, since 2026-10-28) — `delegation.client.acknowledgement_delay_ms` holds the live model's automatic acknowledgement back so the app can slip in a silent update, which is the window a Pipecat client-delegation backend wants before the model fills the silence; `events.ClientDelegationConfig` sends only `type`. — *Needs a call: whether this belongs on the `ClientDelegation` dataclass or should follow from the backend's own timing.*
- **No server-side input mute** (low, since 2026-09-14) — `session.input_audio.mute` / `.unmute` and their acknowledgments are absent from events.py, so pausing input means the pipeline stopping audio, which leaves a gap in the session timeline rather than a mute the server confirms. — *Needs a call: whether withholding audio is good enough, and if not whether the surface is a service method or a frame.*
- **Sessions are always 24 kHz PCM16** (low, since 2026-09-14) — `events.AudioFormat` covers `audio/pcm`, `audio/pcmu` and `audio/pcma`, but `audio.format` is never sent; input is resampled to 24 kHz and output frames are hard-coded to it, so a telephony bot resamples G.711 in both directions. — *Needs a call: whether an 8 kHz G.711 session justifies threading the format through the input resampler and the output frame rate.*
- **No session forking** (low, since 2026-09-14) — a stored session is resumed by connecting to `.../v1/live/sessions/{id}/fork`. Correcting the previous report: the pieces are reachable already, since `on_session_started` hands the app the session resource with its `id` and `base_url` is a constructor argument, so the question is ergonomics, not identity. — *Needs a call: whether forking deserves a first-class surface or whether pointing `base_url` at the fork endpoint is the answer.*

New this run but **not** gaps: the voice catalogue grew to `marin` plus 21 named voices across six languages, and `voice` is `str | None` with no allowlist, so a new built-in name passes through (`quartz` starts a session). `gpt-5.6-terra`, pinned by the two delegation examples, is still served.
