# OpenAI Live (realtime) — 2026-11-09

`gpt-live-1` is still the only live model and carries no deprecation, so nothing is urgent; the one new provider feature since the last run is outbound SIP calling, GA to all organizations on 2026-11-02, which the service cannot reach because it always starts its own WebSocket session. No item is mechanical enough to branch.

## What's new for Pipecat

### PRs

Nothing.

### To consider

- **Outbound SIP calling is unreachable** (medium, since 2026-11-09) — GA on 2026-11-02. A call is placed with `POST /v1/live/sessions` carrying `transport.type: "sip"`, `transport.destination` (E.164) and a `transport.trunk` (TLS `sips:` provider URL, digest auth, caller number); the app then attaches to `wss://.../v1/live/sessions/{id}/attach` and must *not* send `session.start`. `OpenAILiveLLMService` only connects to `base_url` and sends `session.start` from its first context frame, and events.py has no `transport.ringing` / `transport.answered` / `transport.failed` models. The endpoint is live on this account — a private-IP trunk is refused by parameter name — so only Pipecat's side is missing. Note what the mode implies: SIP carries the audio, so the pipeline would hold no audio frames and Pipecat would be the control plane (client-delegation backend, tools, transcripts) for a call OpenAI owns. — *Needs a call: whether Pipecat wants a mode where OpenAI owns the call audio, given it costs session creation over REST, an attach-without-start path and transport events — and whether that same attach path is also the answer to forking.*
- **Custom voices are unreachable** (medium, since 2026-10-28) — a prompt-generated voice is used by setting `audio.output.voice` to `{"id": "voice_123"}`; `OpenAILiveLLMSettings.voice` and `events.AudioOutputConfig.voice` are both `str | None`. Re-checked this run: the object form is validated as a voice reference ("No voice found with id"), while the same id sent as a plain string is refused as an unknown built-in, so there is no string spelling that works. — *Needs a call: whether `voice` widens to a typed reference or a plain dict, and whether the docs' advice to repeat the voice description in `instructions` should be reflected.*
- **Decisions transcript triggers** (medium, since 2026-10-28) — `session.triggers` answers a bounded-choice question on every input or output transcript delta and returns `decision.event`; it is what drives an avatar's expression or gesture mid-conversation. The field is absent from `SessionConfig` and `decision.event` from events.py, while the server accepts a session started with triggers. — *Needs a call: where trigger answers surface — a frame, an event handler, or the thinking channel — since sending the config without routing the results achieves nothing.*
- **Delegated backends skip the reasoning defaults** (medium, since 2026-10-28) — `_responses_delegation_config` sends `reasoning` only when the caller set it, while `OpenAIResponsesLLMService` sends the model's `_THINKING_DEFAULTS` entry when it is unset. The same `OpenAIResponsesLLMSettings(model="gpt-6-sol")` therefore reasons at the server default under delegation and at `effort: none` through the Responses service — in a voice session, the one place the table exists for. — *Needs a call: whether the delegated path should adopt the table, which changes latency and cost for bots that never set reasoning.*
- **Mid-session developer and system messages go nowhere** (medium, since 2026-09-14) — `_handle_context` forwards nothing from a context after the first, because user and assistant messages there cannot be distinguished from the service's own transcript recordings. Developer and system messages can only come from the app, and `instructions` stays appendable for the life of a session; `events.SessionInstructionsAppendEvent` exists and the service never sends it. — *Needs a call: whether to diff each incoming context for new developer/system messages, and whether they belong in instructions or in the thinking channel.*
- **No native Decisions delegation** (low, since 2026-10-28) — `delegation` accepts a third mode, `{"type": "decisions", "decisions": {"model": ..., "questions": [...]}}`, and the Decisions API itself went GA on 2026-10-22. The service's union and constructor know only client and Responses delegation, and `decision.event` has no model. — *Needs a call: whether a bounded-choice backend is a mode Pipecat wants, given it costs a third delegation class plus result routing.*
- **Client delegation cannot delay the acknowledgement** (low, since 2026-10-28) — `delegation.client.acknowledgement_delay_ms` holds the live model's automatic acknowledgement back so the app can slip in a silent update, which is the window a Pipecat client-delegation backend wants before the model fills the silence; `events.ClientDelegationConfig` sends only `type`. — *Needs a call: whether this belongs on the `ClientDelegation` dataclass or should follow from the backend's own timing.*
- **No server-side input mute** (low, since 2026-09-14) — `session.input_audio.mute` / `.unmute` and their acknowledgments are absent from events.py, so pausing input means the pipeline stopping audio, which leaves a gap in the session timeline rather than a mute the server confirms. — *Needs a call: whether withholding audio is good enough, and if not whether the surface is a service method or a frame.*
- **Sessions are always 24 kHz PCM16** (low, since 2026-09-14) — `audio.format` is never sent, and every started session comes back with `{type: audio/pcm, rate: 24000}`; input is resampled to 24 kHz and output frames are hard-coded to it, so a telephony bot resamples G.711 in both directions. — *Needs a call: whether an 8 kHz G.711 session justifies threading the format through the input resampler and the output frame rate.*
- **No session forking** (low, since 2026-09-14) — a stored session is resumed over `.../v1/live/sessions/{id}/fork`, with `store`, Responses delegation settings and `audio.format` overridable. The pieces are reachable already (`on_session_started` hands the app the session resource and `base_url` is a constructor argument), so the question is ergonomics. — *Needs a call: whether forking deserves a first-class surface or whether pointing `base_url` at the fork endpoint is the answer.*

New this run but **not** gaps: the voice table dropped `cedar`, which the `Settings.voice` docstring and `tests/test_openai_live_service.py` use as their example — but the server still starts a session on it, so neither is a stale string; `voice` has no allowlist, so the documented names (`meridian` checked) pass through unchanged. `gpt-6.1-terra` shipped on 2026-10-26, and `gpt-5.6-terra`, pinned by the two delegation examples, is still served and undeprecated.
