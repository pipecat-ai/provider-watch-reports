# OpenAI Live (realtime) — 2026-11-23

`gpt-live-1.1` landed on 2026-11-19 and is already the only GPT-Live model in OpenAI's models index; it connects through `OpenAILiveLLMService` unchanged, but the default bump is a maintainer's call rather than a branch, because `gpt-live-1` carries no deprecation and a speech-to-speech model gives neither a latency nor an aiewf-eval comparison.

## What's new for Pipecat

### PRs

Nothing.

### To consider

- **gpt-live-1.1 is the model OpenAI now lists** (medium, since 2026-11-23) — shipped 2026-11-19: better pronunciation, accent consistency and multilingual transcription, same $0.05/min active price, drop-in on an existing session config. The models index's "Voice and speech" section now carries exactly one GPT-Live entry, `gpt-live-1.1`; `gpt-live-1` is gone from the index though its model page remains and the deprecations page names neither. Our class connects to both (`probe.py run`), and a raw `session.start` on 1.1 comes back with the same audio defaults. What is missing is comparative evidence: `probe.py` is connect-only for realtime units, so there is no TTFB/TTFAT to compare, and aiewf-eval's medium-context leaderboard is text-mode — it has no row for either live model, and the guide treats an absent candidate as a "consider". — *Needs a call: whether disappearing from the models index counts as OpenAI designating 1.1 the successor, given gpt-live-1 is undeprecated and the two models have separate concurrent-session limits, so the bump moves existing bots onto a different quota.*
- **Outbound SIP calling is unreachable** (medium, since 2026-11-09) — a call is placed with `POST /v1/live/sessions` carrying `transport.type: "sip"`, `transport.destination` and a `transport.trunk`, after which the app attaches to `.../sessions/{id}/attach` and must *not* send `session.start`; `OpenAILiveLLMService` only connects to `base_url` and always sends `session.start`, and events.py has no `transport.ringing` / `answered` / `failed`. The SDK's `session_accept_params`, `session_reject_params` and `session_refer_params` put inbound answer/reject and call transfer on the same surface. SIP carries the audio, so the pipeline would hold no audio frames and Pipecat would be the control plane for a call OpenAI owns. — *Needs a call: whether Pipecat wants that mode, given it costs session creation over REST, an attach-without-start path and transport events — and whether the same attach path is also the answer to forking.*
- **Custom voices are unreachable** (medium, since 2026-10-28) — the OpenAPI-generated SDK types the Live voice as `BuiltInVoice | CustomVoiceParam`, the latter `{"id": "voice_123"}`; `OpenAILiveLLMSettings.voice` and `events.AudioOutputConfig.voice` are `str | None`, and last run's probe showed no string spelling reaches a custom voice. — *Needs a call: whether `voice` widens to a typed reference or a plain dict, and whether the docs' advice to repeat the voice description in `instructions` should be reflected.*
- **Decisions transcript triggers** (medium, since 2026-10-28) — `triggers` is a top-level session field that answers a bounded-choice question on every transcript delta and returns `decision.event`; it is what drives an avatar's expression mid-conversation. Absent from `SessionConfig`, and `decision.event` absent from events.py, while the server accepts a session started with triggers. — *Needs a call: where trigger answers surface — a frame, an event handler, or the thinking channel — since sending the config without routing the results achieves nothing.*
- **Delegated backends skip the reasoning defaults** (medium, since 2026-10-28) — `_responses_delegation_config` sends `reasoning` only when the caller set it, while `OpenAIResponsesLLMService` sends the model's `_THINKING_DEFAULTS` entry when it is unset, so the same settings object reasons at the server default under delegation and at `effort: none` through the Responses service. — *Needs a call: whether the delegated path should adopt the table, which changes latency and cost for bots that never set reasoning.*
- **Mid-session developer and system messages go nowhere** (medium, since 2026-09-14) — `_handle_context` forwards nothing from a context after the first, because user and assistant messages there cannot be told apart from the service's own transcript recordings. Developer and system messages can only come from the app, `instructions` stays appendable for the session's life, and `events.SessionInstructionsAppendEvent` already exists unused. — *Needs a call: whether to diff each incoming context for new developer/system messages, and whether they belong in instructions or in the thinking channel.*
- **No native Decisions delegation** (low, since 2026-10-28) — `delegation` accepts a third mode, `{"type": "decisions", ...}`; the service's union and constructor know only client and Responses delegation, and `decision.event` has no model. — *Needs a call: whether a bounded-choice backend is a mode Pipecat wants, given it costs a third delegation class plus result routing.*
- **Client delegation cannot delay the acknowledgement** (low, since 2026-10-28) — `acknowledgement_delay_ms` holds the live model's automatic acknowledgement back so the app can slip in a silent update; `events.ClientDelegationConfig` sends only `type`. — *Needs a call: whether this belongs on the `ClientDelegation` dataclass or should follow from the backend's own timing.*
- **No server-side input mute** (low, since 2026-09-14) — `session.input_audio.mute` / `.unmute` and their acknowledgments are absent from events.py, so pausing input means the pipeline stopping audio, which leaves a gap in the session timeline rather than a mute the server confirms. — *Needs a call: whether withholding audio is good enough, and if not whether the surface is a service method or a frame.*
- **Sessions are always 24 kHz PCM16** (low, since 2026-09-14) — `audio.format` is never sent and every started session comes back `{type: audio/pcm, rate: 24000}`, so a telephony bot resamples G.711 both ways. — *Needs a call: whether an 8 kHz G.711 session justifies threading the format through the input resampler and the output frame rate.*
- **No session forking** (low, since 2026-09-14) — a stored session is resumed over `.../sessions/{id}/fork` with `store`, Responses delegation settings and `audio.format` overridable; the pieces are reachable already, so the question is ergonomics. — *Needs a call: whether forking deserves a first-class surface or whether pointing `base_url` at the fork endpoint is the answer.*
- **No server-side audio fixtures** (low, since 2026-11-23) — `session.output_audio.fixture.play` plays one validated clip (mono PCM16 24 kHz, ≤30 s) through the session, interrupting the model and dropping input for its duration, and acknowledges with `fixture.playing` / `fixture.played`. Probed this run over a plain WebSocket session: both acknowledgments came back, so the feature is reachable on the transport the service already uses; events.py models none of the three events. — *Needs a call: how a bot asks for a fixture (a service method, or a frame the service intercepts), and whether the interrupted speech and dropped input should surface as the usual interruption frames.*

New this run but **not** gaps: **standby mode**, announced alongside gpt-live-1.1, is WebRTC-only — the server rejects `idle_timeout_s` on a WebSocket session by name ("requires a standard WebRTC session with wake policy support") for both gpt-live-1 and gpt-live-1.1, so nothing in `SessionConfig` is missing for the transport this service uses. The SDK's `client.data_channel` session field is likewise "startup-only capabilities for an untrusted frontend attached to a unified WebRTC session". No live model string is hard-coded anywhere but `DEFAULT_MODEL` (examples name `gpt-live-1` only in docstring prose), and `gpt-5.6-terra`, pinned by the two delegation examples, is still served and undeprecated.
