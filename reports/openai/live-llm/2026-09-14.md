# OpenAI Live LLM — 2026-09-14

The Live API went GA on 2026-09-10 and the service already speaks the GA protocol; `gpt-live-1` is the only live model OpenAI publishes, so the default stands. Nothing urgent: the findings are five session affordances the service cannot express, and the one that was worth a branch — `store` — could not be probed on this account.

## What's new for Pipecat

### PRs

Nothing.

### To consider

- **`store` is not reachable from `Settings`** (medium, since 2026-09-14) — the one documented top-level session field `events.SessionConfig` lacks; it keeps a 30-day stereo recording (user left, model right) downloadable from `GET /v1/live/sessions/{id}/content`, and makes the session forkable. A branch adding `store: bool | None | NotGiven` to `Settings` and passing it into `SessionConfig` got as far as the server validating it by name — the startup error names `session.store` as the offending param — but the probe project forbids data persistence, so `store=true` fails startup with `session_storage_not_allowed` and the stored-session path is unverified. Branch dropped rather than proposed on a failed probe. — *Needs a call: a project that permits data persistence to verify it end to end, and whether `SESSION_CLOSE_TIMEOUT_SECS` (10 s) has to grow, since the docs warn a stored session takes longer to finalize.*
- **Mid-session developer and system messages go nowhere** (medium, since 2026-09-14) — `_handle_context` forwards nothing from a context after the first, because user and assistant messages there cannot be distinguished from the service's own transcript recordings. Developer and system messages can only come from the app, and the docs make `instructions` appendable for the life of a session; `events.SessionInstructionsAppendEvent` exists and the service never sends it, so an app injecting context mid-call is silently ignored. — *Needs a call: whether to diff each incoming context for new developer/system messages, and whether they belong in instructions or in the thinking channel.*
- **No server-side input mute** (low, since 2026-09-14) — `session.input_audio.mute` / `.unmute` and their acknowledgments are absent from events.py, so pausing input means the pipeline stopping audio, which leaves a gap in the session timeline rather than a mute the server confirms. — *Needs a call: whether withholding audio is good enough, and if not whether the surface is a service method or a frame.*
- **Sessions are always 24 kHz PCM16** (low, since 2026-09-14) — `events.AudioFormat` covers `audio/pcm`, `audio/pcmu` and `audio/pcma`, but `audio.format` is never sent; input is resampled to 24 kHz and output frames are hard-coded to it, so a telephony bot resamples G.711 in both directions. — *Needs a call: whether an 8 kHz G.711 session justifies threading the format through the input resampler and the output frame rate.*
- **No session forking** (low, since 2026-09-14) — a stored session is resumed by connecting to `.../v1/live/sessions/{id}/fork`, which restores saved state and can override `store`, the delegation settings and the audio format; `reset_conversation` opens a fresh session seeded from the context instead. — *Needs a call: `store` first, then where a fork's source session id comes from.*

`probe.py` classifies this unit as an `llm`, so it sends a text context and waits for `LLMTextFrame` — the rows that are real turns come from `.pw-scratch/live_probe.py`, which builds the service directly, reuses `probe.py`'s `_run_pipeline`, seeds the context with a trailing developer message (the service turns it into commentary, which is how the API asks the model to open) and streams 20 ms silence frames as a transport would, waiting for `SpeechOutputAudioRawFrame`. Without that silence stream the model never speaks and the session closes with `context_injection_incomplete`. The latency is wall clock from the context frame to the first audio, so it covers session start plus the commentary round trip; it shows acceptance, not a ranking.
