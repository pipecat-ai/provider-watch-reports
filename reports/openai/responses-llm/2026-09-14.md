# OpenAI Responses LLM — 2026-09-14

`gpt-6-astra` (GA 2026-09-03) cannot be used with this service at all: it rejects the `reasoning.effort="none"` the service sends by default for every reasoning-capable model. A branch fixes that and adds the `reasoning.mode` field the gpt-5.6 series introduced. Nothing the service hard-codes is retiring, and the default-model question is still blocked on latency alone.

## What's new for Pipecat

### PRs
- https://github.com/pipecat-ai/pipecat/pull/5749 — Support gpt-6-astra and expose the Responses reasoning mode

Two commits. The first adds `_rejects_effort_none`, so models that reason but refuse `effort="none"` are left at the provider's default — the treatment the o-series already had. `gpt-6-astra` goes from a hard 400 on every turn to a working turn at TTFAT 1463 ms; `gpt-5.6-sol`, `gpt-4.1` and `o3` are unchanged. The second adds `mode` to `OpenAIResponsesReasoningConfig`; today `ReasoningConfig(mode="pro")` is silently dropped by Pydantic, so the mode is unreachable except by overriding the whole `reasoning` dict through `extra`.

### To consider
- **Default model** (medium, since 2026-08-25) — the aiewf-eval rows are unchanged: gpt-5.6-sol at `effort="none"` (what our default path sends) scores 96.6% against gpt-4.1's 96.3%, so sol is still the one gpt-5.6 tier that is not a quality regression. Latency remains the blocker and re-measuring did not soften it: on `OpenAIResponsesLLMService` sol's median TTFAT is 646 ms against gpt-4.1's 389 ms on a trivial turn and 891 ms against 407 ms on a reasoning-triggering one. On the HTTP class the trivial-turn gap is only +9% (888 ms vs 815 ms), but the WebSocket class is the one the registry ships. gpt-6-astra is not a candidate — aiewf-eval has not benchmarked it, and it is positioned for "the hardest end-to-end work" rather than latency. — *Needs a call: whether that first-token cost is an acceptable price for a current-generation default, and that `openai/llm` shares the same gpt-4.1 default.*
- **Long-running-work controls** (medium, since 2026-09-14) — OpenAI shipped async tool calling and mid-turn steering on 2026-09-03. Async tools set `async: true` on the tool definition and let the model keep generating while a tool runs, with results returned as INTERRUPT, WHEN_IDLE or SILENT — directly useful for a voice bot that would otherwise go quiet during a slow lookup. Mid-turn steering is a WebSocket message that updates instructions inside a turn. Neither is a pass-through parameter; both need adapter and function-call-result work. — *Needs a call: whether either is worth designing for now, and which one voice users need first.*
- **Responses knobs only reachable via `extra`** (low, since 2026-08-25) — `text.verbosity`, `prompt_cache_key` / `prompt_cache_retention` / `prompt_cache_options`, `context_management`, `truncation`, `tool_choice`, `parallel_tool_calls`, `max_tool_calls`, `moderation` and `reasoning.context` are in the SDK's request schema with no named `Settings` field. `_build_response_params` ends with `params.update(self._settings.extra)`, so users are not blocked. `reasoning.context` is the one that is not a clean pass-through — it interacts with the encrypted-reasoning round-trip. — *Needs a call: named fields versus `extra` as the documented answer.*
- **`service_tier` is construction-time only** (low, since 2026-08-25) — Fast mode is GA and OpenAI pitches it at latency-sensitive workloads, but selecting a tier means rebuilding the service; every other request knob is runtime-updatable through `Settings`. — *Needs a call: whether `service_tier` should move into `Settings`, which would leave two ways to set it.*
- **gpt-6-astra rejects `temperature` / `top_p`** (low, since 2026-09-14) — setting either returns a 400. Both default to `NOT_GIVEN`, so only users who set them are affected, and the branch above does not change that. The service already warns in the analogous reasoning case via `_warn_if_reasoning_unsupported`. — *Needs a call: whether per-model parameter support is worth tracking in the service, or the provider's error message is good enough.*

Harness caveat, unchanged from last run: `probe.py run --model/--setting` never reach `OpenAIResponsesLLMService`. `build_kwargs` reads `inspect.signature(cls.__init__)`, and the WebSocket class's signature is `(*, ws_url=..., **kwargs)`, so neither `model` nor `settings` is in it and both overrides are silently dropped (the run then measures the default model). The WebSocket rows come from `.pw-scratch/ws_probe.py`, which patches `build_kwargs` and reuses `probe.py`'s interleaved repeat and median logic. A second trap for the next researcher: `probe.py` resolves the service class through `inventory`, which puts the main checkout's `src` ahead of `PYTHONPATH`, so probing a worktree's code means running *that worktree's* copy of `scripts/provider-watch/probe.py`.

`tests/test_openai_responses_http.py::TestHttpStreamErrorEvents::test_response_failed_reaches_pipeline_as_error_frame` fails with a `TimeoutError` on `main` as well as on the branch — pre-existing, unrelated to these changes.

Closed since last run: PR #5548 (`fast` service tier docstring) merged on 2026-09-02, and the SDK pin gap is gone — `pyproject.toml` now reads `openai>=1.74.0,<4` against a latest of 3.13.0.
