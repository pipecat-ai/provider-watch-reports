# OpenAI Responses LLM — 2026-10-12

OpenAI shipped `gpt-6-sol` and `gpt-6-luna` (2026-09-22) and `gpt-6.1-sol` (2026-09-29); all three run through this service unchanged, so nothing is broken. The one code change is a docstring: `service_tier="ultrafast"` is a new accepted value the argument's list does not mention.

## What's new for Pipecat

### PRs
- https://github.com/pipecat-ai/pipecat/pull/6136 — Document the "ultrafast" service tier in the OpenAI Responses service

Ultrafast Processing is OpenAI's lowest-latency tier, added for `gpt-6-astra` on 2026-09-29 and `gpt-6.1-sol` on 2026-10-08. `service_tier` already forwards any string to the request, so this is documentation only; a live turn with the tier set confirms it is accepted.

### To consider
- **Default model** (medium, since 2026-08-25) — the candidate set changed: OpenAI's 2026-10-07 changelog entry recommends the GPT-6 family for production API use, and `gpt-6-sol` / `gpt-6-luna` both work through the service as shipped (the reasoning classifier gives them `effort="none"`, which their model pages list as supported). The quality gate still cannot be met: aiewf-eval's medium-context leaderboard has no gpt-6 row at all. Latency does not argue for the move either — on `OpenAIResponsesLLMService`, median TTFAT is 363 ms for gpt-4.1, 542 ms for gpt-6-luna and 677 ms for gpt-6-sol. Among benchmarked models gpt-5.6-sol at `effort="none"` is still the only one at quality parity (96.6% vs gpt-4.1's 96.3%) and still the slowest of the candidates. — *Needs a call: whether to wait for aiewf-eval to benchmark gpt-6, whether any current-generation default is worth its first-token cost, and that `openai/llm` shares the same gpt-4.1 default.*
- **Mid-turn and long-running-work controls** (medium, since 2026-09-14) — unchanged from last run except that the reasoning guide now also documents `configuration_update`, an input item that changes `reasoning.effort` mid-conversation on the gpt-6 family in standard single-agent mode. With async tool calling (`async: true`, results tagged INTERRUPT / WHEN_IDLE / SILENT) and mid-turn steering, that is three provider-side mechanisms for acting inside a turn and none is a pass-through parameter. — *Needs a call: whether any of them is worth designing for now, and which one voice users need first.*
- **Responses knobs only reachable via `extra`** (low, since 2026-08-25) — the SDK's request schema is unchanged this run: `text.verbosity`, `prompt_cache_key` / `prompt_cache_retention` / `prompt_cache_options`, `context_management`, `truncation`, `tool_choice`, `parallel_tool_calls`, `max_tool_calls`, `moderation` and `reasoning.context` have no named `Settings` field. `_build_response_params` ends with `params.update(self._settings.extra)`, so users are not blocked. `reasoning.context` is now documented as `auto` / `current_turn` / `all_turns` with `all_turns` the default for gpt-5.6 — still the one that is not a clean pass-through, since it interacts with the encrypted-reasoning round-trip. — *Needs a call: named fields versus `extra` as the documented answer.*
- **`service_tier` is construction-time only** (low, since 2026-08-25) — Ultrafast makes this more visible: it is access-controlled and available on some models only, so a user who wants it for one model and the default tier for another has to rebuild the service. Every other request knob is runtime-updatable through `Settings`. — *Needs a call: whether `service_tier` should move into `Settings`, which would leave two ways to set it.*
- **gpt-6-astra rejects `temperature` / `top_p`** (low, since 2026-09-14) — unchanged; both default to `NOT_GIVEN`, so only users who set them are affected, and the service already warns in the analogous reasoning case via `_warn_if_reasoning_unsupported`. — *Needs a call: whether per-model parameter support is worth tracking in the service, or the provider's error message is good enough.*

Harness caveat, unchanged across runs: `probe.py run --model/--setting` never reach `OpenAIResponsesLLMService`, because `build_kwargs` reads `inspect.signature(cls.__init__)` and the WebSocket class's signature is `(*, ws_url=..., **kwargs)`, so both overrides are silently dropped and the run measures the default model. The WebSocket rows come from `.pw-scratch/ws_probe.py`, which re-applies `settings` after `build_kwargs` and delegates to `probe.py`'s own interleaved repeat and median logic.

Closed since last run: PR #5749 merged on 2026-09-14, so the two gaps it covered — gpt-6-astra rejecting `effort="none"` and the missing `reasoning.mode` field — are gone. `main` has since extended the same treatment to `gpt-6.1-sol`, which the reasoning guide says rejects both `none` and `minimal`. Nothing this unit hard-codes appears on the deprecations page; the 2026-10-23 `gpt-4.1-nano` retirement does not touch it (the default is `gpt-4.1`, which has no entry, and the examples pin no model).
