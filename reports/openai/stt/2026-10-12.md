# OpenAI STT — 2026-10-12

Nothing to review this run: OpenAI shipped no transcription model, schema or deprecation change since 2026-09-14, and `gpt-transcribe` remains both our default and OpenAI's file-transcription recommendation. The four open items are the same ones, with sharper evidence on two.

## What's new for Pipecat

### PRs
Nothing.

### To consider
- **Realtime default** (medium, since 2026-09-01) — the realtime transcription guide still recommends `gpt-live-transcribe` and never mentions `gpt-realtime-whisper`, which is also still absent from the deprecation table. The case has moved: OpenAI has cut the latency difference from ~900 ms to ~190 ms (TTFB 1210 ms vs 1399 ms, median of 3 isolated sessions each), and `gpt-live-transcribe` emitted 5 interim deltas per segment in every run where `gpt-realtime-whisper` varied between 1 and 5. 15% is still outside the 10% band a default bump needs, so this stays a judgement call. — *Needs a call: follow the docs onto `gpt-live-transcribe` for its steadier partials despite ~190 ms more TTFB, or hold until `gpt-realtime-whisper` is deprecated.*
- **`languages`, and realtime `keywords`** (medium, since 2026-09-01) — last run left open whether `languages` coexists with the singular `language`; it does not. A direct call with both returns `400 invalid_value`, `"The 'language' and 'languages' parameters cannot be used together."`, and the realtime guide says `gpt-live-transcribe` wants `languages` instead of `language`. Since both services always send `language`, a `languages` field cannot be a plain pass-through — it has to suppress `language`. Realtime `keywords` works on `gpt-transcribe` and `gpt-live-transcribe` but not on the default `gpt-realtime-whisper`, so it needs the per-model omission `_omit_unsupported_prompt` already performs for `prompt`. — *Needs a call: whether setting `languages` should silently drop `language`, and whether realtime `keywords` should be silently dropped for models that reject it.*
- **Empty-buffer commit on session start** (medium, since 2026-09-01) — same race, lower rate. Audio appended before our `session.update` takes effect is processed under the session's default turn detection, the server auto-commits, and our commit on `VADUserStoppedSpeakingFrame` hits an empty buffer, so `_handle_error` raises and the websocket reconnects mid-turn. Isolated sessions were clean 6/6; two interleaved `--repeat 3` batches each lost one session (once on `gpt-realtime-whisper`, once on `gpt-live-transcribe` — it is not model-specific), and the failing session returned the truncated `"Stage and easy to build."` — *Needs a call: whether `run_stt` should hold audio until `_session_ready`, and whether an empty-buffer commit deserves an error frame.*
- **Streaming file transcription** (low, since 2026-09-14) — `gpt-transcribe` supports `stream` on the Audio API, emitting `transcript.text.delta` while transcribing; `OpenAISTTService` awaits the whole response, so each segment's ~830 ms is dead time. The realtime class already serves users who want partials. — *Needs a call: whether `SegmentedSTTService` should push interim frames from a streamed response, which is more than a `Settings` field.*

Closed since last run: PR #5750 merged on 2026-09-14, so the `keywords` and realtime `delay` Settings gaps are gone — both fields ship.
