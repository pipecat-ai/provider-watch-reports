# OpenAI STT — 2026-10-28

Nothing new from OpenAI, but the known realtime start-of-session race has got much worse and should be looked at: it now truncates most transcripts instead of occasionally dropping a session.

## What's new for Pipecat

### PRs
Nothing.

### To consider
- **Empty-buffer commit on session start** (high, since 2026-09-01) — raised from medium. The mechanism is the one earlier runs described, but it is no longer rare and the usual symptom is silent data loss, not the error. An ad-hoc client pinned it down: appending audio from the moment the socket opens, before `session.updated` arrives, makes the server apply the session's *default* turn detection, emit `input_audio_buffer.speech_started` and auto-commit — the transcript comes back as `"It's easy to build."` for a clip that says `"The quick brown fox jumps over the lazy dog. Pipecat makes voice agents easy to build."`, and the service's own commit on `VADUserStoppedSpeakingFrame` then hits an empty buffer. Holding the same audio until `session.updated` returns the full transcript with no VAD events, 3/3 on both `gpt-realtime-whisper` and `gpt-live-transcribe`. Through the service, isolated `--repeat 5` probes were 4/5 with truncated text in the runs that survived, against 6/6 clean on 2026-10-12. `OpenAIRealtimeSTTService` connects in `setup()` and appends from the first `InputAudioRawFrame`, so a user who speaks in the first moments of a session loses the start of the utterance. — *Needs a call: whether `run_stt` should hold audio until `_session_ready`, and whether an empty-buffer commit deserves an error frame.*
- **Realtime default** (medium, since 2026-09-01) — the docs case is unchanged: `gpt-live-transcribe` is still "the recommended model", `gpt-realtime-whisper` is still absent from the guide and still absent from the deprecation table. The latency case moved the other way from what the last two runs suggested. Measured through the service, both models look close (TTFB 1230 ms vs 1357 ms, median of 5) — but those sessions are the truncated ones above, so they time a partial segment. Measured on clean sessions (audio held until `session.updated`, commit to final transcript, median of 3) it is 692 ms vs 1014 ms: `gpt-live-transcribe` is ~46% slower, not 15%. — *Needs a call: whether the docs' recommendation outweighs ~320 ms more latency to the final transcript, or the default holds until `gpt-realtime-whisper` is actually deprecated.*
- **`languages`, and realtime `keywords`** (medium, since 2026-09-01) — unchanged from last run and re-confirmed against the current docs and SDK schema. `languages` still cannot coexist with the singular `language` both services always send, so the field has to suppress `language` rather than pass through. Realtime `keywords` is still documented for `gpt-transcribe` and `gpt-live-transcribe` only, so it needs the per-model omission `_omit_unsupported_prompt` already performs for `prompt`. — *Needs a call: whether setting `languages` should silently drop `language`, and whether realtime `keywords` should be silently dropped for models that reject it.*
- **Streaming file transcription** (low, since 2026-09-14) — `gpt-transcribe` supports `stream` on the Audio API, emitting `transcript.text.delta` while transcribing; `OpenAISTTService` awaits the whole response, so each segment's ~1.2 s is dead time. The realtime class already serves users who want partials. — *Needs a call: whether `SegmentedSTTService` should push interim frames from a streamed response, which is more than a `Settings` field.*
