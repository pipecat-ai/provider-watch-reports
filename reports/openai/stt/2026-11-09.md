# OpenAI STT — 2026-11-09

Nothing new from OpenAI; the realtime class is the story — `input_audio_buffer_commit_empty` is fatal, and it is now reachable from an ordinary short speech segment, not just the start-of-session race.

## What's new for Pipecat

### PRs
Nothing.

### To consider
- **Empty-buffer commit is fatal** (high, since 2026-09-01) — re-scoped from "start-of-session race". The server rejects a commit carrying under 100 ms of audio; `_handle_error` re-raises, so the receive loop drops the socket and reconnects, losing whatever the session had in flight. An ad-hoc client reproduced it on a *fully configured* session — `session.updated` received, `turn_detection: null`, no VAD events — by appending 60 ms of speech and committing: `input_audio_buffer_commit_empty`. Since the service commits on every `VADUserStoppedSpeakingFrame` without tracking how much audio it appended, any short VAD segment does this. The start-of-session path is the same rejection reached a different way: audio appended before `session.updated` gets the session's default turn detection and a server auto-commit, so our commit then finds an empty buffer. That window is narrower than last run implied — `session.updated` arrives 75–94 ms after the socket opens (3 sessions) — but `probe.py` bursts the clip, lands inside it every time, and now returns **0/5 with no transcript on both realtime models**, against 4/5 with truncated text on 2026-10-28. An ad-hoc client appending from socket open at near-realtime pace got 4/4 full transcripts (2/4 with a stray `speech_started`), which places the data loss in the service's fatal handling rather than in the server. — *Needs a call: whether an empty-buffer commit should raise and reconnect at all rather than being a logged no-op, and whether `run_stt` should additionally hold audio until `_session_ready`.*
- **Realtime default** (medium, since 2026-09-01) — docs unchanged: `gpt-live-transcribe` is still the guide's recommended starting point, `gpt-realtime-whisper` is still undocumented and still not in the deprecation table. The latency case has flipped to parity: on clean sessions (audio held until `session.updated`, commit to final transcript, median of 3) it is 701 ms for `gpt-realtime-whisper` against 698 ms for `gpt-live-transcribe`, where last run measured 692 vs 1014 ms. Latency no longer argues against the bump, but it cannot be verified through the class while `probe.py run` fails 0/5 on both models, and the swap changes which `Settings` work: `delay` is `gpt-realtime-whisper` only, `keywords`/`languages` are not, and `gpt-live-transcribe` supports no server-side turn detection. — *Needs a call: whether to bump once the commit-empty teardown is fixed and the bump can be probed through the class, given it also swaps which `Settings` fields the default accepts.*
- **`languages`, and realtime `keywords`** (medium, since 2026-09-01) — unchanged, re-confirmed against the current guides and the 3.46.0 SDK schema. `languages` still cannot coexist with the singular `language` both services always send, so the field has to suppress `language`. Realtime `keywords` is still documented for `gpt-transcribe` and `gpt-live-transcribe` only, so it needs the per-model omission `_omit_unsupported_prompt` already performs for `prompt`. — *Needs a call: whether setting `languages` should silently drop `language`, and whether realtime `keywords` should be silently dropped for models that reject it.*
- **Streaming file transcription** (low, since 2026-09-14) — `gpt-transcribe` still supports `stream=true` on the Audio API; `OpenAISTTService` awaits the whole response, so each segment's ~810 ms is dead time. The realtime class already serves users who want partials. — *Needs a call: whether `SegmentedSTTService` should push interim frames from a streamed response, which is more than a `Settings` field.*
