# OpenAI STT — 2026-11-23

Nothing new from OpenAI for transcription; the realtime class's fatal `input_audio_buffer_commit_empty` is re-confirmed, and one new gap: OpenAI diarization ends 2027-02-26 with no successor.

## What's new for Pipecat

### PRs
Nothing.

### To consider
- **Empty-buffer commit is fatal** (high, since 2026-09-01) — re-confirmed, source unchanged since 2026-10-21. An ad-hoc client on a *fully configured* session (`session.updated` received, `turn_detection: null`, no VAD events) appended 60 ms of audio and committed; the server answered `input_audio_buffer_commit_empty` / `invalid_request_error`. `_handle_error` re-raises, so the receive loop drops the socket and reconnects, losing whatever was in flight. Since `_commit_audio_buffer` fires on every `VADUserStoppedSpeakingFrame` without tracking how much audio it appended, any short VAD segment reaches this. The start-of-session path is the same rejection reached a different way: `session.updated` lands 87 ms after `session.created` (1 session this run; 75–94 ms over 3 last run), `probe.py` bursts the clip into that window, the server auto-commits under the session's default turn detection, and our commit then finds an empty buffer. The symptom is flaky rather than absolute, and it swung back this run: `gpt-realtime-whisper` gave a full transcript on 1 of 4 probe runs, a truncated tail on 2, and no final transcript on 1 — against 0/5 with no transcript on 2026-11-09 and 4/5 truncated on 2026-10-28. — *Needs a call: whether an empty-buffer commit should raise and reconnect at all rather than being a logged no-op, and whether `run_stt` should additionally hold audio until `_session_ready`.*
- **Realtime default** (medium, since 2026-09-01) — docs unchanged: `gpt-live-transcribe` is still the guide's recommended starting point, `gpt-realtime-whisper` is still unmentioned there, still not in the deprecation table, and still a GA model in the 3.58.0 SDK (`delay` is documented as "only supported with `gpt-realtime-whisper` in GA Realtime sessions"). Latency moved back *against* the bump: interleaved `--repeat 3` through the class gives 1504 ms for `gpt-realtime-whisper` against 1936 ms for `gpt-live-transcribe` — 29% worse, outside the 10% bar — where last run's clean ad-hoc sessions measured parity (701 vs 698 ms). Both numbers carry the start-of-session loss above, so neither is a clean reading; `gpt-live-transcribe` was the more reliable of the two (3/3 against 2/3). The swap also changes which `Settings` work: `delay` is `gpt-realtime-whisper` only, `keywords`/`languages` are not, and `gpt-live-transcribe` supports no server-side turn detection. — *Needs a call: whether to bump once the commit-empty teardown is fixed and latency can be measured through the class without the start-of-session loss, given it also swaps which `Settings` fields the default accepts.*
- **`languages`, and realtime `keywords`** (medium, since 2026-09-01) — unchanged, re-confirmed against the current guides and the 3.58.0 SDK schema. `languages` still cannot coexist with the singular `language` both services always send, so the field has to suppress `language`. Realtime `keywords` is still documented for `gpt-transcribe` and `gpt-live-transcribe` only, so it needs the per-model omission `_omit_unsupported_prompt` already performs for `prompt`. — *Needs a call: whether setting `languages` should silently drop `language`, and whether realtime `keywords` should be silently dropped for models that reject it.*
- **Diarization retires 2027-02-26** (medium, new) — `_is_diarization_model` matches the substring `diarize`, and `gpt-4o-transcribe-diarize` is the only OpenAI model it reaches. The deprecation table shuts that model down on 2027-02-26, and its listed replacements (`gpt-live-transcribe`, `gpt-transcribe`) do not diarize — the speech-to-text guide itself says its speaker-label examples use deprecated models. So `speaker_format`, the `diarized_json` branch and the docstring's diarization example all stop working on that date. No example pins the string; only the service docstring and `tests/test_openai_stt.py` do, so there is nothing to change yet. — *Needs a call: whether to wait for OpenAI to name a diarizing successor or to document that OpenAI diarization ends 2027-02-26 and point users at another provider.*
- **Streaming file transcription** (low, since 2026-09-14) — `gpt-transcribe` still supports `stream=true` on the Audio API; `OpenAISTTService` awaits the whole response, so each segment's ~916 ms is dead time. The realtime class already serves users who want partials. — *Needs a call: whether `SegmentedSTTService` should push interim frames from a streamed response, which is more than a `Settings` field.*
