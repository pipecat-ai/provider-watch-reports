# Sarvam STT — 2026-11-23

Nothing to change in the service: `saaras:v4` is still Sarvam's default on all three endpoints and every documented connection parameter is reachable. The news is on the margins — realtime lost its beta label, and Sarvam now documents mid-call `keyterms`, which `SarvamRealtimeSTTService` refuses.

## What's new for Pipecat

### PRs
Nothing.

### To consider
- **Registry still scaffolds the legacy endpoint** (medium, since 2026-08-31) — the word "beta" is gone from Sarvam's realtime page, and the streaming page now opens "This page documents the legacy WebSocket (`/speech-to-text/ws`)" and points new integrations at realtime. No sunset date on the legacy endpoint. `sarvam_stt` in `cli/registry/service_metadata.py` still lists `class_name=["SarvamSTTService"]`, the class built on that legacy endpoint, while the unit carries three. — *Needs a call: whether SarvamRealtimeSTTService, or SarvamHttpSTTService, should join the registry's Sarvam STT entry now that Sarvam calls realtime neither beta nor legacy.*
- **Mid-call `keyterms` rejected** (medium, since 2026-11-23) — Sarvam's realtime page states "`keyterms` can also be updated mid-call (`saaras:v4` only)", and the live server confirms it: a `config.update` carrying `keyterms` returned `config.updated` with `applied:["keyterms=['Pipecat']"]`. `keyterms` is a constructor argument here and appears in neither `SarvamRealtimeSTTSettings` nor `_RUNTIME_CONFIG_FIELDS`, so `update_config(keyterms=...)` raises `ValueError`. The generated sarvamai 0.1.49 `RealtimeConfigUpdate` omits `keyterms` as well, so the SDK schema trails both the docs and the server. — *Needs a call: whether `keyterms` moves from a constructor argument to a Settings field, since a runtime value would otherwise contend with the connection-time one in `_query_params()`.*
- **sarvamai pin behind PyPI** (low, since 2026-08-31) — `pyproject.toml` pins `sarvamai==0.1.28`; 0.1.49 shipped today. Against the pinned wheel the STT-facing additions are unchanged from the 0.1.45 comparison: `keyterms`/`with_timestamps` on `transcribe()`, `keyterms` on the streaming `connect()`, and the realtime streaming module itself. Our classes reach `keyterms` by hand through `request_options`, so nothing is out of reach. — *Needs a call: whether the exact pin moves now that the parameters we hand-roll are first-class upstream.*
- **SDK ships a realtime client** (low, since 2026-09-14) — `sarvamai.speech_to_text_realtime_streaming` covers the endpoint `SarvamRealtimeSTTService` implements by hand, and its 0.1.49 connect signature still matches `_query_params()` field for field. — *Needs a call: whether the hand-rolled realtime websocket is worth replacing with the SDK client, which would also require moving the pin.*
- **REST `with_timestamps` unreachable** (low, since 2026-11-09) — Sarvam's REST reference documents `with_timestamps`, returning chunk-level (not word-level) offsets; `SarvamHttpSTTSettings` is empty and `_transcribe()` never sends it, where the realtime class does expose the equivalent `return_timestamps`. — *Needs a call: whether chunk offsets are meaningful when a segment over 30 seconds is split by `_split_wav()` into pieces whose offsets each restart at zero.*
- **Stale saaras:v3 references** (low, since 2026-11-23) — `examples/function-calling/function-calling-sarvam.py` and `examples/update-settings/llm/llm-sarvam.py` override the `saaras:v4` class default with `model="saaras:v3"`, and the comment above `_SUPPORTED_REALTIME_MODELS` still calls `saaras:v3-realtime` "beta-gated" where Sarvam now calls it legacy. Neither string is retired — `saaras:v3-realtime` transcribed fine this run — so this is presentation, not breakage. — *Needs a call: whether the update-settings example pins a non-default model deliberately, to show a setting taking effect, before the examples move to saaras:v4.*

No decisions file exists for this unit, and no digest comment names it.
