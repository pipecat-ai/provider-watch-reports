# Sarvam LLM — 2026-10-12

`deepseekv4-flash` — added to the allowlist by last run's PR — and `glm5.2` are both
retired: `/v2` answers each request with `404 … has been deprecated`. Sarvam's current
open-weight set is `deepseekv4.1-flash` and `glm5.3`, both of which answer through the
class once the allowlist names them; branch ready. Separately, the default `sarvam-105b`
now spends 3.2 s thinking before its first answer token, worse than either previous run.

## What's new for Pipecat

### PRs

- https://github.com/pipecat-ai/pipecat/pull/6138 — Track Sarvam's current open-weight LLM models

### To consider

- **Reasoning cannot be turned off through Settings** (high, since 2026-08-31) — the default `sarvam-105b` reasons on every turn and the cost has gone back up: median TTFAT 4053 ms with 3227 ms of thinking over 5 repeats, against 1921 ms on 2026-09-14 and 10219 ms on 2026-08-31. Four seconds to first token is a lot for a voice agent on a framework default. The off-switch still works — `extra_body.chat_template_kwargs.enable_thinking=false` gives TTFAT 885 ms, thinking 0 — and is reachable as `Settings(extra={"extra_body": {...}})`. Sarvam's own docs disagree on the default: the model page says `low`, the /v2 reference says `max`. — *Needs a call: whether to give `enable_thinking` a field of its own when it contradicts `reasoning_effort` and Sarvam documents it only for the open-weight models, or to leave users on the `extra` escape hatch.*
- **`reasoning_effort` allows the wrong values** (medium, since 2026-10-12) — `SarvamLLMSettings` types it `Literal["low", "medium", "high"]`. On glm5.3, `medium` returns `400 'reasoning_effort' must be one of low, high, max`, while `max` reaches the API fine but fails type checking. `sarvam-105b` still takes `medium`, so the allowed set varies by model, not by API version. — *Needs a call: widen the Literal to the union and validate per model, or split the values by model the way `_REASONING_MODELS` already splits support.*
- **`sarvam-105b-conversations` as the default** (medium, since 2026-08-31) — 775 ms median TTFAT against 4053 ms, GA, and the variant Sarvam describes for "real-time dialogue, voice agents, customer-facing chat". It trades 128K of context for 32K and lives on /v1. — *Needs a call: aiewf-eval's `aiwf_medium_context` leaderboard, re-read this run, still has no Sarvam rows, so the quality condition for a default bump cannot be checked.*
- **Capability tables drifted from the docs** (medium, since 2026-08-31) — the /v2 chat reference now says plainly that `reasoning_effort` applies to `glm5.3` and `deepseekv4.1-flash` and is ignored on `gemma4`, yet `gemma4` sits in `_REASONING_MODELS`. `wiki_grounding` has disappeared from the /v2 reference and from every current model page, yet `_WIKI_GROUNDING_MODELS` still holds `gemma4` and `sarvam-105b`. `sarvam-105b-conversations` is in neither set although /v1 accepts both parameters, so users on it get an error frame. — *Needs a call: HTTP 200 is not proof a parameter does anything, and tightening the sets converts silently-ignored parameters into error frames.*
- **`stream_options` never reaches the API** (medium, since 2026-10-12) — `build_chat_completion_params` pops it unconditionally, so the final usage chunk that `include_usage: true` produces never arrives and Sarvam turns report no token counts. The /v2 reference documents `stream_options` as supported alongside `stream: true`. — *Needs a call: whether /v1, which serves `sarvam-105b-conversations`, accepts it too; the pop is unconditional and lifting it changes requests on both versions.*
- **`x-session-affinity` has no first-class home** (low, since 2026-10-12) — new on 2026-10-10 for `gemma4` on `/v2`: one session ID repeated across a conversation's turns lets later turns reuse cached prompt context. `default_headers={"x-session-affinity": ...}` already reaches it, which suits Pipecat's one-service-per-session shape. — *Needs a call: whether `default_headers` is enough or the service should mint the ID itself.*
- **`sarvamai` pin behind PyPI** (low, since 2026-08-31) — `pyproject.toml` pins `sarvamai==0.1.28`, latest is 0.1.36 (2026-10-06). The LLM service reaches Sarvam through the `openai` SDK, so this only touches it via the shared extra. — *Needs a call: the bump belongs with the Sarvam STT/TTS services that import the SDK.*

`glm5.3-flash`, listed as a gap on 2026-09-14, is gone from `GET /v2/models` and from the
docs; it is dropped rather than carried forward.
