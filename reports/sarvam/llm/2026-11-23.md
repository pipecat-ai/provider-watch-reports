# Sarvam LLM — 2026-11-23

The account has credits again, so the models last run could only read about were
exercised: a branch admits the three Sarvam serves on a serverless key, and
`deepseekv4.1-flash` — last run's one `high` item, called dead on the strength of the
docs — still answers.

## What's new for Pipecat

### PRs

- https://github.com/pipecat-ai/pipecat/pull/6975 — Accept Sarvam's current chat completion models

### To consider

- **Reasoning runs at Sarvam's default on every model** (high, since 2026-08-31) — the service carries no reasoning-defaults table. On the default `sarvam-105b` that costs 1456 ms median TTFAT on a trivial prompt and 3196 ms on a reasoning prompt, against 681 ms and 687 ms for the conversations variant, which never reasons. The /v2 reference documents the lowest value for each model (`none` on the DeepSeek models and `qwen38-27b`, `low` elsewhere), which is what CONTRIBUTING asks an LLM service to send. For `sarvam-105b` both references give the off-switch as an explicit null `reasoning_effort`, and `None` means do-not-send in our code, so that null is unreachable. — *Needs a call: whether Sarvam gets a `_THINKING_DEFAULTS` table — the base `LLMService._apply_thinking_default` is already there — and how to express the explicit null.*
- **`reasoning_effort` allows the wrong values** (medium, since 2026-10-12) — `Literal["low", "medium", "high"]` against a union of `none`, `low`, `medium`, `high`, `max`: /v1 takes all five with a `medium` default, /v2 takes per-model subsets (`low`/`high`/`max` on `glm5.3`, `glm5.3-flash` and `gemma4`, all five on the DeepSeek models and `qwen38-27b`, and `low`/`medium`/`high`/`max` on `kimi-k3.1-pro` where `medium` runs as `high`). So `medium` is accepted by the Literal and rejected by half the catalogue, while `none` and `max` are the reverse. — *Needs a call: widen the Literal to the union and validate per model, or split the values by model the way `_REASONING_MODELS` already splits support.*
- **`sarvam-105b-conversations` as the default** (medium, since 2026-08-31) — half the TTFAT on a trivial prompt and a fifth of it on a reasoning prompt, GA, and the variant Sarvam describes for real-time dialogue and voice agents. It trades 128K of context for 32K, lives on /v1, never reasons, and the model page still calls `sarvam-105b` the flagship. — *Needs a call: aiewf-eval's `aiwf_medium_context` leaderboard, re-read this run, still has no Sarvam rows, so the quality condition for a default bump cannot be checked.*
- **`wiki_grounding` is undocumented but still sent** (medium, since 2026-08-31) — the parameter is in neither chat reference nor on any model page, yet `_WIKI_GROUNDING_MODELS` holds `gemma4` and `sarvam-105b` and the service merges it into `extra_body` for them. The sets are wrong in the other direction too: `sarvam-105b-conversations` is in neither, so Pipecat raises an error frame for `reasoning_effort` on a model /v1 documents as accepting and ignoring any value. — *Needs a call: HTTP 200 is not proof a parameter does anything, and tightening the sets converts silently-ignored parameters into error frames.*
- **`stream_options` never reaches the API** (medium, since 2026-10-12) — `build_chat_completion_params` pops it unconditionally, so the final usage chunk never arrives and Sarvam turns report no token counts. /v2 documents it as valid with `stream: true`, top-level, with `include_usage` also reporting `reasoning_tokens`; /v1, which serves `sarvam-105b-conversations`, documents no such field, so the pop can only be lifted for /v2. — *Needs a call: whether a per-version pop is acceptable given the base URL follows the model, or the field should be gated on something the user sets.*
- **Three Provisioned Throughput models still blocked** (low, since 2026-11-09) — `deepseekv4-pro`, `kimi-k3.1-pro` and `qwen38-27b` are in the /v2 chat enum, and all three answer 400 "not enabled for your organisation" on our key, so none could be probed. — *Needs a call: a Provisioned Throughput account, or a decision to admit models we cannot probe.*
- **`deepseekv4.1-flash` is undocumented but alive** (low, since 2026-11-09) — absent from `GET /v2/models` and from the /v2 chat enum since the 2026-10-30 rename, yet a completion with it returns 200 and echoes the short name back, where a made-up ID returns 404. The branch adds `deepseekv4.1-flash-1017` beside it rather than replacing it. — *Needs a call: whether to drop a working, undocumented name and break user code that passes it, or wait until Sarvam stops serving it.*
- **`x-session-affinity` has no first-class home** (low, since 2026-10-12) — one opaque ID per conversation enables routing and prompt-cache reuse on every /v2 chat model. `default_headers={"x-session-affinity": ...}` already reaches it, which suits Pipecat's one-service-per-session shape. — *Needs a call: whether `default_headers` is enough or the service should mint the ID itself.*
- **`sarvamai` pin behind PyPI** (low, since 2026-08-31) — `pyproject.toml` pins `sarvamai==0.1.28`, latest is 0.1.49 (2026-11-23); Sarvam's 2026-11-06 voice-cloning change names 0.1.45 as its floor. The LLM service reaches Sarvam through the `openai` SDK, so this only touches it via the shared extra. — *Needs a call: the bump belongs with the Sarvam STT/TTS services that import the SDK.*

Two things from last run resolve without code: the 402 that blocked every probe is gone, and
Sarvam's 2026-11-22 move of both 105B models to the Sarvam-105B-1711 weights keeps model IDs,
endpoints and request format unchanged. The catalogue is identical to last run's 16 entries.
