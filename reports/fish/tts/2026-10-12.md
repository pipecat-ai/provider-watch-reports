# Fish TTS — 2026-10-12

Nothing to review: `s2.1-pro` is still Fish's recommended production model, it probes healthy, and
the only retirement announced (`s1`, 2026-12-31) touches nothing Pipecat ships.

## What's new since the last run

- PR 5534 merged on 2026-09-28, so `chunk_length`, `min_chunk_length`,
  `condition_on_previous_chunks` and `prosody_normalize_loudness` now reach the request. The
  docs page has not caught up (listed below).
- Fish announced the `s1` retirement on 2026-10-08: deprecated now, retired 2026-12-31, after
  which `s1` requests are served and billed as `s2.1-pro`. Nothing in `src/pipecat/services/fish/`,
  its tests or `examples/voice/voice-fish.py` names `s1`, so there is nothing to migrate.
- `drama-3-preview` got its own changelog entry on 2026-09-23 — direction in plain prose rather
  than tags, gated behind a request flow, still absent from the plain `/v1/tts/live` model enum.
- `TTSRequest` grew `pronunciation_dictionary`, which is the one genuinely new affordance.

## What's new for Pipecat

### PRs
Nothing.

### To consider
- **Pronunciation dictionaries** (medium, since 2026-10-12) — `TTSRequest.pronunciation_dictionary`
  applies up to 3 dictionaries during synthesis, as either `{id, version}` references to
  platform-managed dictionaries or inline `{items: [{key, value, case_sensitive?}]}` literals (up
  to 5000 entries each); matching is leftmost-longest substring, case-insensitive by default. The
  ad-hoc probe below sent the inline form through the WebSocket start request and got audio back.
  — *Needs a call: the two forms are mutually exclusive in one request, and the reference form
  needs dictionary IDs from a platform API the public spec does not document, so Settings has to
  pick a form or model both.*
- **Word timestamps** (medium, since 2026-09-14) — `wss://api.fish.audio/v1/tts/live/with-timestamp`
  takes the same start request as the endpoint we use and adds `content`, `alignment`, `chunk_seq`
  and `chunk_audio_offset_sec` to each `audio` event; `alignment` is a cumulative snapshot per
  chunk, and absolute word time is `chunk_audio_offset_sec + segment.start`. It also has an
  `error` event the plain endpoint lacks. `TTSService.add_word_timestamps` is the hook on our side.
  — *Needs a call: whether word timestamps justify a second endpoint and the cumulative-alignment
  bookkeeping, or whether the service should just move to the timestamped endpoint.*
- **Multi-speaker and inline references** (medium, since 2026-09-01) — the start request takes
  `references` (inline zero-shot cloning) and an array of model IDs in `reference_id` for
  multi-speaker dialogue with `<|speaker:N|>` tags in the text. `Settings.voice` is a single string
  and nothing sends `references`. — *Needs a call: whether `voice` may hold a list, and where
  reference audio bytes belong in Settings.*
- **`drama-3-preview`** (low, since 2026-09-14) — in the model header enum for `POST /v1/tts`,
  `POST /v1/tts/stream/with-timestamp` and the timestamped WebSocket, but not for the plain
  `/v1/tts/live` the service connects to, where an unrecognized model silently falls back to
  `s2.1-pro`. — *Needs a call: whether to chase a gated preview model whose behavior and
  availability may change.*
- **`features` flags** (low, since 2026-09-14) — last run asked for a probe before adding a field.
  The probe does not settle it: the WebSocket accepted `["quality-guard"]`, an invented flag name
  and an invented top-level key alike, all returning normal audio, and synthesis is
  non-deterministic, so byte-level differences are noise. The schema half is settled —
  `TTSLiveStartEvent.request` is a `$ref` to the `TTSRequest` that carries `features`. — *Needs a
  call: whether to expose a backend-dependent flag list whose one documented value has no
  documented effect and whose typos fail silently.*
- **Generation knobs** (low, since 2026-09-01) — `max_new_tokens`, `repetition_penalty` and
  `early_stop_threshold` sit alongside the exposed `temperature` and `top_p`;
  `early_stop_threshold` is documented as a batch-processing control. — *Needs a call: whether
  they earn Settings surface area for a voice pipeline.*
- **`latency` values** (low, since 2026-09-01) — the API reference enumerates `low`, `normal`,
  `balanced`, while the `Settings` docstring names only the last two. The field is a plain `str`,
  so `low` already reaches the API. — *Needs a call: whether to recommend `low` when Fish's
  real-time streaming guide only documents normal and balanced.*
- **Output bitrates** (low, since 2026-09-01) — `mp3_bitrate` and `opus_bitrate` apply only to
  non-pcm output, and `output_format` is an init-only constructor argument. — *Needs a call:
  whether non-pcm output is a use case worth widening the audio-format arguments for.*
- **Docs page lags the code** (low, since 2026-10-12) — the Settings table on
  docs.pipecat.ai still stops at `prosody_volume`; the four fields PR 5534 added are missing. —
  *Needs a call: the page lives in the docs repo, so whether provider-watch files there or leaves
  it to the docs sync.*

## Verification

| model    | class               | ok | latency     | note                                              |
| -------- | ------------------- | -- | ----------- | ------------------------------------------------- |
| s2.1-pro | FishAudioTTSService | ✅ | TTFB 219 ms | single sample; TTFA 224 ms (5 ms leading silence) |

No default bump is on the table, so no repeat run was needed. As in previous runs, `probe.py run`
never prints its JSON for this service: Fish's WebSocket API has no per-utterance completion event
(`finish` is session-level), so the audio context stays open until the idle sweep, and with
`pause_frame_processing=True` and no output transport in the probe pipeline no
`BotStoppedSpeakingFrame` lifts the pause, leaving `EndFrame` queued until the probe is killed —
the outer shutdown guard added to `probe.py` does not fire either. The latency above is the
service's own TTFB metric from the verbose log.

Ad-hoc probe (`.pw-scratch/fish_ws_probe.py`, five short sessions against `/v1/tts/live` with
`s2.1-pro`), to answer last run's open question about `features`:

| start-request extra                        | result                      |
| ------------------------------------------ | --------------------------- |
| none (baseline)                             | audio, `finish: stop`       |
| `features: ["quality-guard"]`               | audio, `finish: stop`       |
| `features: ["pw-not-a-real-feature"]`       | audio, `finish: stop`       |
| an invented top-level key                   | audio, `finish: stop`       |
| `pronunciation_dictionary` (inline form)    | audio, `finish: stop`       |

The endpoint accepts unknown keys and unknown flag names without complaint, so acceptance alone is
no evidence that `features` is honored; re-running the baseline produced a different audio length,
so output size cannot be used as a differential signal either.
