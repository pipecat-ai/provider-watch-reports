# Speechify TTS — 2026-10-12

`simba-3.2` is still the recommended model and the right default; the quiet
period ended with two additions on 2026-10-05 and 2026-10-08, one of which is a
one-field pass-through on a branch and one of which needs a maintainer's call.

## What's new for Pipecat

### PRs
- https://github.com/pipecat-ai/pipecat/pull/6143 — Add a safety_identifier setting to SpeechifyHttpTTSService

Speechify's 2026-10-05 entry adds an optional `safety_identifier` body field to
`/v1/audio/speech`, `/v1/audio/stream` and `/v1/audio/stream/with-timestamps` —
the last being the endpoint this service calls. It attributes a request to one
end user so per-end-user rate limits and blocks apply to that user instead of
the whole workspace; limits only apply to requests that carry it. The branch
adds it to `SpeechifyTTSSettings`, unset by default, and copies it into the
payload when set. Verified live below: a valid value synthesizes normally, and
an invalid one is rejected by Speechify naming the field, which is what shows
the value reaches the request body rather than being dropped.

### To consider
- **WebSocket streaming text input** (medium, since 2026-10-12) — `GET /v1/audio/stream/ws`, added 2026-10-08, accepts text as it is produced (`input.text`, `input.flush`, `input.close`) and speaks each completed sentence, where the HTTP class re-POSTs per aggregated utterance. With `speech_marks=true` word marks carry absolute times on one session timeline, which is what `_SpeechMarkAccumulator`'s `_cumulative_time` offsetting exists to reconstruct today. Settings are query-string parameters with the HTTP endpoint's names, so `_build_payload`'s logic transfers. The class name `SpeechifyHttpTTSService` already reserves the slot for a sibling. — *Needs a call: whether to add a websocket class at all, and what reconnect behavior the session caps (one concurrent request, 60 s idle close, 5-minute hard close) imply for a long call.*
- **Pinned version has no override and no owner** (low, since 2026-09-28) — `SPEECHIFY_API_VERSION` is the module constant `2026-09-30`; a workspace that must stay on an older version cannot opt out, and the constant advances only when someone edits it. Both version-gated behaviors documented so far favor the current pin. — *Needs a call: whether the pin should be overridable at all, and who advances it as Speechify mints versions.*
- **`es-MX` not in the language map** (low, since 2026-09-14) — `simba-3.0`'s catalogue entry lists `en, de-DE, es-ES, es-MX, fr-FR, it-IT, pt-BR`; `language_to_speechify_language` maps only the six base codes, so `Language.ES_MX` falls through `resolve_language` to the identical string `es-MX` with a spurious `not verified` warning. Synthesis is unaffected. — *Needs a call: whether the map should carry regional keys at all — es-MX is an identity mapping, but the same question for en-GB or pt-PT is a substitution onto en-US/pt-BR and needs a stance.*

Last run's gap — requests carrying no `Speechify-Version` — is closed:
pipecat-ai/pipecat#5937 merged on 2026-09-28 and the header is in the service.
Nothing else moved. The request schema is otherwise unchanged (`input`,
`voice_id`, `model`, `language`, `options.{loudness_normalization,text_normalization}`,
`output_format`), the model enum still admits only `simba-3.0`/`simba-3.2`, and
the 2026-10-09 character-limit change applies to `/v1/audio/speech` only, not to
the streaming endpoint this service calls.
