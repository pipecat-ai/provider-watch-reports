# Speechify TTS — 2026-09-28

A real playback bug, now fixed on a branch: any pipeline running at 16 kHz gets
24 kHz audio labelled 16 kHz, because Speechify only returns true 16 kHz for
`pcm_16000` from API version `2026-09-30`, and the service pinned no version.

## What's new for Pipecat

### PRs
- https://github.com/pipecat-ai/pipecat/pull/5937 — Pin Speechify's API version on SpeechifyHttpTTSService requests

Speechify's 2026-09-30 entry states that `output_format: pcm_16000` returns 16 kHz
audio from that version, and that a workspace pinned earlier "keeps receiving
24 kHz audio for `pcm_16000`, as it always has". `_output_format_from_sample_rate`
asks for `pcm_16000` whenever the pipeline runs at 16 kHz and stamps 16000 onto
every frame, so on an older-pinned workspace the audio plays at the wrong rate.
Measured below: byte-identical to `pcm_24000` without the header, correct with it.
The API reference calls `pcm_16000` one of "the telephony formats Twilio/LiveKit
SIP expect", so telephony pipelines are the ones most exposed.

The branch adds `Speechify-Version: 2026-09-30` to the request headers as
`SPEECHIFY_API_VERSION`. It is bounded: grepping the published OpenAPI spec for
version-gated behavior returns exactly this one clause, so pinning changes nothing
else on the endpoints the service calls. No constructor parameter, matching the
one-line-constant bar.

### To consider
- **Pinned version has no override and no owner** (low, since 2026-09-28) — with the branch applied the version is the module constant `SPEECHIFY_API_VERSION`; a workspace that must stay on an older version cannot opt out, and the constant advances only when someone edits it. Cheap today — one version-gated behavior exists in the whole API reference — but not permanently so. — *Needs a call: whether the pin should be overridable at all, and who advances it as Speechify mints versions.*
- **`es-MX` not in the language map** (low, since 2026-09-14) — `simba-3.0`'s catalogue entry lists `en, de-DE, es-ES, es-MX, fr-FR, it-IT, pt-BR`; `language_to_speechify_language` maps only the six base codes, so `Language.ES_MX` falls through `resolve_language` to the identical string `es-MX` with a spurious `not verified` warning. Synthesis is unaffected. — *Needs a call: whether the map should carry regional keys at all — es-MX is an identity mapping, but the same question for en-GB or pt-PT is a substitution onto en-US/pt-BR and needs a stance.*

Nothing else moved. The request schema is unchanged (`input`, `voice_id`, `model`,
`language`, `options.{loudness_normalization,text_normalization}`, `output_format`
— the service builds all six), so no new `Settings` field is missing. `simba-3.2`
stays `recommended` and is the right default; `simba-3.0` is the catalogue's
`default` but is the multilingual model.

## Verification

Effective rate measured as the audio Speechify sent divided by the duration
Speechify itself reports in `speech.done` — the provider's own numbers on both
sides. `probe.py run` cannot drive this class (no way to supply the required
`aiohttp_session`), so the class rows come from
`.pw-scratch/speechify_class_probe.py`, which reuses `probe.py`'s pipeline harness.

Raw endpoint, `simba-3.2` / `geffen_32`, one call each:

| output_format | `Speechify-Version` sent | ok | audio bytes | reported duration | effective rate |
| ------------- | ------------------------ | -- | ----------- | ----------------- | -------------- |
| `pcm_16000`   | none                     | ✅ | 218720      | 4556 ms           | **24004 Hz** — wrong |
| `pcm_16000`   | `2026-09-30`             | ✅ | 145814      | 4556 ms           | **16002 Hz** — correct |
| `pcm_24000`   | none                     | ✅ | 218720      | 4556 ms           | 24004 Hz — correct, and byte-identical to unpinned `pcm_16000` |
| `pcm_8000`    | none                     | ✅ | 72906       | 4556 ms           | 8001 Hz — correct, so the defect is specific to `pcm_16000` |

Through `SpeechifyHttpTTSService`, before and after the branch:

| model     | pipeline rate | branch | ok | latency     | stamped / true rate  | note |
| --------- | ------------- | ------ | -- | ----------- | -------------------- | ---- |
| simba-3.2 | 16000         | before | ✅ | TTFB 185 ms | 16000 / 24004 Hz     | mismatch — the bug as a user hits it; 13 word marks |
| simba-3.2 | 16000         | after  | ✅ | TTFB 246 ms | 16000 / 16002 Hz     | fixed; 13 word marks, unchanged |
| simba-3.2 | 24000         | before | ✅ | TTFB 101 ms | 24000 / 24004 Hz     | already correct |
| simba-3.2 | 24000         | after  | ✅ | TTFB 88 ms  | 24000 / 24004 Hz     | unchanged by the pin |
| simba-3.0 | 16000         | before | ✅ | TTFB 111 ms | 16000 / —            | 62558→41751 samples across the branch, the same 1.5x drop, so the pin fixes this model too |
| simba-3.0 | 16000         | after  | ✅ | TTFB 144 ms | 16000 / —            | true rate not computed: the 4556 ms divisor is simba-3.2's utterance |

Single calls, not medians: no default bump is on the table, so the latencies only
confirm the pin costs nothing. Word-timestamp output is identical before and after.

Emotion, pitch and rate are still SSML inside `input`, not request fields
- https://docs.speechify.ai/build/guides/concepts/api-versioning — resolution order (header, then workspace default, then oldest supported), existing workspaces are never auto-migrated, and raw HTTP integrations are told to send the header. Explains why the account probed here still gets 24 kHz

- https://docs.speechify.ai/build/changelog/2026/9/23 — voice-cloning consent now required on every API version; `POST /v1/voices` only, synthesis calls and existing cloned voices unaffected. Not this unit
- https://docs.speechify.ai/build/changelog/2026/8/18 — the MP3 128 kbps default is not version-gated and does not touch PCM, so it is not a reason to avoid pinning
