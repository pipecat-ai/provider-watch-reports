# Azure LLM — 2026-08-31

Service is current: both API surfaces work, `DATED_API_VERSION` is still Azure's last dated version, and nothing in the code or examples names a retiring model. No branch this run — the two open questions (the `gpt-4.1` default, and Azure's Responses API) both need a maintainer.

## What's new for Pipecat

### PRs

Nothing.

### To consider

- **Default model is "Legacy" on Azure** (medium, since 2026-08-31) — Azure's retirement schedule lists `gpt-4.1` (2025-04-14) as **Legacy**, retiring 2027-04-14 with no named replacement; "Legacy" is Microsoft's signal that newer models exist and workloads should plan to migrate. aiewf-eval's `aiwf_medium_context` offers quality-parity successors — `gpt-5.1` 98.0% / 739 ms, `gpt-5.6-terra` (medium) 97.8% / 927 ms, `gpt-5.6-sol` 96.6% / 1098 ms against `gpt-4.1` 96.3% / 536 ms — but each is well beyond the 10% TTFAT allowance. Azure also treats the `model` string as a deployment name, so the default only helps users who name deployments after models. — *Needs a call: which GA tier, whether the slower first token is acceptable, and that `openai/llm` and `openai/responses-llm` share this default; the test resource has no gpt-5.x deployment, so the latency comparison could not be re-run on Azure.*
- **No Azure Responses API path** (medium, since 2026-08-31) — Azure's v1 API guidance recommends the Responses API for Azure OpenAI models. `OpenAIResponsesHttpLLMService` already works against Azure when `base_url` is the resource's `/openai/v1/` endpoint — probed live on the same `gpt-4.1` deployment at TTFAT 1157 ms, against 1860 ms for `AzureLLMService`'s chat completions. What is missing is an Azure entry point: no Entra ID token-provider path, and the WebSocket Responses class hardcodes `wss://api.openai.com/v1/responses`. — *Needs a call: an Azure Responses subclass plus docs, or documentation pointing Azure users at `base_url`.*
- **Azure-only request fields reachable only via `extra`** (low, since 2026-08-31) — `data_sources` (On Your Data) and `user_security_context` (Defender for Cloud) are Azure extensions to the chat-completions body with no named `Settings` field. `extra` is merged into the request verbatim in `base_llm`, so they are reachable; not probed, because `data_sources` needs a provisioned AI Search index. — *Needs a call: whether `extra` stays the documented answer for Azure-only fields.*
