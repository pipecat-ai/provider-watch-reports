# Azure LLM — 2026-11-23

`gpt-4.1` is unchanged as Deprecated-with-no-replacement, the quality evidence for `gpt-5.6-sol` / `gpt-5.5` is unchanged, and the bump still cannot be probed — the decision sits with a maintainer.

## What's new for Pipecat

### PRs

Nothing.

### To consider

- **Default model is Deprecated on Azure** (high, since 2026-08-31) — the retirement schedule was refreshed (`ms.date` 2026-11-18, was 2026-09-21) and `gpt-4.1` (2025-04-14) is still **Deprecated**, retirement 2027-04-14, **Replacement** empty; `gpt-4o` still points at `gpt-5.1`, and the o-series rows (`o1`, `o3`, `o3-mini`, `o4-mini`) reached their 2026-11-19 retirement with `gpt-5.6-sol` / `gpt-5.6-terra` named. What the refresh added is coverage: the table now carries GA rows for `gpt-5.5`, the whole `gpt-5.6` family and `gpt-6` / `gpt-6.1` (last month it stopped at gpt-5.6), and none of them is designated as anyone's replacement — so Azure still names no successor for `gpt-4.1`. Deprecated means a subscription that never deployed `gpt-4.1` cannot create the deployment our default names; existing deployments keep serving until retirement, and the resource's data plane still reports `lifecycle_status: "legacy"` for it, so schedule and catalogue continue to disagree on the stage. Quality evidence is unchanged from last run: aiewf-eval `aiwf_medium_context` still has `gpt-4.1` at 95.9% / 743 ms TTFAT P50, with `gpt-5.6-sol` (none) 96.9% / 765 ms (+3.0%) and `gpt-5.5` (none) 98.2% / 780 ms (+5.0%) above it and inside the allowance; `gpt-5.6-terra` (medium) tops the table at 99.9% but costs +35% first-token, `gpt-5.1` is 93.5%, `gpt-6-luna` (low) 91.8%. New this run: `gpt-6.2-astra` and `gpt-6.2-sol` went GA in Foundry on 2026-11-17 and appear in the resource catalogue, but neither is on the leaderboard and neither is on the retirement schedule yet. The probe is still the blocker — `gpt-5.6-sol`, `gpt-5.5` and `gpt-6-sol` all return 404 DeploymentNotFound on the test resource, so every latency figure for a candidate is OpenAI-direct. Azure treats `model` as a deployment name, which softens the impact to users who name deployments after models. — *Needs a call: whether to adopt `gpt-5.6-sol` (or `gpt-5.5`) on OpenAI-direct benchmark evidence alone, given Azure names no replacement for `gpt-4.1` and our resource has no candidate deployment to measure against.*
- **No Azure Responses API path** (medium, since 2026-08-31) — Azure's v1 API guidance recommends the Responses API for Azure OpenAI models (page unchanged, `ms.date` 2026-05-13). `OpenAIResponsesHttpLLMService` already works against Azure when `base_url` is the resource's `/openai/v1/` endpoint (probed live on 2026-08-31: TTFAT 1157 ms against 1860 ms for `AzureLLMService`'s chat completions on the same deployment). What is missing is an Azure entry point: no Entra ID token-provider path, and `OpenAIResponsesWebsocketLLMService` defaults `ws_url` to `wss://api.openai.com/v1/responses` with no Azure equivalent documented (the parameter is overridable, so this is documentation and ergonomics rather than a hard block). — *Needs a call: an Azure Responses subclass plus docs, or documentation pointing Azure users at `base_url`.*
- **Azure-only request fields reachable only via `extra`** (low, since 2026-08-31) — `data_sources` (On Your Data) and `user_security_context` (Defender for Cloud) are Azure extensions to the chat-completions body with no named `Settings` field. `extra` is merged into the request verbatim in `base_llm`, so they are reachable; not probed, because `data_sources` needs a provisioned AI Search index. — *Needs a call: whether `extra` stays the documented answer for Azure-only fields.*
