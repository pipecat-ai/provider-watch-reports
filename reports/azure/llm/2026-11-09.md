# Azure LLM — 2026-11-09

`gpt-4.1` is still Deprecated on Azure with no listed replacement, but aiewf-eval's refresh changed the picture: `gpt-5.6-sol` and `gpt-5.5` now beat it on quality within the latency allowance, so the default bump is a maintainer's call rather than a dead end — it just can't be probed on our resource.

## What's new for Pipecat

### PRs

Nothing.

### To consider

- **Default model is Deprecated on Azure** (high, since 2026-08-31) — the retirement schedule is unchanged since 2026-09-21: `gpt-4.1` (2025-04-14) **Deprecated**, retirement 2027-04-14, **Replacement** still empty, while `gpt-4o` points at `gpt-5.1` and the o-series at `gpt-5.6-sol` / `gpt-5.6-terra`. Deprecated means a subscription that never deployed `gpt-4.1` cannot create the deployment our default names; existing deployments keep serving until retirement. The resource's data plane still reports `lifecycle_status: "legacy"` for `gpt-4.1`, so schedule and catalogue still disagree on the stage. The new fact this run is quality evidence: aiewf-eval's `aiwf_medium_context` leaderboard was re-run (Responses-adapter refresh, OpenAI cohorts on Priority service) and every row moved — `gpt-4.1` is now 95.9% / 743 ms TTFAT P50, and two candidates clear it on both axes: `gpt-5.6-sol` (none) 96.9% / 765 ms, +3.0% latency, and `gpt-5.5` (none) 98.2% / 780 ms, +5.0%. `gpt-5.6-terra` (medium) tops the table at 99.9% but costs +35% first-token; `gpt-5.1` dropped to 93.5% and is out; the only gpt-6 row, `gpt-6-luna` (low), is 91.8%, below the current default, and `gpt-6-astra` / `gpt-6-sol` / `gpt-6.1-sol` / the new `gpt-6.1-terra` are still unbenchmarked. What still cannot be done is the probe: the test resource deploys `gpt-4.1` and `gpt-4o` only, and probing `gpt-5.6-sol` returns 404 DeploymentNotFound, so there is no Azure-side latency measurement — the leaderboard latencies are OpenAI-direct. Azure treats `model` as a deployment name, which softens the impact to users who name deployments after models. — *Needs a call: whether to adopt `gpt-5.6-sol` (or `gpt-5.5`) on OpenAI-direct benchmark evidence alone, given Azure names no replacement for `gpt-4.1` and our resource has no candidate deployment to measure against.*
- **No Azure Responses API path** (medium, since 2026-08-31) — Azure's v1 API guidance recommends the Responses API for Azure OpenAI models (page unchanged, `ms.date` 2026-05-13). `OpenAIResponsesHttpLLMService` already works against Azure when `base_url` is the resource's `/openai/v1/` endpoint (probed live on 2026-08-31: TTFAT 1157 ms against 1860 ms for `AzureLLMService`'s chat completions on the same deployment). What is missing is an Azure entry point: no Entra ID token-provider path, and the WebSocket Responses class hardcodes `wss://api.openai.com/v1/responses`. — *Needs a call: an Azure Responses subclass plus docs, or documentation pointing Azure users at `base_url`.*
- **Azure-only request fields reachable only via `extra`** (low, since 2026-08-31) — `data_sources` (On Your Data) and `user_security_context` (Defender for Cloud) are Azure extensions to the chat-completions body with no named `Settings` field. `extra` is merged into the request verbatim in `base_llm`, so they are reachable; not probed, because `data_sources` needs a provisioned AI Search index. — *Needs a call: whether `extra` stays the documented answer for Azure-only fields.*
