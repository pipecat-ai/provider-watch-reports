# Azure LLM — 2026-10-12

`gpt-4.1` is now **Deprecated** on Azure's schedule — new subscriptions can't deploy the model our default names — but no successor is defensible yet, so this needs a maintainer rather than a branch.

## What's new for Pipecat

### PRs

Nothing.

### To consider

- **Default model is Deprecated on Azure** (high, since 2026-08-31) — the retirement schedule refreshed on 2026-09-21 moved `gpt-4.1` (2025-04-14) from **Legacy** to **Deprecated**, retirement unchanged at 2027-04-14 and the Replacement column still empty. Azure's lifecycle policy defines Deprecated as blocked for new customers — "new customers can't create deployments or access the model", decided per subscription — so a user on a fresh subscription cannot create the `gpt-4.1` deployment our default names; existing deployments keep serving until retirement. The resource's own data plane still reports `lifecycle_status: "legacy"` for `gpt-4.1`, so the published schedule and the catalogue disagree on the stage. Successor candidates grew this run: `gpt-6-astra` (GA 2026-09-03), `gpt-6-sol` and `gpt-6-luna` (GA 2026-09-22) and `gpt-6.1-sol` (GA 2026-09-29, in the catalogue but in no Microsoft page found) — Microsoft positions Sol as the general-purpose production model and the migration target "for teams moving off a legacy model", Luna as the faster small sibling. None of them appears on aiewf-eval's `aiwf_medium_context` leaderboard, so quality parity is unestablished; the benchmarked gpt-5.x rows are unchanged and all cost more than the 10% TTFAT allowance (`gpt-5.1` 98.0% / 739 ms, `gpt-5.6-terra` medium 97.8% / 927 ms, `gpt-5.6-sol` 96.6% / 1098 ms against `gpt-4.1` 96.3% / 536 ms). Azure treats the `model` string as a deployment name, which softens the impact to users who name deployments after models. — *Needs a call: which model becomes the default now that new subscriptions are shut out of `gpt-4.1`, with no gpt-6 benchmark data and a 10%+ first-token cost on every benchmarked gpt-5.x; the test resource deploys only `gpt-4.1` and `gpt-4o`, so the comparison cannot be run on Azure.*
- **No Azure Responses API path** (medium, since 2026-08-31) — Azure's v1 API guidance recommends the Responses API for Azure OpenAI models (page unchanged, dated 2026-05-13). `OpenAIResponsesHttpLLMService` already works against Azure when `base_url` is the resource's `/openai/v1/` endpoint (probed live on 2026-08-31: TTFAT 1157 ms against 1860 ms for `AzureLLMService`'s chat completions on the same deployment). What is missing is an Azure entry point: no Entra ID token-provider path, and the WebSocket Responses class hardcodes `wss://api.openai.com/v1/responses`. — *Needs a call: an Azure Responses subclass plus docs, or documentation pointing Azure users at `base_url`.*
- **Azure-only request fields reachable only via `extra`** (low, since 2026-08-31) — `data_sources` (On Your Data) and `user_security_context` (Defender for Cloud) are Azure extensions to the chat-completions body with no named `Settings` field. `extra` is merged into the request verbatim in `base_llm`, so they are reachable; not probed, because `data_sources` needs a provisioned AI Search index. — *Needs a call: whether `extra` stays the documented answer for Azure-only fields.*
