# Azure Realtime — 2026-11-09

Nothing to review. Azure shipped no realtime model or protocol change this cycle, the class is unchanged in substance, and all five known gaps reproduce with the same maintainer calls.

## What's new for Pipecat

### PRs
Nothing.

### To consider
- **Deployment name never set** (high, since 2026-08-31) — `examples/realtime/realtime-azure.py` and the `azure_realtime` CLI scaffold construct `AzureRealtimeLLMService` with no `Settings(model=...)`, so the base class appends OpenAI's default `?model=gpt-realtime-2.1`. On Azure that query parameter names the user's *deployment*, so a fresh bot connects only if the deployment happens to carry that name. — *Needs a call: which env var names the deployment (the scaffold's env template emits only `AZURE_REALTIME_API_KEY` and `AZURE_REALTIME_BASE_URL`), and whether the service should refuse to connect when no deployment is named.*
- **Scaffold's transcription config is dropped** (medium, since 2026-08-31) — the `azure_realtime` scaffold emits `SessionProperties(input_audio_transcription=InputAudioTranscription(model="whisper-1"))`; that field is not on `SessionProperties`, pydantic ignores it (`model_dump(exclude_none=True)` → `{'type': 'realtime'}`, re-checked this run), and generated bots get no user transcription. The accepted shape is `audio=AudioConfiguration(input=AudioInput(transcription=...))`. — *Needs a call: on Azure the transcription model is itself a deployment name, so fixing the shape still leaves `whisper-1` working only by coincidence.*
- **Reasoning stripped on Azure** (medium, since 2026-08-31) — `_strip_unsupported_reasoning` recognizes reasoning-capable models by substring on `Settings.model`, which on Azure is an opaque deployment name; a `gpt-realtime-2.1` deployment named anything else loses its `Reasoning(effort=...)` before `session.update`. — *Needs a call: whether Azure should skip the capability check entirely or gate it on something explicit.*
- **Transcription/translation sessions** (low, since 2026-08-31) — Azure ships `gpt-realtime-translate`, `gpt-realtime-whisper` and `gpt-live-transcribe` behind a translation flow (`/openai/v1/realtime/translations`) and `session.type = "transcription"`; neither is reachable from this class. — *Needs a call: these are arguably a separate realtime STT/translation service, not this LLM class.*
- **No API-reference page** (low, since 2026-08-31) — `llm/azure` covers only `AzureLLMService` and `s2s/azure` still 404s (both re-checked this run), so nothing on docs.pipecat.ai tells users that `Settings.model` is the deployment name or that dated `api-version` URLs don't work. — *Needs a call: the docs site is a separate repo, so this needs an owner there.*

Not gaps, checked this run: the retirement schedule is unchanged since the last run (`gpt-realtime-2.1` and `-2.1-mini` GA to 2027-06-25, `gpt-realtime-2` preview with `gpt-realtime-2.1` as its replacement), so the inherited default still names a GA Azure model and needs no bump. The realtime how-to was re-touched today; the only substantive differences are a "Connection methods" table (WebRTC / WebSocket / SIP, WebSocket being the server-to-server recommendation this service already uses) and the removal of `gpt-4o-realtime-preview` and `gpt-4o-mini-realtime-preview` from the supported-model list — neither name appears anywhere in Pipecat's Azure code or examples. The GA-endpoint rule ("use the GA endpoint format with `/openai/v1` in the URL. Don't use date-based API versions"), the `api-key` header, the session types and the 60-minute cap all still match the class. The "what's new" page is unchanged (newest entry still May 2026). The only code change to this unit since the last run replaces its `_connect` override with the base class's new `_auth_headers` hook — same headers, no behavior change. The `azure` extra pins only `azure-cognitiveservices-speech` (latest 1.53.0, inside `>=1.47.0,<2`), which the realtime path does not use.
