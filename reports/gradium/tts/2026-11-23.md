# Gradium TTS — 2026-11-23

Nothing to do on models: `default` is still the stable alias and still what we ship, and Gradium shipped no TTS change at all in the two weeks since the last run. The six known gaps stand unchanged; still no branch, because the one PR-shaped fix (`Settings.model` pass-through) needs a live probe and no API key was available for the fifth run running.

## What's new for Pipecat

### PRs
Nothing.

### To consider
- **`Settings.model` is dropped** (medium, since 2026-09-01) — `_build_setup_msg` builds `type`/`output_format`/`voice_id`/`close_ws_on_eos`/`client_req_id` (plus `json_config` and `log_level` when set) and no `model_name`, so a user who sets `Settings(model="gradium-tts-beta")` silently gets the server default and no error. Our default value (`default`) matches the server default, so adding the key is behavior-preserving. — *Needs a call: only in the sense that the fix needs a live probe first; GRADIUM_API_KEY was unset this run too.*
- **Voice tuning is constructor-only** (medium, since 2026-09-01) — `temp`, `padding_bonus` and `rewrite_rules` live in Gradium's `json_config`, which we take as a JSON string at construction time and never as Settings; the deprecated `InputParams.temp` has no replacement field. — *Needs a call: typed per-knob Settings fields, or a single `json_config` dict field superseding the constructor argument.*
- **`pronunciation_id` not exposed** (medium, since 2026-09-01) — a session-wide pronunciation dictionary is a top-level setup field, and websocket-only. A Settings field would pass through in `_build_setup_msg`. — *Needs a call: verifying it needs a real dictionary created on the account, which a probe cannot do.*
- **Stale `_setup_context_ids` after `run_tts`'s inline reconnect** (low, since 2026-09-01) — only `run_tts`'s own `state is State.CLOSED` branch reopens the socket via `_connect()` without clearing the set, so a context already set up on the dead socket gets `text` on a socket that never received its `setup`. — *Needs a call: whether to handle it, or just clear the set in `_connect`.*
- **`Settings.language` is inert** (low, since 2026-09-01) — Gradium's TTS setup has no language field; language comes from the voice, normalization from `rewrite_rules`. — *Needs a call: map it onto `rewrite_rules`, or document it as unsupported here.*
- **Telephony output formats unused** (low, since 2026-09-01) — always `pcm` at 48 kHz, though `ulaw_8000`, `alaw_8000`, lower PCM rates, `wav` and `opus` are available, and Gradium's telephony recipe asks clients not to resample locally. — *Needs a call: whether server-side rate selection is worth diverging from the fixed 48 kHz the docs promise.*

Not gaps: the only release-notes entry since the last run is 2026.11.10 speech-to-text accuracy, which belongs to `gradium/stt`; the 2026.11.09 TTS entry was already covered and was an in-place change to the `default` model. The websocket setup/text/end_of_stream schema is unchanged, nothing in it is new or deprecated, and `cfg_coef` remains the only deprecated `json_config` key (we never send it). Voice Settings now documents `padding_bonus` as -2.0–4.0 rather than -4.0–4.0 — a narrower documented range for a knob this service does not expose, folded into the voice-tuning item's note. Pipecat-side, `log_level` is now sent in the setup message (commit 63fabb485, 2026-11-16), which closes nothing on this list but means server warnings about unknown `json_config` keys reach the logs.

Carried from the previous report and not re-verified: our default voice `_6Aslh2DxfmnRLmP` (Russell). The flagship-voices page still renders its tables client-side and serves no voice ids to a fetcher, and `GET /voices/` needs the missing key. No release note retires a voice id, so it is treated as unchanged.
