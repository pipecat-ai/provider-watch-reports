# Gradium TTS — 2026-10-28

Nothing to do on models: `default` is still the stable alias and still what we ship. October's second half was voice-catalogue and Studio work plus one resampling change that does not reach the `pcm` path this service uses. The six known gaps stand unchanged; still no branch, because the one PR-shaped fix (`Settings.model` pass-through) needs a live probe and no API key was available for the third run running.

## What's new for Pipecat

### PRs
Nothing.

### To consider
- **`Settings.model` is dropped** (medium, since 2026-09-01) — `_build_setup_msg` builds `type`/`output_format`/`voice_id`/`close_ws_on_eos`/`client_req_id` and no `model_name`, so a user who sets `Settings(model="gradium-tts-beta")` silently gets the server default and no error. Our default value (`default`) matches the server default, so adding the key is behavior-preserving. — *Needs a call: only in the sense that the fix needs a live probe first; GRADIUM_API_KEY was unset this run too.*
- **Voice tuning is constructor-only** (medium, since 2026-09-01) — `temp`, `padding_bonus` and `rewrite_rules` live in Gradium's `json_config`, which we take as a JSON string at construction time and never as Settings; the deprecated `InputParams.temp` has no replacement field. — *Needs a call: typed per-knob Settings fields, or a single `json_config` dict field superseding the constructor argument.*
- **`pronunciation_id` not exposed** (medium, since 2026-09-01) — a session-wide pronunciation dictionary is a top-level setup field, and websocket-only. A Settings field would pass through in `_build_setup_msg`. — *Needs a call: verifying it needs a real dictionary created on the account, which a probe cannot do.*
- **Stale `_setup_context_ids` after `run_tts`'s inline reconnect** (low, since 2026-09-01) — only `run_tts`'s own `state is State.CLOSED` branch reopens the socket via `_connect()` without clearing the set, so a context already set up on the dead socket gets `text` on a socket that never received its `setup`. — *Needs a call: whether to handle it, or just clear the set in `_connect`.*
- **`Settings.language` is inert** (low, since 2026-09-01) — Gradium's TTS setup has no language field; language comes from the voice, normalization from `rewrite_rules`. — *Needs a call: map it onto `rewrite_rules`, or document it as unsupported here.*
- **Telephony output formats unused** (low, since 2026-09-01) — always `pcm` at 48 kHz, though `ulaw_8000`, `alaw_8000`, lower PCM rates, `wav` and `opus` are available, and Gradium's telephony recipe asks clients not to resample locally. — *Needs a call: whether server-side rate selection is worth diverging from the fixed 48 kHz the docs promise.*

Not gaps: the 2026-10-28 removal of the 40 ms leading silence (`json_config.no_resampling_delay`, default true) applies only to `pcm_8000`/`pcm_16000`/`pcm_22050`/`pcm_24000`/`pcm_44100`/`ulaw_8000`/`alaw_8000`; `pcm`, `pcm_48000`, `wav` and `opus` are explicitly unaffected, so our fixed `pcm` output is byte-identical to before. Phonon (2026-10-20) is an on-device TTS runtime, not the hosted websocket API this service speaks. Voice-list filters with the new `rank` field and clone enhancement-by-default (both 2026-10-23), the catalogue expansion to 1,400+ voices (2026-10-09), and Voice Localization (2026-10-08) are all REST voice-management features whose output is an ordinary `voice_id` that `Settings.voice` already carries. The websocket setup/text/end_of_stream schema and the `ready`/`audio`/`text`/`end_of_stream`/`error` server messages are unchanged, with no field marked deprecated.

Carried from the previous report and not re-verified: our default voice `_6Aslh2DxfmnRLmP` (Russell) was listed as a flagship voice on 2026-10-12, but the flagship-voices page now renders its tables client-side and serves no voice ids to a fetcher, and `GET /voices/` needs the missing key. No release note retires a voice id, so it is treated as unchanged.
