# Gradium STT — 2026-11-23

Nothing to act on. Gradium's one new STT entry this run, 2026.11.10, improves the
`default` model's accuracy across all languages and its number formatting — again
in place, under the same name, with no new or changed parameters and no
retirement — so the model Pipecat ships is already the improved one. The service
picked up one Pipecat-side change since the last run (#6847, 2026-11-18, which
confirms finalization when a VAD stop's flush is acknowledged); it touches no
provider-facing values. The same five Settings-coverage items carry forward, all
open since 2026-09-01. Nothing could be probed — `GRADIUM_API_KEY` is not set in
this environment — so no item could qualify for a PR.

## What's new for Pipecat

### PRs
Nothing.

### To consider
- **Keyword boosting** (medium, since 2026-09-01) — `json_config.keywords` is not reachable from `Settings`; a `keywords` field passed into the setup message would cover it. `{"words": [...], "boost": 3}`, boost valid from -6 to 6, 3 recommended and 4 for rare vocabulary, 5–6 risking the decoder repeating a keyword, negative values de-boosting. Up to 500 entries, each case/accent variant counting separately, multi-word names split into space-free tokens. Still no saved-dictionary or `keyword_boost_id` equivalent, so the words go inline on every connection. — *Needs a call: the field shape, raw dict vs a typed model carrying the documented boost range; probe blocked on GRADIUM_API_KEY.*
- **Translating model** (medium, since 2026-09-01) — `model="stt-translate"` transcribes into another language chosen with `target_language`, which `Settings` has no field for, and our `language` handling assumes it names the audio's language. Translation output is en/fr/de/es/pt only (no `any`). — *Needs a call: whether translated transcription belongs in an STT service, given the emitted `TranscriptionFrame` would carry the output language, not the audio's.*
- **Required language** (medium, since 2026-09-01) — `json_config.language` is mandatory ("Requests without it are rejected"), stated on both the settings guide and the endpoint reference; `Settings(language=None)` omits it and the setup is rejected. — *Needs a call: fall back to `"any"` or reject at construction time.*
- **`temp` and `padding_bonus`** (low, since 2026-09-01) — documented tuning knobs with no `Settings` fields. Temperature is listed as `temp` 0.0–1.5 on the settings guide and as `temperature` up to 1.0 defaulting to 0 on the endpoint reference. `padding_bonus` remains contested the same way it was last run: the settings guide lists it among the STT `json_config` keys at -4.0 to 4.0, the endpoint reference documents it for TTS only. — *Needs a call: which page holds for the temperature range and key name, and whether `padding_bonus` is an STT knob at all; probe blocked on GRADIUM_API_KEY.*
- **Delay default, allowed values and flush_id type** (low, since 2026-09-01) — we default `delay_in_frames` to 12 where Gradium documents 10, and the deprecated `InputParams` docstring still describes the default as 10, so the two docstrings disagree with each other as well. The four pages' allowed-value sets are unchanged from last run: our docstring's ten match the endpoint reference, the turn-taking recipe lists eleven (adding 32), the settings guide says 7–56 and model-dependent, the WebSocket STT guide says 7–55 with 16 suggested. Our 12 is valid under all four. `_send_flush` sends `flush_id` as a string where the reference types it an integer. — *Needs a call: whether to move our default to Gradium's 10, and confirmation that a string flush_id stays accepted.*

Nothing from the 2026-11-09 report is unaccounted for: it carried no PRs, and all
five of its gaps still hold.
