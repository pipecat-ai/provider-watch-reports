# Gradium STT — 2026-09-14

`default` is still the model to ship and last run's 300 s session cap is gone
(Gradium raised it to 3000 s on 2026-09-02), but reconnect handling is now the
item to look at: a mid-call reconnect keeps the service's turn state, which can
silence turn detection for the rest of the call. Nothing could be probed —
`GRADIUM_API_KEY` is not set in this environment.

## What's new for Pipecat

### PRs
Nothing.

### To consider
- **Stale state after a reconnect** (high, since 2026-09-14) — `WebsocketService._reconnect_websocket` (via `STTService`) tears down and rebuilds only the socket; Gradium's `_disconnect()`, which resets `_turn_phase`, `_accumulated_text`, `_flush_counter` and `_flush_cooldown`, is not on that path. A clean server close does reconnect (the base loop routes a normally-returning `_receive_messages()` into `_maybe_try_reconnect`), but if the reconnect lands while `_turn_phase` is `ENDING`, the `flushed` ack it was waiting for never arrives, `_handle_step` ignores every subsequent step, and no further turn is ever proposed — and with `enable_turn_detection=True` the service recommends `ExternalUserTurnStrategies`, so no local VAD covers for it. Independently of turn detection, leftover `_accumulated_text` is prefixed onto the next transcript. — *Needs a call: where the reset belongs — a Gradium `_reconnect_websocket` override, or resetting the per-connection state inside `_connect_websocket` so both the first connect and every reconnect share one place.*
- **Keyword boosting** (medium, since 2026-09-01) — `json_config.keywords` (`{"words": [...], "boost": 3}`, boost -6 to 6, up to 500 space-free entries, live since 2026-07-22) is not reachable; a `keywords` Settings field passed into the setup message would cover it. There is no `keyword_boost_id` or saved-dictionary equivalent in the current docs. — *Needs a call: the field shape, raw dict vs a typed model carrying the documented boost range; probe blocked on GRADIUM_API_KEY.*
- **Translating model** (medium, since 2026-09-01) — `model="stt-translate"` transcribes into another language chosen with `target_language`, which Settings has no field for, and our `language` handling assumes it names the audio's language. — *Needs a call: whether translated transcription belongs in an STT service, given the emitted `TranscriptionFrame` would carry the output language, not the audio's.*
- **PCM rate fallback** (medium, since 2026-09-01) — `_input_format_from_encoding` maps only 8000/16000/24000 and warns-then-uses `pcm_16000` for anything else; Gradium's `input_format` enum accepts `pcm_22050`, `pcm_44100` and `pcm_48000`, so a 48 kHz pipeline gets mis-transcribed rather than rejected. — *Needs a call: none in principle, but the fix needs a 48 kHz probe, blocked on GRADIUM_API_KEY.*
- **Required language** (medium, since 2026-09-01) — `json_config.language` is mandatory ("Requests without it are rejected"); `Settings(language=None)` omits it and the setup is rejected. — *Needs a call: fall back to `"any"` or reject at construction time.*
- **`temp` and `padding_bonus`** (low, since 2026-09-01) — documented tuning knobs with no Settings fields (`padding_bonus` -4.0 to 4.0 to bias text earlier or later; `temp` listed as 0.0–1.5 on the settings guide and 0–1.4 default 0.7 on the endpoint reference). — *Needs a call: none beyond probe verification (blocked on GRADIUM_API_KEY) and picking which of the two documented `temp` ranges holds.*
- **Delay default and flush_id type** (low, since 2026-09-01) — we default `delay_in_frames` to 12 where Gradium documents 10; our docstring's ten allowed values match the endpoint reference, while the settings guide describes any int 0–80, so the docstring itself is defensible. `_send_flush` sends `flush_id` as a string where the reference types it an integer. — *Needs a call: whether to move our default to Gradium's 10, and confirmation that a string flush_id stays accepted.*

Two items from 2026-09-01 are gone. **Semantic VAD `step` messages** are no longer
dropped: `enable_turn_detection` landed in a9afa61be (2026-09-11) and drives turns
off the `step` signal, and docs.pipecat.ai already documents it. The **300 s
session cap** item no longer holds as written — the cap is 3000 s as of
2026-09-02, and the base receive loop does reconnect on a clean server close
rather than breaking on `ConnectionClosedOK` (that branch only catches a close
raised out of an explicit `recv`/`send`); what survives of it is the stale-state
item above.
