`list-models` failed the same way (401 from `/v1/models`), so the catalogue above comes from Crusoe's docs. The 401 is a credential problem on our side, not a service defect — the request shape and `base_url` match the documented OpenAI-compatible endpoint.

Findings that did not need a probe:

- **Catalogue is unchanged** since the last run: the same 16 model IDs, nothing marked deprecated, retiring, or preview. `zai/GLM-5.2` is present and is the newer of the two GLMs.
- **No default bump is warranted.** Crusoe is a model-agnostic host and designates no successor. On aiewf-eval `aiwf_medium_context`, `glm-5.2 (none)` scores 99.7% / 936 ms P50, ahead of every other model in Crusoe's catalogue except `nemotron-3-ultra (128)` (100% / 541 ms), a 550B model the provider does not position as a replacement for anything.
- **GLM-5.3 exists upstream but not on Crusoe.** The leaderboard now carries `glm-5.3 (low reasoning)` at 98.7% / 2376 ms via Z.AI — a pass-rate and latency regression against 5.2 — and Crusoe does not host it. Nothing to do on either count; re-check if Crusoe adds it.
- **No `Settings` gap.** The class is a thin `OpenAILLMService` subclass; `BaseOpenAILLMService.Settings.extra` already passes arbitrary provider parameters (e.g. GLM thinking controls) straight into the request.
- **Base URL matches** the documented endpoint `api.inference.crusoecloud.com`, and `supports_developer_role = False` remains consistent with the docs, which show only `system`/`user`/`assistant` roles.
- **The example** `examples/function-calling/function-calling-crusoe.py` pins no model string, so nothing there can go stale.
