# Piper TTS — 2026-10-12

Current: no `piper-tts` release since 1.8.0, no API change, and the same four
items carried over — PR 5551 still carries the `/synthesize` docstring and the
synthesis settings.

Piper has no model dimension (`default_model` is `null` for both classes); the
catalogue axis is voices, now 177 across 58 languages in `voices.json`, all
accepted as-is — no allowlist, no per-voice table. Our `piper-tts>=1.3.0,<2`
pin is on the latest release.

One thing to watch, with nothing to do here: `voices.json` added
`lt_LT-reginute1-medium`, whose `lithuanian` phoneme type exists only on
piper1-gpl's unreleased branch — `PhonemeType` in the installed 1.8.0 has
`espeak, text, pinyin, hebrew, japanese, thai`. The voice starts working when
upstream ships it, which our pin already admits. Unlike the zh/ja/th voices,
the Lithuanian phonemizer needs no new extra (espeak-ng plus a bundled pitch
accent dictionary), so it does not widen that item.

## What's new for Pipecat

### PRs
- https://github.com/pipecat-ai/pipecat/pull/5551 — Document PiperHttpTTSService's synthesis endpoint and expose Piper's per-request synthesis controls (open since 2026-09-01, unchanged)

### To consider
- **Docs snippet posts to the server root** (high, since 2026-09-01) — the Piper page on docs.pipecat.ai still constructs `PiperHttpTTSService(base_url="http://localhost:5000", ...)`; against Piper's `http_server` that is `POST /` → 405 (probed 2026-09-01), while `POST /synthesize` → 200. Copy-pasting the documented example never produces audio. — *Needs a call: fix the snippet in the docs repo, or decide whether the service should append `/synthesize` itself — that would break setups whose `base_url` already names the endpoint or points at a legacy Piper server that serves `POST /`.*
- **Chinese, Japanese and Thai voices are unreachable** (medium, since 2026-09-01) — `voices.json` ships `zh_CN`, `ja_JP` and `th_TH` voices, but `pipecat-ai[piper]` installs plain `piper-tts`: `import piper.phonemize_chinese` raises `ModuleNotFoundError: No module named 'unicode_rbnf'`, while `piper.phonemize_japanese` and `piper.phonemize_thai` import `pyopenjtalk` / `tltk` lazily, so those voices fail at synthesis time. — *Needs a call: the `zh` extra pulls `transformers` and `g2pW`, `ja` pulls `pyopenjtalk-plus`, and `th` pulls `tltk` and `pandas` — whether `pipecat-ai[piper]` carries them or the docs tell users to install them.*
- **`volume` and `normalize_audio`** (low, since 2026-09-01) — `SynthesisConfig` in 1.8.0 takes `speaker_id, length_scale, noise_scale, noise_w_scale, normalize_audio, volume`; the last two have no equivalent in Piper's `/synthesize` body, so only `PiperTTSService` could expose them. — *Needs a call: exposing them would make the two Piper settings classes asymmetric.*
- **Vestigial `requests` pin** (low, since 2026-09-01) — the `piper` extra pins `requests>=2.32.5,<3`; `piper-tts` 1.8.0 declares no `requests` dependency in any extra, nothing under `src/pipecat/services/piper/` imports it, and `download_voices` uses `urllib`. — *Needs a call: confirm nothing else in the Piper path needs `requests` before dropping the pin.*
