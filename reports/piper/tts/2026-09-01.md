# Piper TTS — 2026-09-01

`PiperHttpTTSService` 405s when `base_url` is the server root — which is what our
docs show; the branch documents the `/synthesize` endpoint and adds Piper's
speaker and synthesis-scale settings.

Piper has no model dimension: `default_model` is `null` for both classes and the
catalogue axis is voices — 175 across 56 languages in `voices.json`, all of which
both classes accept as-is (no allowlist, no per-voice table).

## What's new for Pipecat

### PRs
- https://github.com/pipecat-ai/pipecat/pull/5551 — Document PiperHttpTTSService's synthesis endpoint and expose Piper's per-request synthesis controls

### To consider
- **Docs snippet posts to the server root** (high, since 2026-09-01) — the Piper page on docs.pipecat.ai constructs `PiperHttpTTSService(base_url="http://localhost:5000", ...)`; against `piper-tts` 1.7.0's `http_server` that is `POST /` → 405, while `POST /synthesize` → 200. Copy-pasting the documented example never produces audio. — *Needs a call: fix the snippet in the docs repo, or decide whether the service should append `/synthesize` itself — that would break setups whose `base_url` already names the endpoint or points at a legacy Piper server that serves `POST /`.*
- **Chinese and Japanese voices are unreachable** (medium, since 2026-09-01) — `voices.json` ships `zh_CN` and `ja_JA` voices, but `pipecat-ai[piper]` installs plain `piper-tts`: `import piper.phonemize_chinese` raises `ModuleNotFoundError: No module named 'unicode_rbnf'`, and `piper.phonemize_japanese` imports `pyopenjtalk` lazily, so a Japanese voice fails at synthesis time. — *Needs a call: the `zh` extra pulls `transformers` and `g2pW` and `ja` pulls `pyopenjtalk-plus` — whether `pipecat-ai[piper]` carries them or the docs tell users to install them.*
- **`volume` and `normalize_audio`** (low, since 2026-09-01) — `SynthesisConfig` takes both, but Piper's `/synthesize` body has no equivalent, so only `PiperTTSService` could expose them. — *Needs a call: exposing them would make the two Piper settings classes asymmetric.*
- **Vestigial `requests` pin** (low, since 2026-09-01) — the `piper` extra pins `requests>=2.32.5,<3`; `piper-tts` 1.7.0 declares no `requests` dependency, nothing under `piper/` imports it, and `download_voices` uses `urllib`. — *Needs a call: confirm nothing else in the Piper path needs `requests` before dropping the pin.*

`PiperTTSService` was probed with `probe.py run` (cwd holding the downloaded
voice, since `download_dir` takes a `Path` the CLI cannot express).
`PiperHttpTTSService` takes an `aiohttp.ClientSession`, which `probe.py` cannot
inject, so it went through `probe.py`'s own `_run_pipeline` from
`.pw-scratch/piper_http_probe2.py` against a local `python -m piper.http_server
-m en_US-ryan-high --port 5099`. No credentials are involved — Piper is local.
