# xAI Realtime — 2026-11-09

Grok Voice 3.0 is out and `grok-voice-latest` — our default — already resolves
to it, so nothing needs changing for the release; the gap list is the September
one minus the merged 11025 Hz fix, plus one low reasoning-defaults item.

## What's new for Pipecat

### PRs
Nothing.

### To consider
- **Missing `format` is never backfilled** (high, since 2026-09-28) — `_ensure_audio_config` only substitutes a wholly missing `audio.input` / `audio.output`. `SessionProperties(audio=AudioConfiguration(output=AudioOutput(speed=1.2)))` therefore keeps `format=None`, and `_get_output_sample_rate()` raises `RuntimeError("Output sample rate not configured.")` from `_handle_evt_audio_delta` — on the first assistant audio chunk and every one after. `speed`, `transport` and `transcription` are exactly the fields a user reaches for without thinking about sample rates, and on the input side the same omission makes the rate silently `None`, which additionally skips the `_ensure_audio_config` rescue in `_update_settings`. No in-tree example sets these, so nothing in the repo is broken today. — *Needs a call: backfilling the missing `format` from the transport's sample rate changes what a currently-broken config does, so it is a behavior fix rather than a value change; rejecting the incomplete config up front is the other option.*
- **Binary audio transport** (medium, since 2026-09-01) — `AudioOutput.transport` exposes xAI's `"binary"` wire path, but `_receive_task_handler` hands every message to `parse_server_event`, which parses JSON. The spec settles the input half: the server "dual-accepts both channels for the configured format", so `_send_user_audio`'s base64 is fine even with `input.transport="binary"`; output "emits on the configured transport only", so a user who sets it gets parse warnings and silence. — *Needs a call: implement binary framing on the receive side, or drop `transport` from `AudioOutput` so the field cannot be set to a value the service does not honor.*
- **SIP `call_id`** (medium, since 2026-09-01) — `_connect` always builds `?model=<model>`; joining an inbound SIP call requires `?call_id=<id>`, which the spec says makes `model` ignored. The service already handles `input_audio_buffer.dtmf_event_received`, which xAI emits on SIP sessions only, so that path is unreachable today. — *Needs a call: `call_id` is per-call rather than per-service, so it needs a constructor or settings shape rather than a pass-through field.*
- **Session resumption never resumes** (medium, since 2026-09-28) — `resumption.enabled` reaches the wire and the service stores `conversation.created`'s id in `self._conversation_id`, but nothing reads it and `_connect` never appends `?conversation_id=`. Opting in makes xAI cache turns for 30 minutes that Pipecat can never replay. — *Needs a call: should the service reconnect with its own cached `conversation_id` automatically, or expose it so the application decides when to resume?*
- **Search-tool options** (medium, since 2026-09-28) — `WebSearchTool` carries only `type` and `XSearchTool` only `allowed_x_handles`, while xAI documents domain filters, a search `location`, date ranges, handle exclusions and image/video understanding. There is no workaround: the `GrokTool` union matches `WebSearchTool` before `dict[str, Any]`, so `{"type": "web_search", "allowed_domains": ["x.com"], "enable_image_understanding": True}` validates into a bare `WebSearchTool` and both options disappear without a warning. — *Needs a call: `allowed_domains`/`excluded_domains` and `allowed_x_handles`/`excluded_x_handles` are documented as mutually exclusive, with maxItems caps, so exposing them needs a stance on client-side validation versus letting the server reject.*
- **`audio/opus` codec** (low, since 2026-09-01) — xAI accepts `audio/opus` (24 kHz mono, one raw Opus packet per payload) for both directions; `events.py` models PCM, PCMU and PCMA only. — *Needs a call: Opus packets must be decoded before becoming `TTSAudioRawFrame`, so a new format class alone would not make it work.*
- **Reasoning runs at the provider default** (low, since 2026-11-09) — xAI documents `reasoning.effort` as `high` (default) or `none`, and the Grok Voice 3.0 page calls out that reasoning is on by default; `Reasoning` is reachable from `SessionProperties` but the service sends no value, so every session reasons unless the developer opts out. CONTRIBUTING's reasoning-defaults convention would have the service send `none`. The measurement does not back it up: an ad-hoc A/B on `grok-voice-latest` gave 855 ms median time-to-first-audio with `high` against 741 ms with `none`, three runs each with overlapping spreads. — *Needs a call: whether speech-to-speech services should adopt the reasoning-defaults convention at all — no realtime service in the repo keeps a defaults table.*

The spec is otherwise matched exactly: all 37 documented server events are in the
receive loop (plus `ping`), all nine client events are sent, and `instructions`,
`voice`, `reasoning.effort`, `turn_detection`, `resumption.enabled`, `replace`,
`audio.output.speed`, `audio.input.transcription.language_hint`/`keyterms`,
`previous_item_id` and all five tool types are reachable from `SessionProperties`.
`response.create`'s `metadata` correlation field is not modelled, but Pipecat
drives `response.create` itself, so there is no user path to set it. The spec's
model enum has been renamed — `grok-voice-think-fast-2.0` is gone, replaced by
`grok-voice-3.0` and the deprecated `grok-voice-2.0` — and the only place in the
repo carrying the old name is a `session.created` parse fixture in
`tests/test_xai_realtime_events.py`, which does not depend on the value.
