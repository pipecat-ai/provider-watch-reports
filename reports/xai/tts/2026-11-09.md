# xAI TTS — 2026-11-09

xAI has documented the `replace` pronunciation map on the streaming WebSocket since the last run, so the open HTTP-only PR 5562 is now half the story; nothing else changed.

## What's new for Pipecat

### PRs
- https://github.com/pipecat-ai/pipecat/pull/5562 — Add a replace setting to XAIHttpTTSService (open since 2026-09-01)

### To consider
- **WebSocket `replace` map** (medium, since 2026-11-09) — `wss://api.x.ai/v1/tts` now takes `{"type": "session.update", "replace": {...}}` at any point, answered with `session.updated`, and the map covers every utterance on the connection (an update mid-utterance applies to the next one). A probe sent it and the server echoed the map and synthesized normally. `XAITTSService` has no way to set it: a `replace` field on `XAIWebsocketTTSSettings`, a `session.update` send in `_connect_websocket`, and a `session.updated` branch in `_receive_messages` would cover it — the existing reconnect-on-settings-change path re-sends the map, so runtime updates need no extra logic. PR 5562's description says the WebSocket endpoint has no equivalent, which the docs now contradict. — *Needs a call: fold this into PR 5562, which touches the same settings area and would otherwise conflict, or land it separately?*
- **HTTP language pass-through** (low, since 2026-09-01) — `XAIHttpTTSService.run_tts` sends `str(self._settings.language)` while `XAITTSService` maps through `language_to_xai_language`, so a region variant outside xAI's list (`en-US`, `fr-CA`) reaches the API verbatim from one class and as the base code from the other. `en-US` was accepted in an earlier probe, so nothing fails today. — *Needs a call: is the verbatim pass-through deliberate, or should the HTTP class use the same map?*
- **`optimize_streaming_latency` range** (low, since 2026-09-01) — both Settings docstrings say 0, 1 or 2; the capability page's WebSocket table now documents 0, 1 and 2 as integers, but the REST reference still documents only `"0"` and `"1"`, typed as strings, for `POST /v1/tts`. Integer 1 and 2 were both accepted. — *Needs a call: which page is authoritative for the HTTP endpoint before we narrow the documented range.*

The built-in voice roster is now 28: `aurora` and `liora` joined the 26 from last run, both listed by `GET /v1/tts/voices` and on xAI's flagship-voices page without a release-notes entry. Neither class gates `voice`, so they work today and this is not a gap. There is still no model parameter on either TTS endpoint — the only voice model slugs (`grok-voice-3.0`, `grok-voice-latest`) belong to the Speech-to-Speech realtime API, and October's Grok Voice 2.0 deprecation does not touch these classes. The REST reference's language list (`auto` plus 20 codes) is still fully covered by `language_to_xai_language`. `speed`, `optimize_streaming_latency`, `text_normalization`, `with_timestamps`, codecs and sample rates are all exposed; `bit_rate` applies only to MP3, which these classes do not emit as raw frames. `with_timestamps` on `POST /v1/tts` returns a non-streaming JSON envelope of base64 audio rather than a byte stream, so it is incompatible with the HTTP class's streaming raw-PCM design and is not listed as a gap; the WebSocket class already produces per-word frames. Speech tags remain inline in `text` and need no Settings field.
