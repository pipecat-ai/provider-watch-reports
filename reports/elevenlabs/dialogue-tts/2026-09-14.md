# ElevenLabs Dialogue TTS — 2026-09-14

`eleven_v3_conversational` is still the model ElevenLabs recommends for realtime
v3 synthesis, the catalogue and the Text-to-Dialogue contract are unchanged since
the last run, and no new branch is warranted — the one PR-sized item is already
open as #5554.

## What's new for Pipecat

### PRs
- https://github.com/pipecat-ai/pipecat/pull/5554 — Expose apply_text_normalization on ElevenLabsDialogueTTSService (open since 2026-09-01)

### To consider
- **Pronunciation dictionaries** (medium, since 2026-09-01) — the multi-stream Text-to-Dialogue endpoint accepts `pronunciation_dictionary_locators` on a context's first message, alongside the `voices` and `voice_settings` the service already sends; `ElevenLabsTTSService` takes the same locators as a constructor argument, this class has no way to pass them. — *Needs a call: it means a new constructor argument, and Text-to-Dialogue documents `normalized_alignment` as "reserved for future use, currently unused", so with a dictionary in play the word timestamps built from the raw alignment would no longer match the spoken text.*
- **Multi-speaker contexts** (low, since 2026-09-01) — `eleven_v3` registers up to 10 voices per context and each input names the `voice_id` that speaks it; the service registers only `settings.voice` and tags every input with it, so the dialogue the endpoint is named for cannot be produced. `eleven_v3_conversational`, the default, is capped at one voice per context anyway. — *Needs a call: whether a Pipecat TTS service should express per-utterance speakers, and through what API.*
- **Missing voice** (low, since 2026-09-01) — `_send_context_init` reads the voice through `assert_given`, which only rejects `NOT_GIVEN`, so an unset voice reaches the wire as `voices: [null]`; ElevenLabs answers `Could not validate message: voices.0: Input should be a valid string`, closes the connection, and the turn ends with no audio. `_register_keepalive_context` already handles the unset case with a debug line. — *Needs a call: refuse a missing voice at construction, as a required setting, or keep logging and let the server answer.*

`probe.py run` still cannot probe this class — it hangs past 280 s and prints
nothing, because the service is constructed with `pause_frame_processing=True`
and the probe pipeline has no output transport, so the `EndFrame` never drains
and `cmd_run`'s `logger.remove()` suppresses the service's own metric lines in
the meantime. The row above comes from an ad-hoc script
(`.pw-scratch/dialogue_probe.py`, one synthesis) that runs the same
`[Source, service, Sink]` pipeline, reads the service's `TTFBMetricsData`, and
exits without a graceful shutdown. Fixing `probe.py` for paused services would
save the next researcher this detour.
