# AWS Transcribe STT — 2026-11-23

Two long-standing gaps closed in main since the last run, and nothing from AWS breaks the service; what is left is medium-and-below.

## What's new for Pipecat

### PRs
Nothing.

### To consider

- **Remaining streaming request parameters unreachable** (medium, since 2026-08-31) — out of reach are custom vocabulary and vocabulary filter (`get_presigned_url` already takes `vocabulary_name` and `vocabulary_filter_name`, and the service never passes them), the plural `vocabulary-names` / `vocabulary-filter-names` that AWS requires instead once language identification is on — newly relevant now that Pipecat supports it — plus `vocabulary-filter-method`, PII redaction/identification with `pii-entity-types`, `language-model-name`, and channel identification. — *Needs a call: which subset to expose first. None of them can be probed end to end without account-side resources, so they cannot ride an automatic PR.*
- **Reconnects lose the session** (medium, since 2026-08-31) — the presigned URL carries neither `session-id` nor `session-resume-window`, so when `WebsocketSTTService` reconnects, AWS treats it as a brand-new stream and the in-flight segment is gone. AWS supports resuming within a 1-300 minute window. — *Needs a call: whether resume earns the state it adds, given how short a voice turn is.*
- **The 16 kHz clamp outlives the bug it hid** (low, since 2026-08-31) — the high-priority half of this item is fixed: `09121a6aa` made `STTService` resample each input frame to `send_sample_rate` before `run_stt`, and `df6b9fd46` made AWS Transcribe declare the rate it actually sends, so 24 kHz audio is no longer labelled 16000 and left untouched. The clamp itself remains: `send_sample_rate` returns 16000 for anything other than 8000 or 16000 Hz, so high-rate pipeline audio is downsampled rather than sent as-is, although `MediaSampleRateHertz` is documented as 8000-48000 and the 2026-08-31 run connected URLs declaring 24000 and 48000. The `sample_rate` docstring still tells users AWS supports only 8000 or 16000 Hz and that other values are "clamped". — *Needs a call: pass the pipeline rate through when it is in range, or keep resampling to 16 kHz; the docstring correction follows the decision.*
- **`transcript-format` unreachable, and probably unimplemented over websocket** (low, since 2026-09-14) — the endpoint accepts an unknown value for it while validating known parameters, which is how the 2026-09-14 run concluded it is ignored on the websocket path; a Settings field would be a silent no-op. Not re-probed this run, since neither the API reference nor the service changed. — *Needs a call: whether to ask AWS if `transcript-format` reaches the websocket endpoint at all, before spending the signer plumbing.*
- **No service for the new synchronous TranscribeAudio API** (low, since 2026-11-23) — AWS's one new streaming-adjacent release this fortnight (2026-11-20): a whole clip in one request, transcript in the response, $0.0070/min against streaming's $0.01/min, with diarization, language identification, custom vocabulary and channel identification included. It is a `SegmentedSTTService` shape, so it cannot be reached from the existing websocket class. — *Needs a call: whether a segmented AWS Transcribe service earns its place, trading interim results and latency for about 30% off.*

Closed since the last report: automatic language identification, which #2849 merged on 2026-11-13 — `language_options`, `identify_multiple_languages` and `preferred_language` are Settings fields now, validated at construction and on each update, with each transcription frame carrying the language AWS identified.
