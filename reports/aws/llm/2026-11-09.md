# AWS Bedrock LLM — 2026-11-09

A quiet run: no commit has touched the service since 2026-10-28, Converse's request shape is unchanged, and nothing in the repo pins a retired model. The only item with new evidence is the reasoning-defaults gap, which two models now demonstrate on a single prompt. No branch — every open item still needs a decision first.

## What's new for Pipecat

### PRs

Nothing.

### To consider

- **No reasoning defaults** (high, since 2026-10-28) — `AWSBedrockLLMService` keeps no `_THINKING_DEFAULTS` table, so a reasoning model runs at whatever Bedrock defaults to. On "A barber shaves every man in town who does not shave himself…", `us.moonshotai.kimi-k3.1` (new this run) took TTFAT 3048 ms untouched against 1238 ms with `effort=low`, and `us.xai.grok-4.7` 9007 ms against 5351 ms; Kimi K3.1 even reasons on "What is the capital of France?" when left alone. Bedrock's `effort` is already a Settings field, so the control exists; what is missing is the per-model table CONTRIBUTING.md asks every LLM service for. — *Needs a call: what a Bedrock table keys on, since model ids carry region and vendor prefixes (`us.moonshotai.kimi-k3.1`), and what to do for models whose reasoning control is vendor-specific — Claude's `thinking` block in `additionalModelRequestFields` — rather than Converse's `effort`.*
- **`latency="optimized"` almost never applies** (medium, since 2026-08-31) — unchanged: the latency-optimized page is still a preview covering Nova Pro, Llama 3.1 70B/405B and Claude 3.5 Haiku, and Claude 3.5 Haiku has left the catalogue entirely, so no current Claude model can accept it. The docstring offers it as a plain "standard or optimized" mode. — *Needs a call: whether to name the supported models in the docstring, validate before sending, or drop the field as Bedrock narrows the preview.*
- **Nova 2 Lite as the default** (medium, since 2026-08-31) — the latency picture moved back: TTFAT medians of 5 are 525 ms for `us.amazon.nova-lite-v1:0` against 588 ms for `us.amazon.nova-2-lite-v1:0`, a 12% gap, where last run measured 563/586. The spreads overlap (473–593 against 533–834), so the two are close but Nova 2 Lite is not demonstrably at parity. The default is still ACTIVE with no EOL date, so there is no deadline. — *Needs a call: aiewf-eval still has no Amazon Nova row of any generation, so the benchmark condition for a default bump cannot be met yet.*
- **Structured output, now that Bedrock has shipped it for Claude** (medium, since 2026-08-31) — unchanged since the 2026-10-18 GA: Converse's `outputConfig.textFormat` is a real capability for the Claude models Pipecat users reach for, but the service leaves `supports_response_schema` False, so `run_inference(response_schema=...)` logs "response_schema is not supported and is ignored", and `run_inference`'s own docstring states that "Bedrock's Converse API has no reply schema". `LLMService.model_supports_response_schema` is the hook for a per-model answer; Nova rejects `outputConfig` outright, and AWS warns that some geographic inference profiles do not support it either. — *Needs a call: whether to claim response-schema support and gate it per model, and how a model that rejects `outputConfig` should behave.*
- **Strict tool use** (medium, since 2026-10-28) — Bedrock documents `strict: true` on a Converse tool definition as the way to make tool names and arguments conform to the input schema, and botocore's `ToolSpecification` carries `strict`. The Bedrock adapter emits `toolSpec` with name, description and inputSchema only, so Pipecat function calls are never schema-validated by the provider. — *Needs a call: whether strict tool use should be on for everyone, a Settings opt-in, or decided per tool, and what a model that rejects `strict` should do.*
- **Guardrails** (medium, since 2026-08-31) — ConverseStream's `guardrailConfig` (`guardrailIdentifier`, `guardrailVersion`, `trace`) has no Settings field and is never sent. — *Needs a call: no guardrail exists in the probe account to verify a pass-through against, and guardrail interventions arriving mid-stream need a stance on what the pipeline should see.*
- **`serviceTier` and `Tool.systemTool`** (low, since 2026-08-31) — AWS positions the priority tier as its fastest, which would matter for voice, but the probe account cannot use it: both `us.amazon.nova-lite-v1:0` and `us.anthropic.claude-haiku-5-5` rejected `serviceTier` last run with "The provided service tier is not supported for this model", and nothing in the catalogue suggests that changed. Like `effort`, `serviceTier` is a top-level Converse member, so `additional_model_request_fields` cannot carry it. `Tool.systemTool` is how Nova 2's built-in web grounding and code interpreter are requested, and the adapter emits `toolSpec` tools only. — *Needs a call: whether to add fields the probe account cannot exercise, or leave both until a model that accepts them is in reach.*
- **The service reaches far more than Nova and Claude** (low, since 2026-09-01) — nothing in the class gates the model and Bedrock's text catalogue is 94 model ids; new since the last run are `anthropic.claude-fable-5-2` and `moonshotai.kimi-k3.1`, with both AI21 Jamba models back in the listing as LEGACY. The class docstring still describes the service as Nova and Claude support, and docs.pipecat.ai scopes it the same way (it now mentions Nova 2 once, in a note about thought frames) while its Basic Setup example pins the LEGACY `us.anthropic.claude-sonnet-4-5-20250929-v1:0`. — *Needs a call: whether to widen the wording, and whether the docs change belongs in this repo or in the docs repo.*

Nothing in the repo pins a retired Bedrock model: `us.anthropic.claude-sonnet-4-6` (seven places), `us.amazon.nova-pro-v1:0`, `us.amazon.nova-lite-v1:0` and `us.anthropic.claude-haiku-4-5-20251001-v1:0` are all ACTIVE. Newly LEGACY this run is `anthropic.claude-opus-4-1-20250805-v1:0`, which the repo does not use.

`us.anthropic.claude-fable-5-2` fails through the class, but not for a Pipecat reason: Claude Fable 5.x requires the account's Bedrock data retention mode to be `aws_review`, set through the control plane's `PUT /data-retention`, and a request under `default` is rejected with a ValidationException. There is no request-level field for it, so there is nothing for the service to pass.
