# Google Interactions Vertex LLM — 2026-11-09

The class (added 2026-11-01) is current: it answers on Vertex at `global`, `us` and `eu`, the Interactions API accepts `gemini-3.8-flash`, `gemini-3.6-flash` and `gemini-4-argon` through it, and nothing it names is retiring. The one thing to decide is the default, which is the slower of the two Flash models and disagrees with the non-Vertex Interactions class.

## What's new for Pipecat

### PRs
Nothing.

### To consider
- **The default is the slower Flash, and the two Interactions classes disagree** (medium, since 2026-11-09) — this class defaults to `gemini-3.8-flash`, `GoogleInteractionsLLMService` to `gemini-3.6-flash`. Through this class, interleaved medians of 5 on a trivial prompt put 3.8 Flash at TTFAT 1072 ms against 699 ms for 3.6 Flash, `thinking_ms` 3 for both and no failures either way — the ~1.5x gap `google/vertex-llm` measured on `generateContent`, without the stalls it saw. Quality points the other way: aiewf-eval's medium-context leaderboard has `gemini-3.8-flash (low)` at 99.9% / 1411 ms P50 and `gemini-3.6-flash (minimal)` at 95.1% / 808 ms. Neither model has a shutdown date. — *Needs a call: should the two Interactions classes agree on one default, or is the Vertex pair deliberately on 3.8 for the benchmark score while the Gemini API pair stays on 3.6 for latency?*
- **No first-tier probe for this unit** (medium, since 2026-11-09) — `probe.py`'s `build_kwargs` finds the base class's required `api_key` and passes `GOOGLE_API_KEY`, which this subclass rejects with `ValueError`; and the credential variables it looks for (`GOOGLE_APPLICATION_CREDENTIALS`, `GOOGLE_PROJECT_ID`) are not the ones CI exports (`GOOGLE_VERTEX_TEST_CREDENTIALS`, `GOOGLE_CLOUD_PROJECT_ID`). Every probe below ran through a scratch wrapper. `google/vertex-llm` has the same gap from the same cause, so one fix closes both. — *Needs a call: should `build_kwargs` skip inherited parameters a subclass rejects, and should the Vertex credential variables CI exports be the names `probe.py` looks for?*
- **google-genai 3.0.0 is outside the pin** (low, since 2026-11-09) — released 2026-11-06; the pin allows at most the installed 2.34.0. Little of 3.0.0 reaches this class: Vertex clients still default to `v1beta1` (where Vertex serves Interactions long decodes), and the Interactions changes are a union-typed `CodeExecutionResultStep.result`, Office/OpenDocument MIME types and preserved unknown fields. The move is a google-extra-wide decision. — *Needs a call: when does the google extra move to `<4`, given 3.0.0 also switches the default HTTP client to httpx2 and the Gemini API default version to v1?*

Checked and not a gap: the docstring's claims hold — `us` and `eu` both answer, and `gemini-2.5-flash` is refused with "Model 'gemini-2.5-flash' is not supported by the Interactions API", so "Gemini 3 models and later" is right (the SDK's own Interactions `Model` enum still lists the 2.5 models the API rejects). Vertex express mode is not a gap here as it is on `google/vertex-llm`: the Interactions API does not work under express-mode API-key auth, so the constructor's `api_key` rejection matches the provider. `gemini-4-argon` answers through this class (GA on Vertex 2026-10-13) but is the frontier Pro-class model, not a Flash successor. The example `examples/function-calling/function-calling-google-interactions-vertex.py` pins no model, so it follows the default. `extra` passes any top-level Interactions request key straight through, so Vertex knobs such as `labels` need no new `Settings` field. A `continuation_required` interaction is only warned about, not continued — that affects long decodes (Vertex, GA 2026-11-05, up to 1,048,576 tokens), is base-class behavior shared with `GoogleInteractionsLLMService`, and is out of reach of this service's 4096-token `max_tokens` default.
