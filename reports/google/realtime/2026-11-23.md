# Google Gemini Live — 2026-11-23

`models/gemini-3.8-live` is still Google's GA Live model, with no successor
and no shutdown date, so the default stands. Main has since moved the google
extra to google-genai 3 with the Developer API clients naming `v1beta`, which
closes last run's top item; the one branch this run is a one-line type fix to
the thinking default.

## What's new for Pipecat

### PRs
- https://github.com/pipecat-ai/pipecat/pull/6965 — Send the Gemini Live thinking default as a ThinkingLevel

### To consider

- **Live transcription options** (medium, since 2026-09-01) — `input_audio_transcription` and `output_audio_transcription` are both bare `AudioTranscriptionConfig()`. The SDK type carries nine fields and the API reference publishes `customVocabulary`, `wordTimestamp`, `diarization`, `sourceText` and `mode`; the capabilities guide pushes `custom_vocabulary` for proper nouns (up to 1,000 terms, best around 100), and the reference documents `mode: SMART` for disfluency removal, noting timestamps and diarization are incompatible with it. `GeminiSTTService` reports the same gap from its side. — *Needs a call: one transcription settings shape shared with `GeminiSTTService`, or a Gemini-Live-only field?*
- **Deprecated `generation_config` wrapper** (medium, since 2026-10-12) — `_connect` still assembles `LiveConnectConfig(generation_config=GenerationConfig(...))`, and google-genai 3.2.0 still warns on every connect that the field goes away "in the next major version". With the extra now pinned `>=3.2.0,<4`, that removal lands in a major our cap excludes, so this is scheduled work rather than a break. It is not mechanical: `response_modalities`, `temperature`, `top_p`, `top_k`, `max_output_tokens`, `seed`, `speech_config` and `media_resolution` all exist at the top level of `LiveConnectConfig`, while `frequency_penalty` and `presence_penalty` do not. — *Needs a call: where `frequency_penalty` and `presence_penalty` go once the wrapper is dropped — deprecate them on Settings, or keep the wrapper until the SDK offers a home?*
- **Hybrid VAD** (medium, since 2026-09-01) — unchanged. The capabilities guide's hybrid VAD (server VAD for speech start and as fallback, client VAD sending `audio_stream_end` so the server finalizes without its silence timer) is unreachable: `audio_stream_end` is a real field on `LiveSendRealtimeInputParameters`, and `audioStreamEnd` is in the published realtime-input message, but the service sends it nowhere, leaving only server-VAD-only or fully manual `activity_start`/`activity_end` turns with no pre-roll. `LiveConnectConfig.explicit_vad_signal` is still SDK-only, with no send-side field and no published message. — *Needs a call: should the upstream VAD's stop signal drive `audio_stream_end`, given the service deliberately emits no turn frames of its own?*
- **In-session context updates** (medium, since 2026-11-09) — when the effective system instruction changes or the context brings its own tools, `_handle_context` reconnects the session. `session.send_context_update(system_instruction=..., tools=...)` updates the preamble in order with the rest of the inputs and keeps the socket, but the Live API reference still publishes no such message (only `BidiGenerateContentClientContent` and `HistoryConfig.initialHistoryInClientContent`), and the SDK notes the update invalidates the prefix cache. — *Needs a call: is an in-session update worth probing as a replacement for the reconnect path, given the API reference has not published the message?*
- **`activity_handling` and interim transcript timestamps** (low, since 2026-09-01) — the two `RealtimeInputConfig` fields the service cannot express; `_connect` sets only `automatic_activity_detection` and `turn_coverage` on that config. `NO_INTERRUPTION` disables server-side barge-in; unlike `turn_coverage` it changes who owns interruptions, since the pipeline's own VAD would still interrupt playback locally while the server keeps generating. — *Needs a call: how a server-side `NO_INTERRUPTION` should interact with `broadcast_interruption()` and the pipeline's interruption handling.*
