# Google Gemini Live — 2026-09-14

Nothing moved on Google's side since 2026-09-01: no new conversational Live
model, no shutdown date on the default, and the rejected-language-code failure
is still open. `turn_coverage` shipped, so no branch this run.

## What's new for Pipecat

### PRs
- https://github.com/pipecat-ai/pipecat/pull/5535 — Add a turn_coverage setting to GeminiLiveLLMService (merged 2026-09-03; the setting is in `GeminiLiveLLMSettings` and reaches `realtime_input_config`, so that gap is closed)

### To consider

- **Rejected language codes** (high, since 2026-09-01) — `_connect` always sets `speech_config.language_code` from `Settings.language`, and the default model accepts only part of what `language_to_gemini_language` produces. Re-probed this run with `--setting language=en-GB`: the socket closes with `1007 ... Unsupported language code 'en-GB' for model models/gemini-2.5-flash-native-audio-preview-12-2025`, and the service retries three times before pushing a fatal error. The 2026-09-01 sweep found 14 of the 30 mapped codes rejected (`ar-XA`, `bn-IN`, `cmn-CN`, `en-AU`, `en-GB`, `en-IN`, `es-ES`, `fr-CA`, `gu-IN`, `kn-IN`, `ml-IN`, `mr-IN`, `ta-IN`, `te-IN`), all of them accepted by `gemini-3.1-flash-live-preview`. The Live guide still says native-audio models choose the language themselves and "don't support explicitly setting the language code". — *Needs a call: narrow the map per model, omit `language_code` for native-audio models as the docs suggest, or let the default bump settle it?*
- **gemini-3.1-flash-live-preview as the default** (medium, since 2026-09-01) — unchanged from the last run. The deprecations page lists the current default with `gemini-3.1-flash-live-preview` as its recommended replacement and no shutdown date for either, and 3.1 Flash Live is still labelled preview (released 2026-03-11), so it does not clear the "preview models are never defaults" bar. It connects through `GeminiLiveLLMService` unchanged and takes every language code the service can emit, but it drops `enable_affective_dialog`, proactive audio and NON_BLOCKING async function calling, which `examples/realtime/realtime-gemini-live-async-tool.py` demonstrates. — *Needs a call: is a preview successor that loses affective dialog, proactivity and async tools an acceptable default, or does the bump wait for a GA Live model?*
- **Hybrid VAD** (medium, since 2026-09-01) — the capabilities guide's hybrid VAD (server VAD for speech start, client VAD sending `audio_stream_end` for immediate finalization instead of the server's silence timer) is unreachable: `audio_stream_end` is sent nowhere in the service, leaving only server-VAD-only or fully manual `activity_start`/`activity_end` turns with pre-roll. google-genai exposes an undocumented `LiveConnectConfig.explicit_vad_signal` and a `VadSignalType` enum, but `LiveSendRealtimeInputParameters` has no matching send-side field and the Live docs never mention it, so that is not an alternative today. — *Needs a call: should the upstream VAD's stop signal drive `audio_stream_end`, given the service deliberately emits no turn frames of its own?*
- **Live transcription options** (medium, since 2026-09-01) — `input_audio_transcription` and `output_audio_transcription` are both built as bare `AudioTranscriptionConfig()`. The Live reference documents five fields on that type: `languageCodes`, `customVocabulary`, `wordTimestamp`, `diarization`, and `mode` (VERBATIM/SMART, where SMART does disfluency removal and formatting). `mode` landed in google-genai 2.19.0 — the `>=1.68.0,<3` pin allows it, but the lock resolves 2.18.1, which does not have the field. `GeminiSTTService` reports the same gap from its side. — *Needs a call: one transcription settings shape shared with `GeminiSTTService`, or a Gemini-Live-only field?*
- **`activity_handling`** (low, since 2026-09-01) — with `turn_coverage` merged this is the last `RealtimeInputConfig` field the service cannot express. `NO_INTERRUPTION` disables server-side barge-in; unlike `turn_coverage` it changes who owns interruptions, since the pipeline's own VAD would still interrupt playback locally while the server keeps generating. — *Needs a call: how a server-side `NO_INTERRUPTION` should interact with `broadcast_interruption()` and the pipeline's interruption handling.*
