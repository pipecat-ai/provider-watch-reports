# Inworld TTS — 2026-09-14

`inworld-tts-2` stays the default and Inworld shipped nothing new in the fortnight; the only change to the picture is a parity gap found on re-reading the HTTP schema.

## What's new for Pipecat

Nothing from the provider. Inworld's TTS release notes still end at 2026-08-09 (`inworld-tts-2-flash`) and 2026-08-06 (the request-level `instruction` field), both already covered by the last run and by the open PR. A 2026-09-02 press release announcing the TTS-2 family's GA and pricing repeats the same two models — no new model ID, no schema change. The catalogue is unchanged at `inworld-tts-2` (flagship, "the best choice for production") and `inworld-tts-2-flash`, so the default stays.

New this run: the HTTP synthesize endpoints document `applyTextNormalization`, which `InworldHttpTTSService` never sends, while `InworldTTSService` accepts it as `apply_text_normalization` and puts it in the create-context config.

### PRs
- https://github.com/pipecat-ai/pipecat/pull/5542 — Add an `instruction` Settings field to the Inworld TTS services and drop a retired model string from an example (open since last run)

### To consider
- **Synthesis context** (medium, since 2026-09-01) — the HTTP endpoints accept `synthesisContext.previousRequests`, a chronological list of the text already synthesized in this conversation, which Inworld says improves quality "especially for short or ambiguous input text" — the sentence-at-a-time traffic a pipeline produces. Neither class sends it. — *Needs a call: where the history lives and how far back it goes; this is service state, not a pass-through field.*
- **Text normalization on the HTTP class** (medium, since 2026-09-14) — `applyTextNormalization` (expands numbers, dates, times, abbreviations) is documented on both the HTTP and WebSocket endpoints, but only `InworldTTSService` sends it; `InworldHttpTTSService` has no way to reach it. — *Needs a call: match the WebSocket class with a constructor argument, or move both onto the shared `InworldTTSSettings`; a Settings field alone would give the WebSocket class two ways to set the same thing.*
- **`enhanceGeneration`** (low, since 2026-09-01) — a boolean that denoises the synthesized audio, documented on the HTTP synthesize endpoints and defaulting to false, with no Settings field. — *Needs a call: whether a second HTTP-only field on the shared `InworldTTSSettings` is acceptable, given the WebSocket API does not document it.*
- **Docs page model list** (low, since 2026-09-01) — docs.pipecat.ai still offers `inworld-tts-1.5-max` and `inworld-tts-1.5-mini`, both deprecated at Inworld, and does not mention `inworld-tts-2-flash`. — *Needs a call: the page lives in the docs repo, so someone with access there has to update it.*
- **Dropped `temperature` in the Ultravox example** (low, since 2026-09-01) — `realtime-ultravox-text.py` passes `temperature=1.1` to `InworldTTSService`, which has no such constructor argument; `**kwargs` swallows it and the setting stays `None`. — *Needs a call: the fix is to move the call to `settings=InworldTTSService.Settings(...)`, which changes what the example does (temperature would start applying) rather than just correcting a value.*
- **`bitRate` and character timestamps** (low, since 2026-09-01) — `audioConfig.bitRate` is not settable for the compressed encodings `encoding=` already allows, and `timestampType` is hard-coded to `WORD` though the API also offers `CHARACTER`. — *Needs a call: whether either is worth surfacing, given word timestamps are what the word-timestamp plumbing consumes.*

## Verification

| inworld-tts-2       | InworldTTSService     | ✅ | TTFB 119 ms | single sample; default unchanged                  |
| inworld-tts-2       | InworldHttpTTSService | ✅ | TTFB 249 ms | single sample                                     |

No default bump is proposed, so these are single samples rather than medians. `inworld-tts-2-flash` on `InworldTTSService` was verified last run and nothing in the class or the provider's schema changed, so it was not re-probed.

Two harness notes carried over from the last run, neither a finding about Inworld. `probe.py run --service InworldTTSService` synthesizes but never exits — with no transport in the probe pipeline no `BotStoppedSpeakingFrame` arrives to lift the `pause_frame_processing=True` pause, so `EndFrame` never traverses and the `worker.cancel()` fallback hangs too; because `--json` only prints after the run, the process now produces no output at all and the TTFB above had to be read from `--verbose` logs. And `probe.py` still cannot construct `InworldHttpTTSService`, which has a required `aiohttp_session`; the HTTP rows come from a scratch wrapper that reuses `probe.py`'s `_run_pipeline` and supplies the session.
