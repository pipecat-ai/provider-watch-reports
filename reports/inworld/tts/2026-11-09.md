# Inworld TTS — 2026-11-09

`inworld-tts-2` stays the default and the catalogue is unchanged; the news is Reasoning for TTS-2 (2026-10-28), which no class can reach, and a branch adding the `enhance_generation` pass-through.

## What's new for Pipecat

PR 5542 merged on 2026-11-07, closing last run's two `pr` gaps: `instruction` is now an `InworldTTSSettings` field and the Ultravox example no longer names the retired `inworld-tts-1`. A probe confirms the merged field does what the docstring claims — the same line synthesized with `instruction="speak extremely slowly…"` runs 16.5 s against a ~4 s baseline, matching the inline-tag form exactly. Worth recording for the next researcher: `instruction` has disappeared from the request-schema page, and the endpoint ignores unknown request fields with a 200 rather than rejecting them, so the only way to tell a live field from a dead one here is to measure its effect.

From the provider since the last run:

- **Reasoning** (blog 2026-10-28, `synthesisContext.reasoning` / `reasoningContext`): a model reads the text before synthesis and writes a steering instruction for it. `inworld-tts-2` only, same model ID, rolling out by region. Neither class can set it.
- The HTTP and WebSocket schemas have grown several fields the last reading did not have: workspace pronunciation dictionaries, `lipsyncConfig` visemes, `languageSettings.candidates`, `voiceDesign`, and multi-speaker `script` / `outputMode`. Visemes, voice design and multi-speaker scripts have no counterpart in a Pipecat TTS pipeline, so they are not listed as gaps; the other two are.
- A 2026-09-11 OpenAI-compatible `/v1/audio/speech` endpoint. Nothing for these classes — it is an alternative entry point, already reachable through the OpenAI-compatible TTS service.

### PRs
- https://github.com/pipecat-ai/pipecat/pull/6654 — Add an `enhance_generation` Settings field to the Inworld TTS services

The field was last run's lowest-priority item, held back by the question of whether a second HTTP-only field belongs on the shared `InworldTTSSettings`. Merging `instruction` — the first such field, with the same "the WebSocket API has no equivalent" docstring — answered it.

### To consider
- **Reasoning** (medium, since 2026-11-09) — `synthesisContext.reasoning: REASONING_ON` has Inworld write the delivery direction for each line itself, with `reasoningContext` (≤600 characters) describing the scene or character and the generated instruction returned as `reasoningInstruction`. Inline `[tags]`, which the expression adapter emits, take precedence where they appear. — *Needs a call: whether a TTS service should opt into a pre-synthesis model step at all, since Inworld says it "adds a short step before synthesis starts."*
- **Synthesis context** (medium, since 2026-09-01) — `synthesisContext.previousRequests`, a chronological list of up to 5 earlier texts (2,000 characters combined), which Inworld says improves quality "especially for short or ambiguous input text". Now on the WebSocket create config as well as the HTTP endpoints; neither class sends it. — *Needs a call: where the history lives and how far back it goes; this is service state, not a pass-through field.*
- **Text normalization on the HTTP class** (medium, since 2026-09-14) — `applyTextNormalization` is documented on both transports, but only `InworldTTSService` sends it; `InworldHttpTTSService` has no way to reach it. — *Needs a call: match the WebSocket class with a constructor argument, or move both onto the shared `InworldTTSSettings`; a Settings field alone would give the WebSocket class two ways to set the same thing.*
- **Workspace pronunciation dictionaries** (medium, since 2026-11-09) — `pronunciationDictionarySettings.dictionaries` (1–3 workspace resource names, in priority order) and `enableCustomPronunciation`, both `inworld-tts-2` with a `language` set. Pipecat's inline-IPA path still works, so this is an alternative rather than a hole. — *Needs a call: a shape for a nested list of workspace resource names, plus a stance on the documented mutual exclusion between the two fields.*
- **Language candidates** (low, since 2026-11-09) — the WebSocket create config takes `languageSettings.candidates`, up to 10 BCP-47 tags to constrain auto-detection; the service sends a single `language` or nothing. — *Needs a call: whether a WebSocket-only language shortlist belongs on the shared Settings beside the existing single `language`.*
- **Docs page model list** (low, since 2026-09-01) — docs.pipecat.ai still offers `inworld-tts-1.5-max` and `inworld-tts-1.5-mini`, both deprecated at Inworld, and does not mention `inworld-tts-2-flash`. — *Needs a call: the page lives in the docs repo, so someone with access there has to update it.*
- **Inert `temperature` in the examples** (low, since 2026-09-01) — `realtime-ultravox-text.py` passes `temperature=1.1` as a constructor argument the service does not have, so `**kwargs` swallows it; `voice-inworld.py` sets it through `Settings`, where it reaches the request but Inworld documents `temperature` as ignored on `inworld-tts-2`. Either way the examples suggest a knob that does nothing. — *Needs a call: whether to drop `temperature` from both examples rather than move the first onto `Settings`.*
- **`bitRate` and character timestamps** (low, since 2026-09-01) — `audioConfig.bitRate` is not settable for the compressed encodings `encoding=` already allows, and `timestampType` is hard-coded to `WORD` though the API also offers `CHARACTER`. — *Needs a call: whether either is worth surfacing, given word timestamps are what the word-timestamp plumbing consumes.*

## Verification

| model                             | class                          | ok | latency     | note                                        |
| --------------------------------- | ------------------------------ | -- | ----------- | ------------------------------------------- |
| inworld-tts-2                     | InworldTTSService              | ✅ | TTFB 196 ms | `probe.py run`, single sample               |
| inworld-tts-2                     | InworldHttpTTSService          | ✅ | TTFB 325 ms | baseline                                    |
| inworld-tts-2 + `instruction`     | InworldHttpTTSService          | ✅ | TTFB 334 ms | merged field still accepted                 |
| inworld-tts-2-flash               | InworldHttpTTSService          | ✅ | TTFB 200 ms | works unchanged                             |
| inworld-tts-2 + `enhance_generation=True` | InworldHttpTTSService (branch) | ✅ | TTFB 387 ms | the branch's new field, live                |

No default bump is proposed, so these are single samples rather than medians.

Two measurements behind claims above, both on the non-streaming endpoint with the same sentence. Steering effect: 3.94 s and 4.18 s of audio with no instruction, 16.48 s with `instruction` set to "speak extremely slowly, drawing out every single word", 16.60 s with the same words as an inline `[tag]` — the request-level field is still honored and behaves like the tag. Unknown-field handling: a request carrying an invented field name returned 200 with audio, so acceptance alone proves nothing about a field.

Last run's two harness notes: `probe.py run --service InworldTTSService` now completes and prints its JSON, so the WebSocket row no longer needs log-reading. `probe.py` still cannot construct `InworldHttpTTSService`, which has a required `aiohttp_session`; the HTTP rows come from a scratch wrapper around `probe.py`'s `_run_pipeline`.
