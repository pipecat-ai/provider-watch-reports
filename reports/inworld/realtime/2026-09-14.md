# Inworld Realtime — 2026-09-14

The default `openai/gpt-4.1-mini` is healthy — still in Inworld's router, not on OpenAI's
deprecation list — but four docstrings tell users to pass `openai/gpt-4.1-nano`, which OpenAI
shuts down on 2026-10-23; a branch fixes that. Inworld shipped no release notes since July, so
the standing gaps are unchanged, plus one newly confirmed: `input_image` works on the wire and
is unreachable from Pipecat.

## What's new for Pipecat

### PRs
- https://github.com/pipecat-ai/pipecat/pull/5754 — Stop pointing Inworld Realtime docstrings at a retiring model
- https://github.com/pipecat-ai/pipecat/pull/5541 — Expose Inworld Realtime's documented session fields (server_vad tuning, transcription hints, output speed, noise reduction) (open since last run)

### To consider
- **`providerData` is discarded** (high, since 2026-09-01) — `_send_session_update` replaces `session_properties.provider_data` with `{"metadata": {"sdk": "pipecat-realtime"}}` before sending, so anything a user configures there is dropped. That single field is how Inworld exposes back-channel interjections, responsiveness fillers, automatic memory, STT tuning (voice profile, end-of-turn thresholds), TTS segmentation/delivery/timestamps, prompt caching and `auto_tool_response`. — *Needs a call: merge the user's object under the sdk marker, or model the branches as typed settings — and decide whether a user-supplied `metadata` may replace the marker.*
- **Images unreachable** (medium, since 2026-09-14) — Inworld's realtime API takes `input_image` content parts on `conversation.item.create` (data URL or URL reference, `detail` low/high/auto), and a probe got a completed response out of one. `ItemContent.type` is a closed `Literal` without an image member, there are no `image_url`/`detail` fields, and `llm.py` has no image path at all. — *Needs a call: whether a realtime service consumes `InputImageRawFrame` directly or takes images only from the `LLMContext`, and whether an image append should trigger a response.*
- **Duplicate follow-up after tool results** (medium, since 2026-09-01) — Inworld defaults `providerData.auto_tool_response` to true and starts the response itself once `function_call_output` arrives, but `_process_completed_function_calls` also sends `response.create`; the loser is rejected with `conversation_already_has_active_response`, which `_NON_FATAL_ERROR_CODES` swallows, and the modalities on our `ResponseCreateEvent` never apply. — *Needs a call: set `auto_tool_response=false` to keep Pipecat in control, or stop sending `response.create` after tool results.*
- **LLM generation controls** (medium, since 2026-09-01) — `max_output_tokens`, `tool_choice`, `truncation` and `text_generation_config` (reasoning `effort` NONE…XHIGH, `topP`, penalties, `maxNewTokens`) are unreachable; the inherited `LLMSettings` fields that overlap are logged as unhandled. Reasoning matters here: the router marks most current models reasoning-capable, and Inworld notes they may add latency unless `effort: "NONE"` is set. — *Needs a call: map the inherited `LLMSettings` names onto Inworld's, or expose `text_generation_config` verbatim.*
- **`LLMMessagesAppendFrame` unsupported** (medium, since 2026-09-01) — the handler logs a warning and drops the frame, though `conversation.item.create` expresses exactly this. — *Needs a call: whether an appended message should also trigger a response, given the server owns conversation state.*
- **Per-modality usage dropped** (low, since 2026-09-01) — `response.done` carries `usage.tts.audio_seconds`, `usage.stt.audio_seconds` and the effective router model; only the token counts are read. — *Needs a call: which Pipecat metric a cascaded realtime service reports TTS/STT seconds under.*
