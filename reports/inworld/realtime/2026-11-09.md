# Inworld Realtime — 2026-11-09

The default `openai/gpt-4.1-mini` now has a shutdown date — OpenAI retires it on 2027-01-14 and
Inworld's router drops retired upstream models — but every successor measured here is slower to
first token, so the bump is a maintainer's call rather than an automatic PR. Both PRs from the
last run merged, which closes four gaps including the `providerData` overwrite and the duplicate
tool follow-up. One new bug: a session configured for text-only output pushes no text frames at
all.

## What's new for Pipecat

### PRs
Nothing.

### To consider
- **Default retires 2027-01-14** (high, since 2026-11-09) — OpenAI schedules `gpt-4.1-mini-2025-04-14` for shutdown on 2027-01-14 with `gpt-6-luna` as the replacement, and Inworld's router removes models once upstream retires them (`gpt-4.1-nano`, present last run, is gone from the catalogue since its 2026-10-23 shutdown). The successor is better on quality and worse on latency: aiewf-eval scores `gpt-6-luna (low)` at 91.8% against `gpt-4.1-mini` at 81.8%, while measured through Inworld's realtime API median TTFAT is 821 ms against 504 ms. `openai/gpt-6-luna:fast` lands at 602 ms but is not on the leaderboard. The leaderboard row is at `low` reasoning effort, which this service has no way to request (see the generation-controls item). `examples/realtime/realtime-inworld-locally-driven-turns.py` pins the same model string. — *Needs a call: accept the extra first-token latency for the quality gain, take `openai/gpt-6-luna:fast` on latency grounds without a benchmark row, or leave the OpenAI family — the date forces one of them before 2027-01-14.*
- **Text-only output is silent** (high, since 2026-11-09) — with `output_modalities=["text"]` the server streams `response.output_text.delta` and `response.output_text.done`, and no audio-transcript deltas. Neither type is in `_server_event_types`, so `parse_server_event` returns `None`, the receive loop logs them as unhandled, and `_push_output_transcript_text_frames` is never reached: the pipeline sees no `LLMTextFrame` and no `TTSTextFrame`. `output_modalities` is a documented `SessionProperties` field that `_create_response` forwards verbatim, so this is reachable from ordinary configuration. The fix is an event model for the two types plus a dispatch branch. — *Needs a call: whether a text-only session should push `TTSTextFrame` alongside `LLMTextFrame`, as the audio path does, when there is no audio to aggregate against.*
- **`response.speak` unreachable** (medium, since 2026-11-09) — Inworld shipped `response.speak` on 2026-09-23: supply text and the session's TTS speaks it verbatim, no LLM call, with optional `force_uninterruptible` and `metadata`. A probe got `accepted=true` and a complete audio response. Pipecat already has the frame for this, `TTSSpeakFrame`, and the service ignores it. — *Needs a call: whether a realtime LLM service should consume `TTSSpeakFrame` at all (none does today), and how `force_uninterruptible` squares with Pipecat's own `interruptible` flag.*
- **Images unreachable** (medium, since 2026-09-14) — `conversation.item.create` takes `input_image` parts (data URL or URL, `detail` low/high/auto), confirmed on the wire last run. `ItemContent.type` is a closed `Literal` with no image member, there are no `image_url`/`detail` fields, and `llm.py` has no image path. — *Needs a call: whether a realtime service consumes `InputImageRawFrame` directly or takes images only from the `LLMContext`, and whether an image append should trigger a response.*
- **LLM generation controls** (medium, since 2026-09-01) — `max_output_tokens` (1–4096 or `"inf"`), `tool_choice`, `truncation` and `text_generation_config` (`reasoning.effort` NONE…XHIGH, `reasoning.maxTokens`, `reasoning.exclude`, `topP`, penalties, `maxNewTokens`) are all unreachable; the overlapping inherited `LLMSettings` fields are logged as unhandled. Reasoning effort is what the default-model decision turns on, so this item gates that one. — *Needs a call: map the inherited `LLMSettings` names onto Inworld's, or expose `text_generation_config` verbatim.*
- **`LLMMessagesAppendFrame` unsupported** (medium, since 2026-09-01) — the handler logs a warning and drops the frame, though `conversation.item.create` expresses exactly this. — *Needs a call: whether an appended message should also trigger a response, given the server owns conversation state.*
- **Per-modality usage dropped** (low, since 2026-09-01) — a probe's `response.done` carried `usage.llm.model`, `usage.tts` (`model`, `characters`, `audio_seconds`), `usage.input_token_details` (cached/cache-write/text/audio) and `usage.output_token_details` (text/audio/reasoning); `_handle_evt_response_done` reads only the three totals. — *Needs a call: which Pipecat metric a cascaded realtime service reports TTS/STT seconds and cached tokens under.*
- **Idle timeout has no effect in the pipeline** (low, since 2026-11-09) — the merged session-fields PR exposed `TurnDetection.idle_timeout_ms`, but the server's `input_audio_buffer.timeout_triggered` is unmodelled and dropped, so arming the timer changes nothing downstream. The smart-turn events `input_audio_buffer.turn_suggestion` / `.turn_suggestion_revoked` are unmodelled too. — *Needs a call: which Pipecat frame an idle timeout becomes, given the service already proposes turn boundaries.*

`probe.py run` is connect-only for a realtime class and reports no latency, so the default-bump
comparison was measured ad-hoc: one text turn per connection, three interleaved turns per model,
timed from `response.create` to the first text delta, with the same session properties the service
sends.

Carried forward from the last run and now closed: the `providerData` overwrite (`_send_session_update`
merges the user's object under the sdk marker) and the duplicate follow-up after tool results
(it now sets `auto_tool_response=false`), both fixed in merged work alongside PR #5541's session
fields; and the `gpt-4.1-nano` docstrings, fixed by PR #5754.
