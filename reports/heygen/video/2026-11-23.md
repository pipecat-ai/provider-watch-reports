# HeyGen Video — 2026-11-23

Service is current with LiveAvatar's LITE API — nothing in the changelog since 2026-10-23 touches it — and the open decision is still what to do about the Interactive Avatar default, whose backend HeyGen is actively deleting.

## What's new for Pipecat

### PRs

Nothing. Dedupe found only the two merged provider-watch PRs already accounted for (#5539, #5753); no open one.

### To consider

- **Legacy Interactive Avatar backend is dead** (high, since 2026-09-01) — `HeyGenVideoService` with no `service_type` argument builds a `HeyGenApi` against `https://api.heygen.com/v1/streaming.*`, and those endpoints 404. New today: `GET /v2/avatars`, which still answered 200 on 2026-11-09, now returns 410 `endpoint_retired` pointing at `/v3/avatars`, so HeyGen is removing the legacy surface rather than leaving it dark. Pipecat's examples, the Pipecat docs page and HeyGen's own Pipecat page all tell users to pass `service_type=ServiceType.LIVE_AVATAR`; the constructor default and the `HeyGenVideoService` docstring ("Defaults to using the `Shawn_Therapist_public` avatar with `v2` version") are what still point at the dead API. — *Needs a call: flip the default to `LIVE_AVATAR`, or deprecate `ServiceType.INTERACTIVE_AVATAR` and `api_interactive_avatar.py` on the normal cycle.*
- **`error` and `warning` events go nowhere** (medium, since 2026-09-14) — `_handle_ws_server_event` branches on `session.state_updated` and `agent.state_updated` only; everything else is a trace line. Today's probe sent a bad command and got `error` / `invalid_request_error` back on the live socket. `video_starvation` — LiveAvatar's video generation failing to keep up with the audio Pipecat feeds it — arrives the same way. — *Needs a call: whether these become `push_error` and with what fatality, given `video_starvation` is expected under load.*
- **Commands sent before the session reports `connected`** (medium, since 2026-09-01) — the LITE events page still states the requirement. `HeyGenClient` logs `session.state_updated` and nothing more; `agent.speak` goes out as soon as TTS audio is queued after the WebSocket opens. — *Needs a call: gating means buffering or dropping the first audio, which changes startup timing.*
- **`agora_config` unexposed** (low, since 2026-09-01) — the remaining LITE session field Pipecat cannot set. — *Needs a call: the client only knows how to join the LiveKit room named in the start response, so an Agora-hosted avatar would be unreachable from the service.*
- **`avatar_persona` on a LITE request does nothing** (low, since 2026-09-01) — the field is still absent from `LiteSDKSessionTokenConfigDataSchema`. In LITE mode Pipecat supplies the audio, so voice, context and language belong to the pipeline. — *Needs a call: drop the field, or document it as FULL-mode only.*
- **`agent.speak_started` / `agent.speak_ended` unhandled** (low, since 2026-09-01) — both fired in order in today's session, each echoing the utterance id as `source_event_id`, exactly the correlation TTFB metrics would want. Today TTFB stops on the first `BotStartedSpeakingFrame` decoded off the LiveKit track. — *Needs a call: whether avatar-speech metrics should come from these events instead.*
- **No 429 handling** (low, since 2026-09-14) — 10 req/s per API key and 5 req/s per session token on `sessions/start`, `stop` and `keep-alive`, returning 429 with `Retry-After`. `LiveAvatarApi._request` raises `LiveAvatarApiError` on any non-ok status, so a 429 while creating a session is a setup failure. — *Needs a call: whether the retry belongs in the service or in the application spawning sessions; one bot never approaches the limit.*
