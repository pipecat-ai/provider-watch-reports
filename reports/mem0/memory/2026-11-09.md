# Mem0 memory — 2026-11-09

Still current: the service matches the mem0 2.x contract and the pin `mem0ai>=2,<3` resolves the latest release, 2.2.1. The four known affordance gaps hold unchanged; mem0's new User Profiles API is the only new item, and it is beta.

## What's new for Pipecat

### PRs
Nothing.

### To consider
- **Search options** (medium, since 2026-09-01) — `rerank`, `categories` and metadata filters are not reachable from `InputParams`, nor are `latest_only`, `keyword_search` and `reference_date`. mem0 2.0.0 flipped the `rerank` default from true to false, so Pipecat users silently lost managed reranking on upgrade; `rerank: bool = False` would pass straight through to both clients. `reference_date` is platform-only — OSS `Memory.search` raises on it in 2.2.1. — *Needs a call: reranking costs 150-200 ms per turn on the retrieval path in front of the LLM call, so someone has to say whether it is opt-in only or the new default, and whether cloud-only options belong in an `InputParams` shared by both clients.*
- **Add options** (medium, since 2026-09-01) — `_store_messages` sends `messages` plus a fixed `metadata={"platform": "pipecat"}` and nothing else; `AddMemoryOptions` also carries `custom_instructions`, `agent_custom_instructions`, `infer`, `expiration_date`, `timestamp`, `custom_categories` and `structured_data_schema`. `custom_instructions` (what to extract) and `infer=False` (store verbatim) are the two users typically ask for. — *Needs a call: whether caller metadata merges with or replaces the `platform` tag, and which options to surface individually rather than accepting an options object.*
- **Entity-ID filter semantics differ between the two clients** (medium, since 2026-09-01) — with `local_config` set and more than one of `user_id`/`agent_id`/`run_id` configured, `_retrieve_memories` and `get_memories` pass flat filter keys, which mem0 treats as AND; ANDing `user_id` and `agent_id` matches only records with both fields, which the default extraction path never produces, so recall returns nothing. The cloud path builds `{"OR": [...]}` and works. — *Needs a call: OSS `Memory.search` still raises "filters must contain at least one of: user_id, agent_id, run_id" unless one is a flat top-level key, so a bare OR filter is rejected; aligning the local path needs a decision on the filter shape and a local-client run to confirm.*
- **Synchronous clients on a thread** (low, since 2026-09-01) — every store/search/get_all goes through `asyncio.to_thread` around the sync client; mem0ai 2.x ships `AsyncMemoryClient` and `AsyncMemory`. — *Needs a call: whether the rewrite is worth it, given `to_thread` already keeps the event loop free.*
- **User Profiles** (low, since 2026-11-09) — SDK 2.2.0 (2026-09-23) added `get_profile()`, `generate_profile()` and the profile-settings methods to `MemoryClient`/`AsyncMemoryClient`. A profile is a JSON-Schema-shaped summary of an entity's memories that mem0 refreshes roughly every 10 messages, so seeding context once at session start would avoid a search on every turn. — *Needs a call: the feature is beta and has to be enabled per project by mem0 support, so someone has to say whether it belongs in the service yet, and whether a profile would replace or supplement the per-turn search results.*
