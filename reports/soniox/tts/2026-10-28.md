# Soniox TTS — 2026-10-28

Current: `tts-rt-v2` is the only real Soniox TTS model and the one we ship, at 213 ms median TTFB. Nothing qualifies for a PR; the audio-format item is now backed by a reproduced API rejection and moves to medium.

## What's new for Pipecat

### PRs
Nothing.

### To consider
- **Audio formats beyond PCM16** (medium, since 2026-08-31) — `audio_format` is a free-form constructor argument, but the service treats every `pcm_*` format alike: `setup()` checks `sample_rate` against one flat `VALID_SAMPLE_RATES` set and `_build_config_msg` sends `sample_rate` only when the format starts with `pcm_`. Soniox's format reference is per format — `pcm_mulaw` and `pcm_alaw` allow 8000 Hz only, `flac`/`aac` start at 16000, and `mp3`/`opus`/`aac` take a `bitrate` we never send. A probe this run with `audio_format="pcm_mulaw"` on a 24000 Hz pipeline passed the local check with no warning and came back `400 invalid_request` ("unsupported audio_sample_rate 24000 for format 'pcm_mulaw', allowed: [8000]"), which leaves the service unusable for that turn. Even where the config is accepted, the receive path wraps Soniox's bytes in `TTSAudioRawFrame` without decoding, so mulaw, flac and the lossy formats are not playable downstream. — *Needs a call: whether to model Soniox's per-format rate/bitrate table and expose `bitrate`, or to narrow `audio_format` to the formats the receive path can actually play.*
- **Audio tags reach the word frames** (low, since 2026-09-14) — v2's expressive control is bracketed markup inside the `text`, and Soniox returns the tag characters in the character timestamps, so the word-aligned frames include them (the 2026-09-14 probe turned two tags into `[excited]` and `[calm]` TTSTextFrames, which the RTVI observer forwards as bot-output progress). Nothing misaligns — the aggregated text carries the tags as well — but a bot using v2's headline feature shows markup in its word-by-word output. Re-checked this run: the emotion page still offers no API field, and the timestamps page documents `return_timestamps` as the only option, with nothing to keep tag characters out. — *Needs a call: stripping the markup from the spoken-word frames also means deciding what the aggregated text and the assistant transcript should hold.*
- **Docs name a voice no model lists** (low, since 2026-08-31) — the Pipecat docs page uses `Maya` in its setup example while documenting `Bryce` as the default; the catalogue's 200-voice list has no `Maya` (confirmed again this run), while `Bryce` and `Nora` (both example bots) are in it. Soniox accepts the name and synthesizes anyway, so the example runs. — *Needs a call: the page lives in the docs repo, so it is a separate change from anything here.*
- **Two-minute cap per stream** (low, since 2026-10-12) — Soniox's new real-time limits page states the 2-minute stream duration as fixed and not raisable, and says to start a new stream to continue. A Pipecat turn context is one `stream_id` for the whole turn, so a turn that runs past the cap gets a 413 `max_audio_duration_reached`: the receive loop pushes a non-fatal error, emits `TTSStoppedFrame` and removes the audio context, and the turn's remaining sentences then re-open the stream but have their audio discarded because the context no longer exists. Rare for conversational turns, reachable with long `TTSSpeakFrame` narration. — *Needs a call: whether a turn should roll onto a fresh `stream_id` at the cap or the limit should simply be documented.*

**The catalogue is unchanged.** `GET /v1/tts-models` still returns three ids — `tts-rt-v2` (`aliased_model_id: null`, `supports_voice_cloning`, `supports_silence_reduction`, `supports_timestamps`, `supports_speed_adjustment`, speed 0.7–1.3) with `tts-rt-v1` and `tts-rt-v1-preview` both aliased to it — each carrying the same 200-voice, 63-language list. All 63 codes are reachable through `language_to_soniox_tts_language`, with nothing missing and nothing stale. The only new field on the model entry is `voice_cloning_max_audio_duration_ms: 120000`, which concerns the voice-cloning REST resource rather than this service. Voice entries are `{id, gender, description}`; `voice` is a free string, so none of it needs code.

**The config schema and the connection rules are where they were.** `CreateTTSPayload` in the OpenAPI spec and the WebSocket config table list the same fields as last run, and `bitrate` remains the only one we never send. The keepalive page keeps the rules it was rewritten to last run — keepalive from the moment the connection opens, a ~40 s idle limit, a recommended 20–30 s cadence, no deadline before the first stream and no limit between streams — so the service's connect-in-`setup()` with a 20 s keepalive stays correct and `KEEPALIVE_INTERVAL_SECONDS` sits exactly in the recommended band. The config-message `api_key` field is still deprecated with refusal from 2027-01-15, and Pipecat has sent `Authorization: Bearer` on the connection since 2026-10-09.

Soniox now publishes its own Pipecat TTS integration page. It describes the service as shipped, except that it gives the default voice as `Adrian` (the code's default is `Bryce`) and omits `reduce_silence` and `client_reference_id` from its Settings table; the page is Soniox's, so there is nothing to change here. Nothing from the 2026-10-12 report is unaccounted for.
