# Soniox TTS — 2026-09-14

Current: `tts-rt-v2` is the only Soniox TTS model left and the one we ship; one settings pass-through is on a branch, and idle-connection churn remains the finding worth a maintainer's eyes.

## What's new for Pipecat

### PRs
- https://github.com/pipecat-ai/pipecat/pull/5752 — Expose client_reference_id on SonioxTTSService

### To consider
- **Idle connections churn** (medium, since 2026-08-31) — Soniox's keepalive page still states that keepalive only works after the first stream starts and that a connection producing no audio for more than 3 minutes is closed even with keepalives flowing. `SonioxTTSService` connects in `setup()` and sends the first config only when a turn context is created, so a bot that idles before its first turn hits the ~10s unconfigured close, and one that idles more than 3 minutes between turns hits the no-audio close; in both cases the base websocket reconnect loop opens another connection immediately. Synthesis after the idle still works — the cost is churn, warning-level log noise, and a reconnect that can land while a turn is starting (`_disconnect_websocket` clears the active audio context and `_configured_contexts`). — *Needs a call: the fix is a lifecycle change — open the socket on the first stream instead of in `setup()`, and let an idle connection close instead of reconnecting — not a settings pass-through.*
- **Compressed audio formats** (low, since 2026-08-31) — Soniox takes `bitrate` alongside `sample_rate` for mp3/opus/aac; `audio_format` is a constructor argument that accepts those values, but `bitrate` is never sent. — *Needs a call: the receive path wraps Soniox bytes in `TTSAudioRawFrame` with no decoding, so compressed output is unusable downstream regardless; the choice is exposing `bitrate` or rejecting non-PCM formats.*
- **Audio tags reach the word frames** (low, since 2026-09-14) — v2's expressive control is bracketed markup in the text, and Soniox returns the tag characters in the character timestamps, so the word-aligned frames include them: the probe below turned two tags into `[excited]` and `[calm]` TTSTextFrames, which the RTVI observer forwards as bot-output progress. Nothing misaligns — the aggregated text carries the tags as well — but a bot using v2's headline feature shows markup in its word-by-word output. — *Needs a call: stripping the markup from the spoken-word frames also means deciding what the aggregated text and the assistant transcript should hold.*
- **Docs name a voice no model lists** (low, since 2026-08-31) — the Pipecat docs page uses `Maya` in its setup example; the catalogue's single 200-voice list (shared by all three ids) has no `Maya`. A probe with `voice=Maya` still synthesized audio, so the example runs; the name is just not in the current catalogue. — *Needs a call: the page lives in the docs repo, so it is a separate change from anything here.*

TTFB runs higher than the 121 ms of 2026-09-01; it is runner-and-region noise, and no finding here rests on a latency comparison.

`GET https://api.soniox.com/v1/tts-models` shows the v1 retirement completed: `tts-rt-v1` and `tts-rt-v1-preview` now both carry `aliased_model_id: tts-rt-v2`, and all three ids share one voice list that has grown from 70 to 200 entries (`Bryce`, the shipped default, and `Nora`, used by both example bots, are in it). The catalogue's 63 language codes match `language_to_soniox_tts_language`'s map exactly, so no language is unreachable. `voice` is a free string, so new voices and cloned-voice ids need no code change; v2's `supports_voice_cloning` is satisfied the same way, by passing the cloned id as `voice`. The websocket config schema is unchanged, and with `reduce_silence` merged (#5567) `bitrate` and `client_reference_id` are the only fields left unsent. Nothing from the 2026-09-01 report is unaccounted for.
