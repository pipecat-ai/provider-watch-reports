# Soniox TTS — 2026-09-01

Current: `tts-rt-v2` is Soniox's only active TTS model and the one we ship; the branch adding the one config field the API has and we lack is ready for review, and idle-connection churn remains the finding worth a maintainer's eyes.

## What's new for Pipecat

### PRs
- https://github.com/pipecat-ai/pipecat/pull/5567 — Add a reduce_silence setting to SonioxTTSService

### To consider
- **Idle connections churn** (medium, since 2026-08-31) — Soniox's keepalive page states that keepalive "only works after you start your first stream" and that a connection producing no audio for more than 3 minutes is closed even with keepalives flowing. `SonioxTTSService` connects in `setup()` and sends the first config only when a turn context is created, so a bot that idles before its first turn hits the ~10s unconfigured close, and one that idles more than 3 minutes between turns hits the no-audio close; in both cases the base websocket reconnect loop opens another connection immediately. Synthesis after the idle still works — the cost is churn, warning-level log noise, and a reconnect that can land while a turn is starting (`_disconnect_websocket` clears the active audio context and `_configured_contexts`). — *Needs a call: the fix is a lifecycle change — open the socket on the first stream instead of in `setup()`, and let an idle connection close instead of reconnecting — not a settings pass-through.*
- **Compressed audio formats** (low, since 2026-08-31) — Soniox takes `bitrate` alongside `sample_rate` for mp3/opus/aac; `audio_format` is a constructor argument that accepts those values, but `bitrate` is never sent. — *Needs a call: the receive path wraps Soniox bytes in `TTSAudioRawFrame` with no decoding, so compressed output is unusable downstream regardless; the choice is exposing `bitrate` or rejecting non-PCM formats.*
- **`client_reference_id`** (low, since 2026-08-31) — a documented optional string recorded with the request in Soniox's usage logs, with no Settings field or constructor argument. — *Needs a call: whether per-request usage tagging is something Pipecat should carry.*
- **Docs name a v1-only voice** (low, since 2026-08-31) — the Pipecat docs page for the service uses `Maya` in its setup example; the models endpoint lists `Maya` under `tts-rt-v1` and `tts-rt-v1-preview` only, never `tts-rt-v2`. — *Needs a call: the page lives in the docs repo, so it is a separate change from anything here.*

`GET https://api.soniox.com/v1/tts-models` supplied the catalogue: three entries, `tts-rt-v2` alone with `supports_silence_reduction: true` and the 70-voice list containing `Bryce`; `tts-rt-v1-preview` still aliases `tts-rt-v1`. Emotion and tone in v2 are inline text markup (`[excited]`, `*stress*`), not config fields, so they already pass through `run_tts` untouched; language mixing is automatic from the text with no extra parameter. Nothing from the 2026-08-31 report is unaccounted for.
