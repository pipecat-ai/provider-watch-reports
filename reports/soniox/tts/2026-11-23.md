# Soniox TTS — 2026-11-23

`tts-rt-v2` is still the only Soniox TTS model and probes clean at 237 ms; the new finding is that pre-opening a stream before the first sentence is a request Soniox rejects after ~5 s.

## What's new for Pipecat

### PRs
Nothing.

### To consider
- **Pre-opened streams time out after ~5 s** (high, since 2026-11-23) — the WebSocket page and the keepalive page both state that a stream receiving no `text` for more than a few seconds without `text_end: true` is terminated with `request_timeout`, and that keepalives do not hold a stream open. Measured directly: a stream whose config was sent and nothing else was terminated at 5.2 s with `408 request_timeout` plus `terminated`, identically with keepalives every 5 s and with none at all. `SonioxTTSService.on_turn_context_created` sends the config on `LLMFullResponseStartFrame` to overlap stream creation with sentence aggregation, so every turn whose first sentence takes longer than that window — a thinking LLM, a slow first token — collects the 408. A pipeline probe delaying the first text by 8 s showed the consequence: `_receive_messages` pushes a non-fatal ErrorFrame (`Soniox TTS error 408 request_timeout`, category UNKNOWN since `classify_http_status_code(408)` has no mapping) and the worker logs "Something went wrong", while the audio is unharmed — the audio context is only created when text arrives, so the discard of `_configured_contexts` lets the first sentence re-open the same stream_id and the turn speaks in full. The cost is a false service error on a path where nothing actually failed, which application error handlers are meant to act on (a fallback switch, for instance). — *Needs a call: whether a `request_timeout` on a stream that never received text should be swallowed as the expected outcome of pre-opening, or whether the stream should stop being pre-opened before there is text for it.*
- **Audio formats beyond PCM16** (medium, since 2026-08-31) — `audio_format` is a free-form constructor argument, but the service treats every `pcm_*` format alike: `setup()` checks `sample_rate` against one flat `VALID_SAMPLE_RATES` set and `_build_config_msg` sends `sample_rate` only when the format starts with `pcm_`. Soniox's format reference is per format — `pcm_mulaw` and `pcm_alaw` allow 8000 Hz only, `flac`/`aac` start at 16000, and `mp3`/`opus`/`aac` take a `bitrate` we never send. The 2026-10-28 probe with `audio_format="pcm_mulaw"` on a 24000 Hz pipeline passed the local check with no warning and came back `400 invalid_request` ("allowed: [8000]"); neither the format table nor the service has changed since, so it was not re-probed. Even where the config is accepted, the receive path wraps Soniox's bytes in `TTSAudioRawFrame` without decoding, so mulaw, flac and the lossy formats are not playable downstream. — *Needs a call: whether to model Soniox's per-format rate/bitrate table and expose `bitrate`, or to narrow `audio_format` to the formats the receive path can actually play.*
- **Audio tags reach the word frames** (low, since 2026-09-14) — v2's expressive control is bracketed markup inside the `text`, and Soniox returns the tag characters in the character timestamps, so the word-aligned frames include them (the 2026-09-14 probe turned two tags into `[excited]` and `[calm]` TTSTextFrames, which the RTVI observer forwards as bot-output progress). Nothing misaligns — the aggregated text carries the tags as well — but a bot using v2's headline feature shows markup in its word-by-word output. Re-checked this run: the emotion page still offers no API field, and the timestamps page documents `return_timestamps` as the only option, noting that characters map to Soniox's preprocessed text with nothing to keep tag characters out. — *Needs a call: stripping the markup from the spoken-word frames also means deciding what the aggregated text and the assistant transcript should hold.*
- **Docs name a voice no model lists** (low, since 2026-08-31) — the Pipecat docs page uses `Maya` in its setup example while documenting `Bryce` as the default; the catalogue's 200-voice list has no `Maya` (confirmed again this run), while `Bryce`, `Nora` and `Adrian` are in it. Soniox accepts the name and synthesizes anyway, so the example runs. — *Needs a call: the page lives in the docs repo, so it is a separate change from anything here.*
- **Two-minute cap per stream** (low, since 2026-10-12) — Soniox's limits page still states the 2-minute stream duration as fixed and not raisable, and says to start a new stream to continue. A Pipecat turn context is one `stream_id` for the whole turn, so a turn that runs past the cap gets a 413 `max_audio_duration_reached`: the receive loop pushes a non-fatal error, emits `TTSStoppedFrame` and removes the audio context, and the turn's remaining sentences then re-open the stream but have their audio discarded because the context no longer exists. Rare for conversational turns, reachable with long `TTSSpeakFrame` narration. — *Needs a call: whether a turn should roll onto a fresh `stream_id` at the cap or the limit should simply be documented.*

**The catalogue is unchanged.** `GET /v1/tts-models` still returns three ids — `tts-rt-v2` (`aliased_model_id: null`, voice cloning, silence reduction, timestamps, speed 0.7–1.3, `voice_cloning_max_audio_duration_ms: 120000`) with `tts-rt-v1` and `tts-rt-v1-preview` both aliased to it — each carrying the same 200-voice, 63-language list, with no `Maya`. All 63 codes are reachable through `language_to_soniox_tts_language`. `voice` is a free string, so none of it needs code.

**The config schema and the limits are where they were.** The WebSocket config table lists the same fields as last run and `bitrate` remains the only one we never send; the `api_key` config field is still deprecated with refusal from 2027-01-15, and Pipecat sends `Authorization: Bearer` on the connection. Limits are unchanged (100 requests/min, 3 concurrent streams, 5 streams per connection, 2-minute stream duration, 5,000 characters per text message), as is the audio-format table. Connection-level keepalive rules also stand — from connection open, ~40 s idle limit, 20–30 s recommended cadence, no deadline before the first stream — so `KEEPALIVE_INTERVAL_SECONDS = 20` is right; what the pages make explicit, and the probes confirm, is that the per-stream no-text timer is a separate thing that keepalives do not touch. Soniox's own Pipecat TTS page still differs only in naming `Adrian` as the default voice. Nothing from the 2026-11-09 report is unaccounted for.
