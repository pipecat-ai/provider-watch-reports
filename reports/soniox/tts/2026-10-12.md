# Soniox TTS — 2026-10-12

Current: `tts-rt-v2` is the only Soniox TTS model and the one we ship. Soniox loosened its connection idle rules, so last run's medium idle-churn gap is gone; nothing this run qualifies for a PR.

## What's new for Pipecat

### PRs
Nothing.

### To consider
- **Compressed audio formats** (low, since 2026-08-31) — Soniox takes `bitrate` alongside `sample_rate` for mp3/opus/aac; `audio_format` is a constructor argument that accepts those values, but `bitrate` is never sent. — *Needs a call: the receive path wraps Soniox bytes in `TTSAudioRawFrame` with no decoding, so compressed output is unusable downstream regardless; the choice is exposing `bitrate` or rejecting non-PCM formats.*
- **Audio tags reach the word frames** (low, since 2026-09-14) — v2's expressive control is bracketed markup inside the `text`, and Soniox returns the tag characters in the character timestamps, so the word-aligned frames include them (the 2026-09-14 probe turned two tags into `[excited]` and `[calm]` TTSTextFrames, which the RTVI observer forwards as bot-output progress). Nothing misaligns — the aggregated text carries the tags as well — but a bot using v2's headline feature shows markup in its word-by-word output, and the emotion page still offers no API field and no way to keep tags out of the timestamps. — *Needs a call: stripping the markup from the spoken-word frames also means deciding what the aggregated text and the assistant transcript should hold.*
- **Docs name a voice no model lists** (low, since 2026-08-31) — the Pipecat docs page uses `Maya` in its setup example; the catalogue's 200-voice list has no `Maya` (confirmed again this run), while `Bryce` (our default) and `Nora` (both example bots) are in it. Soniox accepts the name and synthesizes anyway, so the example runs. — *Needs a call: the page lives in the docs repo, so it is a separate change from anything here.*
- **Two-minute cap per stream** (low, since 2026-10-12) — Soniox caps a single TTS request at 2 minutes of audio and says to split longer text across requests. A Pipecat turn context is one `stream_id` for the whole turn, so a turn that runs past the cap gets a 413 `max_audio_duration_reached`: the receive loop pushes a non-fatal error, emits `TTSStoppedFrame` and removes the audio context, and the turn's remaining sentences then re-open the stream but have their audio discarded because the context no longer exists. Rare for conversational turns, reachable with long `TTSSpeakFrame` narration. — *Needs a call: whether a turn should roll onto a fresh `stream_id` at the cap or the limit should simply be documented.*

## Verification

| model     | class            | ok | latency                            | note                                            |
| --------- | ---------------- | -- | ---------------------------------- | ----------------------------------------------- |
| tts-rt-v2 | SonioxTTSService | ✅ | TTFB 251 ms (median of 5, 227–280) | shipped default; 9 word frames, 13 audio frames |
| tts-rt-v2 | ad-hoc websocket | ✅ | —                                  | idle check: open 75 s before the first stream and 210 s between streams, keepalives every 20 s, both followed by successful synthesis |

**Last run's medium gap is closed by Soniox, not by us.** The keepalive page no longer says keepalive counts only after the first stream or that a connection with no audio for 3 minutes is closed; it now states that "Keepalive works from the moment the connection opens", that the connection needs a message at least every 40 seconds and "has no deadline for its first stream", and that "There is no limit on how long a connection may wait between streams." The ad-hoc probe matches: a connection idled 75 s before any stream and 210 s between streams stayed `OPEN` and synthesized afterwards. `SonioxTTSService` connecting in `setup()` with a 20 s keepalive is therefore correct as written — no lifecycle change needed. The only residue is prose: the module comment and `_keepalive_task_handler`'s docstring still say the idle timeout is 20-30 s where the docs now say about 40 s. The cadence is conservative either way, so it is not listed as a gap.

**The `api_key` config field's retirement is already handled.** The websocket reference now marks `api_key` in the config message deprecated and says connections that send the key only there are refused from 2027-01-15. Pipecat sends `Authorization: Bearer` on the connection as of 2026-10-09, so there is nothing to do.

The catalogue is unchanged in substance: `tts-rt-v2` is the only real model (`aliased_model_id: null`, `supports_voice_cloning`, `supports_silence_reduction`, `supports_timestamps`, `supports_speed_adjustment`, speed 0.7–1.3), and `tts-rt-v1` and `tts-rt-v1-preview` both carry `aliased_model_id: tts-rt-v2`. All three ids share one 200-voice, 63-language list; voice entries now carry `gender` and a `description`, which needs no code change because `voice` is a free string. The 63 catalogue codes are all reachable through `language_to_soniox_tts_language` (none missing), including Norwegian after the 2026-10-09 Bokmål fix. The websocket config schema and `CreateTTSPayload` are otherwise unchanged, and `bitrate` remains the only config field we never send. Nothing from the 2026-09-28 report is unaccounted for.
