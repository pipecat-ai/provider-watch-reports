# Soniox TTS — 2026-09-28

Current: `tts-rt-v2` is the only Soniox TTS model and the one we ship, last run's branch merged as #5752, and nothing this run qualifies for a PR.

## What's new for Pipecat

### PRs
Nothing.

### To consider
- **Idle connections churn** (medium, since 2026-08-31) — Soniox's keepalive page still says "Keepalive works only **after** you start your first stream" and that "a connection that generates **no audio for more than 3 minutes** is closed even if keepalives are still flowing"; the connection-level idle limit is about 40 seconds with no active stream and no message. `SonioxTTSService` connects in `setup()` and sends the first config only when a turn context is created, so a bot that idles before its first turn has no way to hold the connection open, and one that idles more than 3 minutes between turns hits the no-audio close; in both cases the base websocket reconnect loop opens another connection immediately. Synthesis after the idle still works — the cost is churn, warning-level log noise, and a reconnect that can land while a turn is starting (`_disconnect_websocket` clears the active audio context and `_configured_contexts`). — *Needs a call: the fix is a lifecycle change — open the socket on the first stream instead of in `setup()`, and let an idle connection close instead of reconnecting — not a settings pass-through.*
- **Compressed audio formats** (low, since 2026-08-31) — Soniox takes `bitrate` alongside `sample_rate` for mp3/opus/aac; `audio_format` is a constructor argument that accepts those values, but `bitrate` is never sent. — *Needs a call: the receive path wraps Soniox bytes in `TTSAudioRawFrame` with no decoding, so compressed output is unusable downstream regardless; the choice is exposing `bitrate` or rejecting non-PCM formats.*
- **Audio tags reach the word frames** (low, since 2026-09-14) — v2's expressive control is bracketed markup inside the `text`, and Soniox returns the tag characters in the character timestamps, so the word-aligned frames include them (last run's probe turned two tags into `[excited]` and `[calm]` TTSTextFrames, which the RTVI observer forwards as bot-output progress). Nothing misaligns — the aggregated text carries the tags as well — but a bot using v2's headline feature shows markup in its word-by-word output. — *Needs a call: stripping the markup from the spoken-word frames also means deciding what the aggregated text and the assistant transcript should hold.*
- **Docs name a voice no model lists** (low, since 2026-08-31) — the Pipecat docs page uses `Maya` in its setup example; the catalogue's 200-voice list has no `Maya` (confirmed again this run), while `Bryce` (our default) and `Nora` (both example bots) are in it. Soniox accepts the name and synthesizes anyway, so the example runs. — *Needs a call: the page lives in the docs repo, so it is a separate change from anything here.*

`client_reference_id` closed: #5752 merged 2026-09-14 and the docs page already documents the field, so it is no longer a gap.

The catalogue is unchanged from last run: `tts-rt-v2` is the only real model, `tts-rt-v1` and `tts-rt-v1-preview` both carry `aliased_model_id: tts-rt-v2`, and all three ids share one 200-voice, 63-language list with `supports_voice_cloning` / `supports_silence_reduction` / `speed` 0.7–1.3. The 63 catalogue codes match `language_to_soniox_tts_language`'s map exactly (no missing, no extra), so no language is unreachable. `voice` is a free string, so new voices — the library grew to 200 on 2026-09-09 — and cloned-voice ids need no code change. Soniox's OpenAPI spec confirms the TTS request schema is unchanged and that `bitrate` is the only field we never send. Soniox also offers a request/response REST TTS endpoint (`POST https://tts-rt.soniox.com/tts`) that Pipecat does not wrap; it returns a complete file, carries no field the WebSocket lacks, and Soniox's own guidance sends low-latency and LLM-driven callers to the WebSocket API, so it is not treated as a gap. Nothing from the 2026-09-14 report is unaccounted for.
