# Soniox STT — 2026-11-23

Current: `stt-rt-v6` remains Soniox's latest real-time model and Pipecat's default, and the probe transcribes cleanly; the new material this run is on the connection, not the model — ping/pong liveness, stream reconnect and `idle_timeout_ms` now appear in the WebSocket reference and none is used.

## What's new for Pipecat

### PRs
Nothing.

### To consider
- **Real-time translation** (medium, since 2026-08-25) — v6 does transcription and translation on one stream via a `translation` config object (`one_way` with `target_language`, or `two_way` with `language_a`/`language_b`); `SonioxSTTSettings` has no field for it and `_connect_websocket` never sends the key. — *Needs a call: translation tokens arrive interleaved with the originals, distinguished only by `translation_status` and carrying no `start_ms`/`end_ms`, so `_receive_messages` would have to decide whether they become their own frames or are dropped from the transcript — not a pass-through field.*
- **No connection liveness** (medium, since 2026-11-23) — Soniox documents a `{"type":"ping","id":N}` control message answered by `pong`, and now recommends it over `keepalive` for new clients precisely because a dropped connection is silent: writes keep succeeding and no close arrives. `_send_keepalive` sends `{"type":"keepalive"}`, which the server never answers, and the base loop only sends it when no audio has gone out for a second — so during a call the service cannot tell a dead socket from a quiet caller. The docs' guidance is to ping every quarter of the idle timeout (5 s at the default) *even while sending audio* and treat a late pong as a lost connection. — *Needs a call: pinging on a fixed interval and acting on a missing pong changes the websocket lifecycle, and the pong deadline arguably belongs in `WebsocketSTTService` for every service rather than in this one.*
- **Stream reconnect** (low, since 2026-11-23) — `"enable_reconnect": true` in the start request makes Soniox send a `reconnect` message with a token and a `reconnect_url`; after a drop the client reconnects there with the token and its `last_seq`, gets the responses it missed, and resends from `last_request + 1`. The stream stays one stream: one transcript, the same speaker labels, one bill, and no extra concurrency slot. Pipecat's reconnect path opens a fresh stream instead and loses all of that. — *Needs a call: this is not a settings field. It needs `seq` tracking, a numbered buffer of every outbound message held until a pong confirms it, rotating tokens, a retry loop bounded by the reconnect window, and `connection_replaced` handling — a decision on whether that belongs in the service.*
- **`idle_timeout_ms`** (low, since 2026-11-23) — a start-request parameter (3000–20000, default 20000) that bounds how long a stream stays open without a client message; lowering it returns the concurrency slot sooner when a connection is lost without a close frame. Not in `SonioxSTTSettings`. — *Needs a call: it is coupled to the keepalive loop, whose interval is 5 s, so values below about 5000 would kill healthy idle streams; it needs the two reconciled, not a straight pass-through.*

Resolved since the last run: https://docs.pipecat.ai/api-reference/server/services/stt/soniox now documents `stt-rt-v6` as the default and lists `enable_agent_text_input`, `enable_echo_cancellation`, `agent_text_lead_ms` and `speaker_format`, so that gap is dropped.

`stt-rt-v5`'s removal on 2026-12-15 is three weeks out, after which requests route to v6 automatically. Pipecat's default is v6 and no example or docstring pins v5; it appears only in `tests/test_soniox_stt.py`, standing for "a model without agent text input" and never reaching the network. Nothing to change.

The start request's `api_key` field stays deprecated, with connections authenticating only that way refused from 2027-01-15. The service sends the key in the `Authorization` header on connect and never puts it in the config message, so nothing is affected — noted again so a future run does not re-derive it.
