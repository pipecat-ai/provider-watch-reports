# NVIDIA STT — 2026-09-01

Nothing to bump: `nemotron-asr-streaming` and `canary-1b-asr` are both live and correct on the hosted NVCF endpoints. The gaps are in how the services express NVIDIA's multilingual ASR and how they report a rejected config.

## What's new for Pipecat

### PRs
Nothing.

### To consider
- **Streaming class skips the locale map** (medium, since 2026-09-01) — `language_to_nvidia_nemotron_speech_language` exists in `nvidia/stt.py` but only `NvidiaSegmentedSTTService` wires it into `language_to_service_language`. `NvidiaSTTService` inherits the base implementation, so `Language.DE` reaches the NIM as `de` where Riva expects `de-DE`. — *Needs a call: whether a three-line override is safe for deployments already passing raw locale strings, and how to verify it — the hosted NVCF deployment is English-only, so it takes a self-hosted multi-type NIM.*
- **Locale map covers 15 of 40 locales** (medium, since 2026-09-01) — Nemotron 3.5 ASR Streaming's `type=multi` transcribes 40 language-locales (release 26.05.0); the map has Arabic, English, French, German, Hindi, Italian, Japanese, Korean, Portuguese (BR), Russian and Spanish. Dutch, fr-CA, pt-PT, Turkish, Ukrainian, Vietnamese, Chinese, Polish, Czech, Swedish and the rest fall back to a bare base code the NIM rejects. — *Needs a call: verification requires a self-hosted multi-type NIM, so the table cannot be extended on probe evidence from the hosted endpoint.*
- **Diarization settings are a no-op on the segmented service** (medium, since 2026-09-01) — `speaker_diarization` and `diarization_max_speakers` are inherited into `NvidiaSegmentedSTTSettings`, but the segmented `_create_recognition_config` never calls `riva.client.add_speaker_diarization_to_config`. Setting them changes nothing and logs nothing. — *Needs a call: whether hosted Canary supports offline diarization at all; if not, the fields belong on the streaming settings class rather than the shared base.*
- **Rejected configs retry forever instead of erroring** (medium, since 2026-09-01) — `_response_handler` funnels every `grpc.RpcError` into `_request_reconnect()`. The language probes below show a permanent `INVALID_ARGUMENT` producing a drop/reconnect cycle and no `ErrorFrame`, so a misconfigured pipeline just goes quiet. — *Needs a call: which gRPC status codes should be fatal rather than retried, and whether that belongs here or in `STTService`'s reconnect policy.*
- **Stale function id in the published docs** (low, since 2026-09-01) — docs.pipecat.ai's NVIDIA STT page gives `ee8dc628-76de-4acc-8595-1836e7e857bd` for `NvidiaSegmentedSTTService`; the code ships `b0e8b4a5-217c-40b7-9b96-17d84e666317`, which is what build.nvidia.com publishes and what transcribed successfully here. — *Needs a call: the fix lives in the docs repo, not this one.*
- **SageMaker default model string unverified** (low, since 2026-09-01) — `cache-aware-parakeet-rnnt-en-US-asr-streaming-sortformer` names the NIM profile behind the SageMaker wrapper. NVIDIA superseded the cache-aware Parakeet streaming line with Nemotron 3.5 ASR Streaming on 2026-06-04, so the string may have moved with it. — *Needs a call: a deployed SageMaker endpoint name to probe against; none is configured in this environment.*
