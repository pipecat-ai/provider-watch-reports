# Bland TTS — 2026-10-12

Nothing to ship: Bland's v2 TTS schema, model list and endpoint set are unchanged since the
2026-09-14 run, and both classes still send every field the API reads. Still unverified live.

## What's new for Pipecat

### PRs

Nothing.

### To consider

- **Turn length cap** (low, since 2026-10-12) — Bland caps a realtime turn at 4,000 characters
  cumulatively across one `context_id` and rejects the overflow with `context_overflow`
  ("One turn exceeded 4,000 characters"); `/v2/tts` caps a request at 5,000. `BlandTTSService`
  streams tokens into a single `context_id` for the whole bot turn and never counts them, so a
  long-form response ends mid-sentence with an ErrorFrame, and `BlandHttpTTSService` gets a 400
  for an over-long text. Rare for conversational turns, reachable for read-aloud use.
  — *Needs a call: whether the service should open a fresh `context_id` when a turn approaches
  the cap (changes turn semantics and billing granularity) or the cap should simply be
  documented on the class.*

## Notes

- **Nothing new from the provider.** The changelog's newest entry is still Adaptive Resumption
  (2026-08-03), with no TTS API surface; the last TTS entries remain BTTS Experimental
  (2026-04-30) and the Bland Speech launch (2026-03-11).
- **Model list unchanged.** `GET /v2/tts-models` still lists `btts-3` (recommended, controls
  calibrated for it, 48 kHz native) and `btts-2` (still synthesizes, controls untuned). The
  model is a property of the voice — the resolved model comes back in the `x-model` response
  header, there is no request field — so `default_model: null` stays correct.
- **Request schema still fully covered.** HTTP `/v2/tts` takes `text`, `voice`,
  `audio.{encoding,sample_rate,container}` and `controls.{expressiveness,stability}`; the
  WebSocket `init` takes `voice`, `audio` and the same two controls, with `speak`,
  `end_of_turn`, `cancel` and `close` as the client messages and the voice fixed for the life of
  the connection. There is still no language, speed or model field anywhere. The only documented
  value not sent is `audio.encoding: mulaw`, which Pipecat cannot use — `TTSAudioRawFrame`
  carries linear PCM and telephony serializers convert at the wire.
- **`auto_formatting` is not in the public reference.** The setting shipped on 2026-10-05
  (`5b2c37005`, authored by a Bland engineer) and is sent top-level on both transports, but
  neither `/api-v2/post/tts`, `/api-v2/post/tts-ws` nor the Writing for Speech page documents
  it — that page says there is no dedicated field for number reading. Unset by default, so no
  user is exposed to it unless they opt in; worth re-checking against the reference each run.
- **New OpenAI-compatible surface, no action.** `POST /v2/audio/speech` implements OpenAI's
  `/audio/speech` contract (`model` = `btts-3`/`btts-2`, OpenAI voice aliases mapped to Karen /
  Matthew / River, `speed` fixed at 1.0, `instructions` ignored). It is a migration path for
  OpenAI SDK users, strictly poorer than the native endpoints the Pipecat classes already call;
  the previous run's index reading did not call it out, so it may predate this run.
- **Concurrency, not rate limits.** An open WebSocket holds one org-wide speech slot until it
  closes (1 slot before a first top-up, 5 after); admission failure surfaces as the
  `rate_limited` error code, which `_connect_websocket` already reports from the non-`ready`
  reply.
- **No SDK.** The `bland` extra has no dependencies; both classes speak HTTP/WebSocket directly,
  so there is no pin to fall behind.
