# Bland TTS — 2026-11-09

Nothing to ship: Bland's v2 TTS schema, model list and endpoint set are unchanged since the
2026-10-12 run, and both classes still send every field the API reads. Still unverified live.

## What's new for Pipecat

### PRs

Nothing.

### To consider

- **Turn length cap** (low, since 2026-10-12) — Bland caps a realtime turn at 4,000 characters
  cumulatively across one `context_id` and rejects the overflow with `context_overflow`
  ("Turn exceeded 4,000 characters"); `/v2/tts` caps a request at 5,000. `BlandTTSService`
  streams tokens into a single `context_id` for the whole bot turn and never counts them, so a
  long-form response ends mid-sentence with an ErrorFrame, and `BlandHttpTTSService` gets a 400
  for an over-long text. Rare for conversational turns, reachable for read-aloud use.
  — *Needs a call: whether the service should open a fresh `context_id` when a turn approaches
  the cap (changes turn semantics and billing granularity) or the cap should simply be
  documented on the class.*

## Notes

- **Nothing new from the provider.** The changelog's newest entry is still Adaptive Resumption
  (2026-08-03), with no TTS API surface; the last TTS entries remain BTTS Experimental
  (2026-04-30) and the Bland Speech launch. A web search for a newer BTTS generation turns up
  only the existing Speech v3 / `btts-3` material.
- **Model list unchanged.** `GET /v2/tts-models` still lists `btts-3` ("Prefer `btts-3` or
  newer", 48 kHz native, controls calibrated for it) and `btts-2` (listed because it still
  synthesizes, controls untuned). Neither is labelled deprecated. The model is a property of the
  voice — the resolved model comes back in the `x-model` response header, there is no request
  field — so `default_model: null` stays correct.
- **Request schema still fully covered.** HTTP `/v2/tts` takes `text`, `voice`,
  `audio.{encoding,sample_rate,container}` and `controls.{expressiveness,stability}`; the
  WebSocket `init` takes `voice`, `audio` and the same two controls, with `speak`,
  `end_of_turn`, `cancel` and `close` as the client messages and the voice fixed for the life of
  the connection. There is still no language, speed, style, seed or model field anywhere — the
  ElevenLabs migration guide says as much explicitly. The only documented value not sent is
  `audio.encoding: mulaw`, which Pipecat cannot use — `TTSAudioRawFrame` carries linear PCM and
  telephony serializers convert at the wire.
- **`auto_formatting` is still not in the public reference.** The setting is sent top-level on
  both transports, but neither `/api-v2/post/tts`, `/api-v2/post/tts-ws` nor the Writing for
  Speech page documents it, and that page still says the only number control is how you write
  the text. Unset by default, so no user is exposed unless they opt in; worth re-checking
  against the reference each run.
- **No expression markup.** Delivery is `controls` plus in-text punctuation, CAPITALS and the
  `<|N|>` pause marker (0.1–10.0 s; above 10.0 fails the request). The `<vocal burst>` string on
  the Writing for Speech page is a spacing illustration, not a documented tag, so the model
  performs no sounds or deliveries and needs no expression adapter.
- **Token streaming is the documented best practice.** Writing for Speech now states that a turn
  sent as one large `speak` returns no audio until `end_of_turn`, while the same words as deltas
  start playing about a second in — which is what `TextAggregationMode.TOKEN`, the class
  default, already does.
- **Browser token endpoint, no action.** `POST /v1/speak/stream-input-token` mints a 5-minute JWT
  passed as a `?token=` query parameter so browsers never hold a long-lived key. Server-side
  Pipecat authenticates with the `Authorization` header the WebSocket reference still documents.
- **Concurrency limits restated.** The limits page now gives a flat default of 1 concurrent
  generation per organization across every speech surface, raised by request rather than by a
  wallet top-up. Admission failure still surfaces as `rate_limited`, which `_connect_websocket`
  already reports from the non-`ready` reply.
- **No SDK.** The `bland` extra has no dependencies; both classes speak HTTP/WebSocket directly,
  so there is no pin to fall behind.
