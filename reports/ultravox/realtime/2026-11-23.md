# Ultravox Realtime — 2026-11-23

Nothing breaks: the catalogue replaced both `ultravox-v0.6` entries with two Inworld-backed models and all three current models answer through the class unchanged, but Ultravox's per-call opt-in for server-VAD turn messages is a capability the service leaves on the table.

## What's new for Pipecat

### PRs
Nothing.

### To consider
- **Server turn messages unused** (medium, since 2026-11-23) — Ultravox sends `user_started_speaking` / `user_stopped_speaking` to any connection that asks for them through `medium.serverWebSocket.dataMessages`; the API accepts the opt-in (probed, 201 with the flags echoed back). The service hardcodes `medium` to `inputSampleRate` alone, so it never asks, and both messages would hit the debug-log default case in `_receive_messages` if they arrived. That is exactly the limitation the class docstring documents — no RTVI speech events, `TurnTrackingObserver`, turn recording, `UserIdleController`, mute strategies or voicemail detection — with a local VAD approximation offered in place of Ultravox's own turn decisions. — *Needs a call: whether server turn frames should be on by default or opt-in, and how they coexist with the local-VAD path the docstring recommends today.*
- **Tool-result options** (medium, since 2026-09-01) — `client_tool_result` accepts `agentReaction` (`speaks` | `listens` | `speaks-once`) and `responseType` (hang-up, new-stage), as well as `errorType`/`errorMessage` and `updateCallState`; `_send_tool_result` sends only `invocationId` and `result`, so a handler cannot make the agent listen after a tool, end the call, or move to another call stage. — *Needs a call: how a function handler would carry these — a result-string convention, a new frame, or a service-level default.*
- **Text-injection urgency** (medium, since 2026-09-01) — `_send_user_text` can pass `urgency`, but only the async-tool progress path does (`soon`/`later`); `InputTextRawFrame` text and async-tool final results take Ultravox's documented default of `soon`, so injected text can never interrupt (`immediate`) and an application has no way to choose. `threadId` is omitted everywhere. — *Needs a call: urgency is per-message, so it needs a stance — a Settings default for all injected text, or a per-frame field.*
- **Query parameters unreachable** (medium, since 2026-11-09) — `priorCallId`, `enableGreetingPrompt` and `throttle` are query parameters on the call-creation endpoints, not body fields, so `extra` — which merges into the JSON body — cannot express them. The greeting prompt showed up in all four connect checks this run: every call opened with "Hello, this is [Your Name]." before answering, and nothing in Pipecat can switch it off. Creating the call outside Pipecat and passing the join URL via `JoinUrlInputParams` covers all three. — *Needs a call: whether params should grow a query-parameter escape hatch (e.g. `extra_query`), or the `JoinUrlInputParams` workaround is the intended answer.*
- **WebSocket medium options unreachable** (medium, since 2026-11-23) — the same hardcoded `medium` hides `clientBufferSizeMs` (default 60 ms; the docs recommend a large value such as 30000 for clients that implement `playback_clear_buffer`, which this service does), `mediaIdleTimeout` (recommended 30–60 s, and documented as a likely future default) and `outputSampleRate`. Reaching any of them means replacing the whole `medium` object through `extra` and restating the sample rate. — *Needs a call: whether the medium sub-object should get its own params fields or `extra` should deep-merge.*
- **Unimplemented protocol messages** (low, since 2026-09-01) — `forced_agent_message`, `hang_up` and `spawn_thread` are never sent; `call_started` (with `callId` and `mediumRestriction`, logged in this run), `pong` and the thread messages only reach the debug log. — *Needs a call: which of these Pipecat should model at all; threads and forced messages have no frame-level equivalent today.*
- **Inert `Settings.model`** (low, since 2026-09-01) — the model is fixed by `OneShotInputParams`, so a model passed in `settings` at construction is dropped silently; runtime updates do warn, and docs.pipecat.ai documents the field as "Not used". — *Needs a call: whether to warn or reject an inert `Settings.model`.*
- **No tier-2 probe** (low, since 2026-09-01) — the constructor takes a required `params` object rather than `api_key`/`model`, so `probe.py run` fails in `build_kwargs` and each run needs an ad-hoc connect script. — *Needs a call: this is a probe.py change (params-object support), not a service change.*

The catalogue change is not a gap. `GET /api/models` now returns `inworld/deepseek-v4.1-flash`, `inworld/gemma4-31b` and `ultravox-v0.7`; `ultravox-v0.6` and `ultravox-v0.6-llama3.3-70b` are gone, with no deprecation entry and no mention in the docs or the blog (Inworld acquired Ultravox in late 2026). Nothing in Pipecat gates the model — `OneShotInputParams.model` is a free string defaulting to `None` — so both new names work as-is (probed), the one retired name appears nowhere in the repo, and `ultravox-v0.7`, the docstring's example, is still served and still the documented server default. The `priorCallId` deprecation tracked last run reached removal on 2026-11-17 without touching Pipecat, which never sends the parameter.

Body-level call parameters remain not-gaps: `extra` merges into the request body, covering `vadSettings`, `firstSpeakerSettings`, `triggers`, `additionalModels`, `mediumRestriction`, `backgroundAudio`, `dataConnection`, `retentionPolicy`, `admissionPreference`, `externalVoice`, `initialState`, `callbacks`, `sharedSecrets` and `transcriptionSettings` (recognition prompts, new since the last run). Deprecated body fields are `firstSpeaker` and `transcriptOptional`, plus the Cartesia voice-override `speed`; none appears in Pipecat.
