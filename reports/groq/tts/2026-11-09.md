# Groq TTS — 2026-11-09

Groq shipped nothing for TTS since the last run and the service is unchanged; the only item
worth a maintainer's time is still the buffered response.

## What's new for Pipecat

### PRs
Nothing.

### To consider
- **The response is buffered, not streamed** (high, since 2026-09-14) — still true, and both
  halves re-measured today on the same text: reading `/audio/speech` through
  `with_streaming_response` gives `transfer-encoding: chunked`, 86 chunks, first bytes at
  0.231 s and completion at 0.901 s, while `run_tts` calls `self._client.audio.speech.create()`
  and the probe pipeline receives a single `TTSAudioRawFrame` with TTFB 1.048 s. Switching to
  the streaming client plus the base class's `_stream_audio_frames_from_iterator(strip_wav_header=True)`
  would stream and retire the per-chunk `wave.open` decode. — *Needs a call: this rewrites
  `run_tts` rather than swapping a value, so a maintainer should own the move to the streaming
  client and the shared audio helper.*
- **`output_format` promises formats Orpheus rejects** (medium, since 2026-09-01) — the
  constructor's `GroqAudioFormat` alias still offers `flac`, `mp3`, `mulaw` and `ogg`; the
  Orpheus page still says the only supported format is `wav`, and a user who sets anything else
  gets an `ErrorFrame` and no audio. Our docs page already spells the constraint out, so the
  code's type hint is the last place promising the other four. — *Needs a call: narrowing the
  public alias to `Literal["wav"]` or dropping the argument is a breaking change.*
- **`Settings.speed` is inert** (low, since 2026-09-01) — `speed=1.5` returns 4.96 s of audio
  for text that renders in 4.96 s at the default. Only an inline comment in `run_tts` records
  this; the `Settings` docstring advertises a "Speech speed multiplier". — *Needs a call:
  document the no-op on the field, or warn when a user sets anything other than 1.0.*
- **200-character input limit is unenforced** (low, since 2026-09-01) — Groq still caps input at
  200 characters per request and Pipecat's sentence aggregation regularly exceeds that, but the
  API accepts longer text, so this is a quality guideline rather than a rejection. — *Needs a
  call: whether over-limit input actually degrades before adding splitting or a warning.*

Groq's catalogue still holds exactly the two Orpheus models with six voices each, the changelog
still ends at 2026-04-18, no Orpheus entry appears on the deprecations page, and the `groq` pin
still covers the latest release. No model string is hard-coded in the examples or the CLI
registry. Two things a future reader should not "fix": the service deliberately never sends
`sample_rate` — passing it only rewrites the WAV header (`sample_rate=16000` returned the same
238,150 bytes with the header relabelled), so the frames would claim a rate the samples do not
have; and the API reference's `response_format` default of `mp3` does not apply to Orpheus,
which returns 24 kHz WAV.

Also resolved since the last run: `probe.py run` no longer stalls on this service, so the
latencies below come from the probe's own metrics rather than `--verbose` logs.
