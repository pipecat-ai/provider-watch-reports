# Groq TTS — 2026-11-23

Nothing moved on Groq's TTS side; the default stands, and the new item is that Orpheus's vocal
directions have no expression adapter.

## What's new for Pipecat

### PRs
Nothing.

### To consider
- **The response is buffered, not streamed** (high, since 2026-09-14) — unchanged. Today's
  `probe.py run` again received a single `TTSAudioRawFrame` for the whole utterance at
  TTFB 996 ms, against first bytes at 0.231 s when the same endpoint is read through
  `with_streaming_response` (measured 2026-11-09; not re-measured today, since neither the
  service nor the API changed). Switching to the streaming client plus the base class's
  `_stream_audio_frames_from_iterator(strip_wav_header=True)` would stream and retire the
  per-chunk `wave.open` decode. — *Needs a call: this rewrites `run_tts` rather than swapping a
  value, so a maintainer should own the move to the streaming client and the shared audio
  helper.*
- **`output_format` promises formats Orpheus rejects** (medium, since 2026-09-01) — the
  constructor's `GroqAudioFormat` alias still offers `flac`, `mp3`, `mulaw` and `ogg` while the
  Orpheus page still says the only supported format is `wav`; the account-wide API reference
  keeps listing all five with an `mp3` default, which is what the alias mirrors. Our docs page
  already spells the constraint out, so the type hint is the last place promising the other
  four. — *Needs a call: narrowing the public alias to `Literal["wav"]` or dropping the argument
  is a breaking change.*
- **No expression adapter for Orpheus's vocal directions** (medium, since 2026-11-23) — new this
  run, because Pipecat's expressive-conversation adapters landed on 2026-10-24 and Groq was not
  revisited against them. `canopylabs/orpheus-v1-english` performs bracketed one- to two-word
  directions covering delivery (`[cheerful]`, `[whisper]`, `[deadpan]`) and sounds
  (`[dramatic gasp]`, `[exasperated sigh]`, `[giggling]`), and Groq states there is no exhaustive
  list — the free-text case `allows_free_text_delivery`/`allows_free_text_sounds` exist for. A
  probe sending that markup synthesized normally (TTFB 790 ms), so the text passes through
  untouched today; the service just never declares the capability. — *Needs a call: directions
  are English-only, so `get_expression_adapter()` would have to choose by model, and an adapter
  brings an `examples/expressive-conversation/` bot and an `evals/release/manifest.yaml` entry
  with it.*
- **`Settings.speed` is inert** (low, since 2026-09-01) — the API accepts 0.5–5 and Orpheus
  ignores it; only an inline comment in `run_tts` records this, while the `Settings` docstring
  advertises a "Speech speed multiplier". — *Needs a call: document the no-op on the field, or
  warn when a user sets anything other than 1.0.*
- **200-character input limit is unenforced** (low, since 2026-09-01) — Groq still caps input at
  200 characters per request and Pipecat's sentence aggregation regularly exceeds that, but the
  API accepts longer text, so this is a quality guideline rather than a rejection. — *Needs a
  call: whether over-limit input actually degrades before adding splitting or a warning.*

Groq's catalogue still holds exactly the two Orpheus models with six voices each, no Orpheus row
appears on the deprecations page (the PlayAI shutdown of 2025-12-31 remains the only TTS entry,
and nothing in the repo references it), and the `groq` pin still covers the latest release. The
changelog's newest entry is 2026-09-21, but its only TTS content is still the 2026-04-18 Arabic
voices — the previous report's "nothing after 2026-04-18" was about TTS, not the page as a whole.
`Settings.model` has no allowlist, so the Arabic model needs only a model plus an Arabic voice.
Two things a future reader should not "fix": the service deliberately never sends `sample_rate`
(passing it only rewrites the WAV header, so the frames would claim a rate the samples do not
have), and the API reference's `response_format` default of `mp3` does not apply to Orpheus,
which returns 24 kHz WAV.
