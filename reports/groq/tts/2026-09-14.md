# Groq TTS — 2026-09-14

`canopylabs/orpheus-v1-english` is still Groq's current English model and the right default;
the open question is latency — Groq streams the audio and the service waits for all of it.

## What's new for Pipecat

### PRs
- https://github.com/pipecat-ai/pipecat/pull/5538 — merged 2026-09-03, reworked in review from
  pinning 24 kHz to letting `sample_rate` float; the sample-rate gap is closed.

### To consider
- **The response is buffered, not streamed** (high, since 2026-09-14) — `/audio/speech` replies
  with `transfer-encoding: chunked` and fills in progressively: 0.5 s of playable audio arrives
  at 0.271 s and 10 s of it by 1.62 s. `run_tts` calls `self._client.audio.speech.create()`,
  which buffers the body, so `iter_bytes()` yields the entire 756 KB in a single chunk and the
  service's measured TTFB for that same text was 2.664 s. `with_streaming_response.create()`
  plus the base class's `_stream_audio_frames_from_iterator(strip_wav_header=True)` would both
  stream and retire the per-chunk `wave.open` decode — which today also tags every frame 24 kHz
  regardless of the rate negotiated at `StartFrame`, leaving the downstream transport to
  resample. — *Needs a call: this rewrites `run_tts` rather than swapping a value, so a
  maintainer should own the move to the streaming client and the shared audio helper.*
- **`output_format` promises formats Orpheus rejects** (medium, since 2026-09-01) — the
  constructor's `GroqAudioFormat` alias offers `flac`, `mp3`, `mulaw` and `ogg`; Groq's Orpheus
  page now says flatly that WAV is the only supported format, and the 2026-09-01 run got
  `400 … response_format must be one of [wav]` for `mulaw`. A user who sets
  `output_format="mp3"` gets an `ErrorFrame` and no audio. — *Needs a call: narrowing the public
  alias to `Literal["wav"]` or dropping the argument is a breaking change, so the choice between
  narrowing, validating at construction, and documenting is a maintainer's.*
- **`Settings.speed` is inert** (low, since 2026-09-01) — Orpheus accepts any `speed` in the
  documented 0.5–5 range and returns byte-identical PCM. Only an inline comment in `run_tts`
  records this; the `Settings` docstring advertises a "Speech speed multiplier", and the Orpheus
  page does not document `speed` at all. — *Needs a call: document the no-op on the field, or
  warn when a user sets anything other than 1.0.*
- **200-character input limit is unenforced** (low, since 2026-09-01) — Groq's Orpheus page caps
  input at 200 characters per request, and Pipecat's sentence aggregation regularly exceeds
  that. A 235-character request synthesized 15.8 s of audio without complaint, so this is a
  quality guideline rather than a rejection. — *Needs a call: whether over-limit input actually
  degrades before adding splitting or a warning.*

Nothing has changed on Groq's side since the last run: the same two Orpheus models, no TTS
entries on the deprecations page (the PlayAI shutdown of 2025-12-31 is long settled and nothing
in the repo references it), no changelog entries after 2026-04-18, and the `groq` pin still
covers the latest release. `Settings.model` has no allowlist, so `canopylabs/orpheus-arabic-saudi`
needs only a model plus an Arabic voice. Orpheus's vocal direction tags (`[cheerful]`,
`[whisper]`) are inline text and pass through unchanged.

## Verification

| model                         | class / path                          | ok | latency                    | note |
| ----------------------------- | ------------------------------------- | -- | -------------------------- | ---- |
| canopylabs/orpheus-v1-english | GroqTTSService, short text            | ✅ | TTFB 1.013 s               | shipped default; TTFA 1.412 s, 0.399 s leading silence |
| canopylabs/orpheus-v1-english | GroqTTSService, 235-char text         | ✅ | TTFB 2.664 s               | TTFA 3.112 s; no error despite the documented 200-char limit |
| canopylabs/orpheus-v1-english | raw `create().iter_bytes()`           | ⚠️ | —                          | one chunk of 756,550 bytes (15.8 s of audio): the body is fully buffered before `run_tts` sees a byte |
| canopylabs/orpheus-v1-english | raw `with_streaming_response`         | ✅ | first bytes 0.212 s        | `transfer-encoding: chunked`, 93 chunks; 0.5 s of audio at 0.271 s, 2 s at 0.478 s, 10 s at 1.62 s, complete at 2.42 s |

`probe.py run` still never prints its JSON for this service: `TTSService._maybe_pause_frame_processing`
holds frame processing until a `BotStoppedSpeakingFrame` the bare probe pipeline never emits, so
the run stalls at shutdown and is killed. Latencies above are read from `--verbose` logs. It is a
harness limitation shared by every TTS service with `pause_frame_processing=True`, not a Groq
defect. Ad-hoc scripts are in `.pw-scratch/groq_tts_chunking.py`, `groq_tts_stream.py`,
`groq_tts_stream2.py`.
