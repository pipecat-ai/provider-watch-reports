# Cartesia TTS — 2026-10-28

No new Cartesia TTS model, so `sonic-3.6` stays the default; the long-blocked `accent` field is now readable from the public Get Voice response, and the branch adds it as a pass-through setting.

## What's new for Pipecat

Cartesia's changelog has no October entries — the newest section is September, which was already covered. The `sonic-2` / `sonic-turbo-*` / `sonic-3-2025-10-27` sunset landed on 2026-10-20 as announced; the only retiring model string left in the repo is the `sonic-2` fallback in `src/pipecat/evals/services.py`, and that is settled (see below). `sonic-3.6` is still GA and recommended, `sonic-3.6-2026-08-27` the stable snapshot, `sonic-preview` the only beta. The WebSocket and HTTP request schemas are unchanged and the pinned `Cartesia-Version: 2026-03-01` carries no end-of-support date. The `cartesia` extra still declares no SDK dependency, so there is nothing to compare against PyPI.

Two items from the previous report are gone. The eval harness's `sonic-2` fallback is decided: PR #6122 was approved but closed with "this code is actually deprecated and not used", recorded in `decisions.md`. And `locale` is no longer a gap — Cartesia's reference now states that `language` and `locale` accept exactly the same values (base codes like `en`, regional codes like `en-GB`), so `locale` is a synonym, and the service already sends regional codes through `language` since the locale map landed.

The `accent` blocker is also gone. Last run the valid accent values were only in Cartesia's authenticated capability guide; the API reference now points at the `accents` field of the Get Voice response, which is readable unauthenticated-by-docs and returns per-voice entries (`british`, `castilian`, `mexican`, …) for the registry's default voice. That makes a pass-through field probeable, and it probes clean: `accent=british` synthesizes on both classes, and a bogus value is rejected by Cartesia with a 400, which confirms the field is genuinely read rather than ignored.

One thing checked and cleared: the API reference abbreviates `generation_config.emotion` to five values, but `CartesiaEmotion` in the expression adapter sends extended ones. A direct `/tts/bytes` call shows `excited` and `joking/comedic` are still accepted, so the adapter and the `GenerationConfig` docstring are correct.

### To consider
- **Dict-valued `generation_config` breaks a turn** (medium, since 2026-09-14) — any dict-shaped settings path — `TTSUpdateSettingsFrame(settings={"generation_config": {...}})`, or `probe.py --setting`, which hit it this run — goes through `CartesiaTTSSettings.from_mapping`, which stores the nested value as a plain `dict`; `_generation_config` then calls `.model_dump()` on it and raises `AttributeError`, so the turn pushes an error and produces no audio. `fish`, `inworld`, `google` and `anthropic` override `from_mapping` for exactly this. — *Needs a call: whether the dict path should coerce into `GenerationConfig` — and what happens to unknown keys — or reject nested values outright.*
- **`add_phoneme_timestamps`** (low, since 2026-08-25) — Cartesia can return phoneme-level timestamps alongside the word timestamps the WebSocket service already consumes. — *Needs a call: a consumer for phoneme timestamps in the pipeline before adding a setting nothing reads.*
